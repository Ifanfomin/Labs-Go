# Тип bool и логические операции

Электронный замок мастерской решает одно: открыть дверь или нет. Правило у
него такое: сотрудник мастерской проходит в рабочее время, с 9:00 до 18:00, а
дежурный проходит в любой час. Замку не нужно число или текст. Ему нужен ответ
«да» или «нет», и этот ответ складывается из нескольких проверок: сотрудник ли
пришедший, который сейчас час, дежурит ли он.

Для таких ответов в Go есть тип `bool`. Из урока 2.1 вы знаете, что у него два
значения, `true` и `false`, и что нулевое значение — `false`. В этом уроке
значения `bool` получаются из сравнений, соединяются операциями «не», «и»,
«или» и возвращаются из функций. К концу урока вы сможете:

- отличить значение `bool` от похожих строки и числа;
- соединить проверки операциями `!`, `&&` и `||` и проследить, какие операнды
  вычислены;
- записать интервал с явными краями и его отрицание;
- вернуть решение из функции одним выражением;
- подобрать входы, на которых неверное правило даёт другой ответ.

Примеры печатают через `fmt.Println` и `fmt.Printf` с глаголами `%v` и `%T` из
урока 2.1; значение `bool` печатается словом `true` или `false`. Код примеров
можно изменить и запустить снова, такие опыты ничем не проверяются.

## Значения типа bool

Тип `bool` хранит ответ на вопрос «да или нет». Значений у него ровно два:
`true` — истина, «да», и `false` — ложь, «нет». Переменная `bool`, объявленная
без начального значения, получает `false`: после `var duty bool` дежурство не
отмечено, пока программа не присвоит `true`.

`true` и `false` — предобъявленные имена, как `int` и `string` в уроке 2.1, а
не ключевые слова. Пишут их без кавычек.

Похожие на них записи значениями `bool` не являются. `"false"` в кавычках —
обычная строка из пяти букв. То, что буквы складываются в слово false, для
типа ничего не значит: в уроке 2.1 строка `"42"` тоже не стала числом.
Программа ниже пытается положить такую строку в переменную `bool`. Прежде чем
читать дальше, скажите, соберётся ли она.

```go
@broken string-false
```

Не соберётся:
`cannot use "false" (untyped string constant) as bool value in variable declaration`.
Строковый литерал нельзя использовать как значение `bool`. Число тоже нельзя:
объявление `var ready bool = 0` компилятор отвергает так же, потому что целый
литерал 0 не годится как значение `bool`. Ноль в Go не означает «ложь», а
единица — «истину».

В переменную `bool` кладут `true`, `false` или выражение, которое даёт `bool`.
Главный источник таких выражений — сравнения.

## Сравнение даёт значение bool

Сравнение отвечает на вопрос о двух значениях, и ответ имеет тип `bool`. В Go
шесть операторов сравнения:

| Запись | Истинно, когда |
|---|---|
| `a == b` | значения равны |
| `a != b` | значения не равны |
| `a < b` | `a` меньше `b` |
| `a <= b` | `a` меньше `b` или равно ему |
| `a > b` | `a` больше `b` |
| `a >= b` | `a` больше `b` или равно ему |

Равенство пишется двумя знаками, `==`; один знак `=` — присваивание из урока
2.1. Две строки равны, только когда совпадают символ в символ, как в уроке
1.12. Заглавная и строчная буква — разные символы, поэтому «Ольга» и «ольга» —
разные строки.

Сравнение — такое же выражение, как сумма в уроке 2.4: его значение можно
напечатать, положить в переменную или вернуть из функции. Программа ниже
сравнивает час, температуру и имя. Прежде чем смотреть вывод, предскажите
каждую строку, а для переменной `open` — ещё и её тип.

```go

### Example: `01-compare`

Источник: `examples/01-compare/`

```go
package main

import "fmt"

func main() {
	hour := 7
	temp := 36.6
	name := "Ольга"

	fmt.Println("hour > 5:", hour > 5)
	fmt.Println("hour == 5:", hour == 5)
	fmt.Println("hour != 5:", hour != 5)
	fmt.Println("temp <= 37.5:", temp <= 37.5)
	fmt.Println("name равно «ольга»:", name == "ольга")

	open := hour >= 9
	fmt.Printf("open = %v, тип %T\n", open, open)
}

```
```

Само по себе сравнение ничего не печатает и ничего не решает. Оно вычисляется
в значение, а что с этим значением делать, решает код вокруг. В последних
строках значение сравнения `hour >= 9` сохранено в переменной `open`.
Переменная объявлена через `:=` от сравнения и получила тип `bool` — так же,
как переменная, объявленная от `true` в уроке 2.1. Сравнение имени дало ложь:
первые буквы у двух строк разные.

Операнды сравнения обязаны быть совместимы. Для типов, которые вы уже знаете,
это значит: либо оба значения одного типа, либо одно из них — литерал, который
помещается в тип другого. Переменная `temp` объявлена от литерала с точкой и
имеет тип `float64`. Литерал `37.5` рядом с ней становится значением
`float64`, как литерал рядом с переменной `int8` в уроке 2.4. А две
переменные разных числовых типов сравнить нельзя, даже когда числа кажутся
сравнимыми:

```go
@broken int-float
```

Компилятор отвечает
`invalid operation: hours > limit (mismatched types int and float64)` — то же
сообщение о несовпадающих типах, что при сложении `int` и `int64` в уроке 2.4.
`hours` объявлена от целого литерала и имеет тип `int`, `limit` — от литерала с
точкой и имеет тип `float64`. Сравнить их можно после явного преобразования
одного значения в тип другого; его разбирает урок 2.9. Почему результаты
вычислений с `float64` часто сравнивают с допуском, а не через `==`, разбирает
урок 2.5.

Не каждый тип допускает все шесть операторов:

| Тип | `==` и `!=` | `<`, `<=`, `>`, `>=` |
|---|---|---|
| целые типы, `float64` | есть | есть |
| `string` | есть | есть; как упорядочены строки, разбирает урок 2.14 |
| `bool` | есть | нет |

Два значения `bool` равны, когда оба `true` или оба `false`. А порядка у `bool`
нет: вопрос «больше ли `true`, чем `false`» в Go не имеет смысла.

```go
@broken bool-order
```

Сообщение `invalid operation: staff < duty (operator < not defined on bool)`
так и говорит: оператор `<` для `bool` не определён. Как сравнивают составные
значения — массивы и структуры, — разбирают уроки модулей 4 и 6.

## Числа и строки не заменяют условие

Во многих языках число или строка сами работают как условие: ноль и пустая
строка считаются ложью, остальное — истиной. В Go такого правила нет. Там, где
нужно условие, язык требует значение `bool`, и никакое другое значение его не
заменяет.

Условие вы видели в уроке 1.12: после `if` стоит сравнение, и тело в фигурных
скобках выполняется, когда сравнение истинно. Программа ниже пытается
поставить после `if` само число — «если есть непрочитанные сообщения».
Прежде чем читать дальше, скажите, что ответит компилятор.

```go
@broken int-condition
```

`non-boolean condition in if statement` — условие в инструкции `if` не
логическое. Число 3 не является ни `true`, ни `false`, и Go не решает за вас,
что оно должно означать. По той же причине операция `!`, которую разбирает
следующий раздел, к числу не применяется. И превратить число или строку в
`bool` преобразованием тоже нельзя.

Починка — назвать правило сравнением. «Есть непрочитанные» значит «число
непрочитанных больше нуля»: `unread > 0`. Для счётчика, который не бывает
отрицательным, то же самое говорит `unread != 0`. Для строки так же: «имя
задано» — это `name != ""`. Сравнение делает правило видимым: читатель кода
видит, с чем сравнивают значение, и не угадывает соглашение.

## Три логические операции: НЕ, И, ИЛИ

Правило замка состоит из трёх вопросов: сотрудник ли пришедший, рабочее ли
сейчас время, дежурит ли он. Ответ на каждый — `bool`. Соединяют такие ответы
три логические операции:

- `!a` — «не `a`». Меняет значение на противоположное: `!true` даёт `false`,
  `!false` даёт `true`. Операнд у `!` один, и знак стоит перед ним.
- `a && b` — «`a` и `b`». Истинно, только когда истинны оба операнда. Так
  записывают требование «нужно и то, и другое»: сотрудник и рабочее время.
- `a || b` — «`a` или `b`». Истинно, когда истинен хотя бы один операнд, в том
  числе оба сразу. Так записывают разрешение «хватит одного из двух»:
  рабочее время или дежурство.

Таблица ниже перебирает все четыре сочетания двух значений; такую таблицу
называют таблицей истинности. В столбце «И» стоит значение `a && b`, в
столбце «ИЛИ» — значение `a || b`.

| `a` | `b` | И | ИЛИ |
|---|---|---|---|
| `false` | `false` | `false` | `false` |
| `false` | `true` | `false` | `true` |
| `true` | `false` | `false` | `true` |
| `true` | `true` | `true` | `true` |

Читайте таблицу по столбцам. У «и» только одна строка с `true` — последняя,
где истинны оба операнда. У «или» только одна строка с `false` — первая, где
ложны оба. Отсюда короткое правило: `&&` ложно, если ложен хотя бы один
операнд; `||` истинно, если истинен хотя бы один.

Операнды всех трёх операций — только значения `bool`. Запись `unread && true`
с числом `unread` не соберётся по той же причине, по которой не собрался `if`
с числом: число не бывает ни истиной, ни ложью.

Знаки удвоены не случайно. Одиночные `&` и `|` в Go тоже есть, но это другие
операции: они работают с отдельными битами целых чисел, и их разбирает урок
2.10. Для условий пишут `&&` и `||`.

Программа ниже отвечает на три вопроса о человеке у двери: он сотрудник,
сейчас нерабочее время, у него дежурство. Прежде чем смотреть вывод, найдите
ответ на каждый вопрос в таблице истинности.

```go

### Example: `02-logic`

Источник: `examples/02-logic/`

```go
package main

import "fmt"

func main() {
	staff := true
	inHours := false
	duty := true

	fmt.Println("сотрудник и рабочее время:", staff && inHours)
	fmt.Println("рабочее время или дежурство:", inHours || duty)
	fmt.Println("сейчас не рабочее время:", !inHours)
}

```
```

Сотрудник пришёл в нерабочее время, поэтому «и» дало ложь: одного истинного
операнда мало. «Или» дало истину, потому что дежурство истинно. `!` превратило
ложное `inHours` в истину.

## Правый операнд вычисляется не всегда

У `&&` и `||` есть свойство, которое видно не по результату, а по тому, что
программа сделала. Go вычисляет эти операции так: сначала левый операнд, и
только потом, если нужно, правый.

- В `a && b`, если `a` ложно, ответ уже известен: `false`, каким бы ни было
  `b`. Правый операнд не вычисляется.
- В `a || b`, если `a` истинно, ответ тоже известен: `true`. Правый операнд не
  вычисляется.
- В остальных случаях — `a` истинно при `&&`, `a` ложно при `||` — ответ
  зависит от `b`, и `b` вычисляется.

Такое поведение называют **сокращённым вычислением**. Вычисление операнда
бывает работой — например, вызовом функции, которая что-то печатает. Если
правый операнд не вычислен, этой работы не происходит.

Программа ниже делает вычисление видимым. Функция `checkBadge` получает имя,
печатает строку о том, чей пропуск проверяет, и возвращает результат
сравнения `name == "Ольга"`: действителен только пропуск Ольги. Строка с
именем служит отметкой — если её нет, функцию не вызывали. В `main` четыре
случая. В каждом программа печатает операцию и значение левого операнда,
затем вычисляет выражение и печатает итог. Прежде чем смотреть вывод, для
каждого случая скажите, появится ли строка о проверке пропуска и каким будет
итог.

```go

### Example: `03-short-circuit`

Источник: `examples/03-short-circuit/`

```go
package main

import "fmt"

// checkBadge печатает, чей пропуск проверяет, и возвращает,
// действителен ли этот пропуск.
func checkBadge(name string) bool {
	fmt.Println("   проверяем пропуск:", name)
	return name == "Ольга"
}

func main() {
	inHours := false
	fmt.Println("1) && при inHours = false")
	open := inHours && checkBadge("Ольга")
	fmt.Println("   итог:", open)

	inHours = true
	fmt.Println("2) && при inHours = true")
	open = inHours && checkBadge("Ольга")
	fmt.Println("   итог:", open)

	duty := true
	fmt.Println("3) || при duty = true")
	open = duty || checkBadge("Иван")
	fmt.Println("   итог:", open)

	duty = false
	fmt.Println("4) || при duty = false")
	open = duty || checkBadge("Иван")
	fmt.Println("   итог:", open)
}

```
```

В первом случае `inHours` ложно, и `&&` дало `false`, не вызывая
`checkBadge`: вне рабочего времени пропуск даже не проверяют. Во втором левый
операнд истинен, ответ зависит от пропуска, и функция вызвана. В третьем
дежурство истинно, `||` уже знает ответ, и пропуск Ивана не проверялся. В
четвёртом дежурства нет, и исход решает только проверка пропуска.

Сравните первый и четвёртый случаи. В первом функцию не вызывали, в четвёртом
вызвали, а итог в обоих — `false`. По итогу не видно, вычислялся ли правый
операнд. Это видно только по действию, которое операнд совершает, — здесь по
напечатанной строке.

Сокращённое вычисление есть только у `&&` и `||`. У сравнения, у сложения из
урока 2.4 и у других операций с двумя операндами вычисляются оба операнда.

Функция `checkBadge` печатает внутри себя только ради наблюдения. Функции
упражнения этого урока ничего не печатают: они возвращают `bool`, а проверка
видит только возвращённое значение.

## Порядок операций и скобки

Правило замка целиком — «сотрудник в рабочее время или дежурный». В коде это
`staff && inHours || duty`. В записи две логические операции, и ответ зависит
от того, какие операнды относятся к какой операции.

Какие операнды к какой операции относятся, решает **приоритет** — правило
группировки. Он говорит, какая операция забирает свои операнды в группу
раньше других, как если бы вокруг неё поставили скобки. Ниже — относительный
приоритет только тех операций, которые нужны в этом уроке; это не полная
таблица операций Go. От сильного уровня к слабому:

1. `!` и унарный минус из урока 2.4; `!` относится только к ближайшему
   операнду справа.
2. `+` и `-` между двумя операндами из урока 2.4.
3. Сравнения `==`, `!=`, `<`, `<=`, `>`, `>=`.
4. `&&`.
5. `||`.

Операции одного уровня группируются слева направо, как `+` и `-` в уроке 2.4.
Отсюда четыре следствия:

- `staff && inHours || duty` группируется как `(staff && inHours) || duty`:
  `&&` забирает свои операнды раньше, чем `||`;
- `!inHours && duty` группируется как `(!inHours) && duty`, а не
  `!(inHours && duty)`;
- `9 <= hour && hour < 18` группируется как `(9 <= hour) && (hour < 18)`:
  сравнения сильнее `&&`, поэтому скобки вокруг них не нужны;
- `hour + 1 < 18` группируется как `(hour + 1) < 18`: с числом 18
  сравнивается сумма.

Приоритет расставляет скобки, но не назначает очередь вычисления. Для `&&` и
`||` после группировки действует правило из раздела о сокращённом
вычислении: у каждой такой операции сначала вычисляется левый операнд, а
правый — только если он нужен. В `duty || staff && inHours` группа
`staff && inHours` сильнее, но она целиком — правый операнд `||`, а левый —
`duty`. Если `duty` истинно, ответ `||` уже известен, и группу программа не
вычисляет вовсе.

Разная группировка означает разные правила. Пусть к двери подошёл дежурный
охранник: он не сотрудник мастерской, время нерабочее, но у него дежурство.
Программа ниже считает для него три записи. Прежде чем смотреть вывод,
расставьте в каждой записи скобки по приоритету и предскажите значение.

```go

### Example: `04-grouping`

Источник: `examples/04-grouping/`

```go
package main

import "fmt"

func main() {
	staff := false
	inHours := false
	duty := true

	fmt.Println("без скобок:", staff && inHours || duty)
	fmt.Println("скобки так, как группирует Go:", (staff && inHours) || duty)
	fmt.Println("скобки вокруг ||:", staff && (inHours || duty))
}

```
```

Первые две записи — одно правило: `&&` сильнее `||`, и скобки во второй
записи только показывают группировку, которую и так задаёт приоритет. Третья
запись, со скобками вокруг `||`, — другое правило: «сотрудник, и при этом
рабочее время или дежурство». По нему дежурный, который не числится
сотрудником, не пройдёт. Скобки вокруг `||` изменили ответ.

Отсюда практическое правило. Когда в одном выражении стоят и `&&`, и `||`,
ставьте скобки так, как задумано правило, даже если приоритет группирует
так же: `(staff && inHours) || duty`. Читатель кода увидит замысел сразу, и
ему не придётся вспоминать приоритеты.

## Интервал: два сравнения через И

Рабочее время — это **интервал**: часы от начала до конца. В математике
интервал пишут одной цепочкой, например 9 ≤ hour ≤ 17. Программа ниже
пробует записать так же интервал с 9 до 17 часов включительно. Прежде чем
читать дальше, скажите, что Go сделает с этой цепочкой.

```go
@broken chained
```

Сообщение
`invalid operation: 9 <= hour <= 17 (mismatched types untyped bool and untyped int)`
объясняет, что произошло. Два сравнения стоят на одном уровне и группируются
слева направо: запись читается как `(9 <= hour) <= 17`. Результат группы
`9 <= hour` — логическое значение, у которого конкретный тип ещё не выбран.
Компилятор называет его `untyped bool`, так же как в уроке 2.4 он называл
целый литерал `untyped int`. Внешнее сравнение сопоставило бы это логическое
значение с числом 17, а логическое значение с числом не сравнивается. Ошибку
находит компилятор до запуска, поэтому программа не выполняется вовсе.

В Go интервал — это два сравнения, соединённые `&&`: одно сравнивает значение
с началом, другое — с концом. Для замка час `hour` — целое число от 0 до 23, и
рабочее время — `9 <= hour && hour < 18`, то есть «час не меньше 9 и меньше
18». Каждое сравнение проверяет свой край, а `&&` требует, чтобы выполнялись
оба.

У каждого края есть решение: входит он в интервал или нет.

- `9 <= hour` — край 9 входит: в 9:00 дверь уже открывается.
- `hour < 18` — край 18 не входит: в 18:00 рабочий день закончен.

Это решение принимает правило задачи, а не язык. Записывайте его явно: `<=`
включает край, `<` не включает. Удобно писать оба сравнения в порядке
числовой оси, меньшее значение слева: `9 <= hour && hour < 18` читается как
отрезок от 9 до 18.

Проверять интервал нужно на краях. Если перепутать `<` и `<=`, ответы внутри
интервала не изменятся, и ошибка проявится только на самом краю. Функция
`inHours` в программе ниже возвращает значение этого интервала. Прежде чем
смотреть вывод, предскажите пять ответов, особенно для 9 и 18 часов.

```go

### Example: `05-interval`

Источник: `examples/05-interval/`

```go
package main

import "fmt"

// inHours сообщает, попадает ли час в рабочее время: с 9:00 включительно
// до 18:00, когда дверь уже закрыта.
func inHours(hour int) bool {
	return 9 <= hour && hour < 18
}

func main() {
	fmt.Println("час 8 —", inHours(8))
	fmt.Println("час 9 —", inHours(9))
	fmt.Println("час 12 —", inHours(12))
	fmt.Println("час 17 —", inHours(17))
	fmt.Println("час 18 —", inHours(18))
}

```
```

В 9 часов край входит в интервал, в 18 — нет. Если бы в записи стояло
`hour <= 18`, ответ поменялся бы только в одной строке — для 18 часов.
Поэтому проверка на краю ловит ошибку в знаке, а проверка в полдень её не
замечает. С `float64` интервал записывается так же:
`36.0 <= temp && temp <= 37.5`.

## Как построить отрицание составного условия

Замку нужно и обратное правило: когда показывать табличку «мастерская
закрыта». Это нерабочее время — все часы, которые не попадают в интервал.
Самая прямая запись — отрицание всего интервала:
`!(9 <= hour && hour < 18)`. Скобки здесь обязательны: без них `!` отнёсся бы
только к ближайшему операнду, а не ко всему интервалу.

Часто полезна запись без внешнего `!`, в которой сразу видно, какие часы
подходят. Её выводят рассуждением:

1. Интервал требует двух условий сразу: час не меньше 9 и час меньше 18.
2. Чтобы требование не выполнилось, достаточно нарушить одно из двух условий.
   Поэтому в отрицании «и» становится «или».
3. Каждое сравнение заменяется противоположным. «Неверно, что `9 <= hour`»
   значит `hour < 9`. «Неверно, что `hour < 18`» значит `hour >= 18`. Край при
   этом переходит на другую сторону: 9 был внутри интервала и в отрицание не
   входит, 18 был снаружи и в отрицание входит.

Получается `hour < 9 || hour >= 18`.

Частая ошибка — перевернуть сравнения, но оставить `&&`:
`hour < 9 && hour >= 18`. Час не бывает одновременно меньше 9 и не меньше 18,
поэтому такое выражение ложно при любом часе. **Контрпример** — вход, на
котором запись расходится с правилом, — находится сразу: в 20 часов
мастерская закрыта, а выражение даёт ложь.

Программа ниже считает три записи для четырёх часов: отрицание всего
интервала, выведенную форму с `||` и ошибочную форму с `&&`. Прежде чем
смотреть вывод, заполните таблицу сами, а для ошибочной формы найдите часы, на
которых она расходится с первой записью.

```go

### Example: `06-negation`

Источник: `examples/06-negation/`

```go
package main

import "fmt"

func main() {
	fmt.Println("час | отрицание | через || | через &&")

	hour := 8
	fmt.Println(hour, "|", !(9 <= hour && hour < 18), "|", hour < 9 || hour >= 18, "|", hour < 9 && hour >= 18)

	hour = 12
	fmt.Println(hour, "|", !(9 <= hour && hour < 18), "|", hour < 9 || hour >= 18, "|", hour < 9 && hour >= 18)

	hour = 18
	fmt.Println(hour, "|", !(9 <= hour && hour < 18), "|", hour < 9 || hour >= 18, "|", hour < 9 && hour >= 18)

	hour = 20
	fmt.Println(hour, "|", !(9 <= hour && hour < 18), "|", hour < 9 || hour >= 18, "|", hour < 9 && hour >= 18)
}

```
```

Первые два столбца совпадают во всех строках: это одно правило, записанное
двумя способами. Третий столбец везде ложен. С правильным ответом он совпадает
только в полдень, а в 8, 18 и 20 часов расходится.

Рассуждение работает и в обратную сторону. «Не (`a` или `b`)» значит «не `a`
и не `b`»: `!(a || b)` совпадает с `!a && !b`. А `!(a && b)` совпадает с
`!a || !b`. Правило одно: при отрицании каждая часть переворачивается, а `&&`
и `||` меняются местами.

Часть таких ошибок можно найти автоматически. Запись `x != 1 || x != 2`
истинна при любом `x`, и команда `go vet` из урока 1.10 выводит о ней
предупреждение `suspect or` («подозрительное или»); `go test` перед тестами
выполняет эту проверку тоже. Но находит `go vet` не всё: ошибочная третья
запись из программы `06-negation` проходит проверку без предупреждений.
Надёжнее проверить правило на контрпримере.

## Функция-предикат возвращает выражение

Функцию, которая отвечает на вопрос «да или нет» и возвращает `bool`,
называют **предикатом**. `inHours` из примера `05-interval` — предикат. Её
тело — одна строка: `return 9 <= hour && hour < 18`.

Ветвление для этого не нужно. Выражение после `return` само вычисляется в
`true` или `false`, и `return` отдаёт это значение вызывающему коду. Запись
«если интервал выполнен, вернуть `true`, иначе вернуть `false`» говорит то же
самое длиннее. Тернарного оператора `?:` из других языков в Go нет, и он здесь
не нужен. Ветвление `if` с `else` как тему разбирает урок 3.1.

Предикат возвращает значение, а не печатает его. Правило урока 1.7 действует
и здесь: напечатанное уходит в вывод программы, а вызывающий код получает
только то, что стоит после `return`. Функция, которая печатает `true` и
возвращает `false`, для вызывающего кода отвечает «нет».

Внутри предиката можно вызвать другой предикат. Например, тело
`return !inHours(hour)` — это отрицание интервала, записанное через уже
готовую функцию. Оно даёт те же ответы, что `hour < 9 || hour >= 18`.

## Как проверить правило, а не один удачный вход

Тест предиката сравнивает возвращённое `bool` с ожидаемым. Как в уроке 1.12,
прошедшая проверка устанавливает ответ только на своём входе. Поэтому входы
выбирают так, чтобы каждая часть правила хоть раз решила исход, а каждая
правдоподобная ошибка дала другой ответ. Для интервала
`9 <= hour && hour < 18`:

- 9 часов, ожидается `true` — отличает запись `9 < hour`, где выпал край 9;
- 18 часов, ожидается `false` — отличает `hour <= 18`, где край 18 попал
  внутрь;
- 8 часов, ожидается `false` — отличает `9 <= hour || hour < 18`: с `||`
  выражение истинно при любом часе;
- 12 часов, ожидается `true` — подтверждает обычный случай, но ни одной из
  этих ошибок не отличает.

Для отрицания `hour < 9 || hour >= 18` есть ещё ошибка «забыли `!`»: функция
вернула сам интервал и расходится с правилом на любом входе. Ошибку «`&&`
вместо `||`» отличает любой час вне интервала, например 20.

Для правила из нескольких частей нужны входы, где решает каждая часть. Для
`(staff && inHours) || duty`: сотрудник в рабочее время без дежурства —
`true`; сотрудник в нерабочее время без дежурства — `false`, время
действительно требуется; не сотрудник в рабочее время без дежурства —
`false`, требуется и сотрудник; не сотрудник в нерабочее время с дежурством —
`true`. Последний вход отличает правило от записи со скобками вокруг `||` из
примера `04-grouping`.

Тест видит только возвращённое значение, а какой операнд вычислялся, не
показывает: в примере `03-short-circuit` первый и четвёртый случаи вернули
одинаковый итог. Порядок вычисления проверяют трассировкой с отметками, как в
том примере, или чтением кода.

В собственном тесте проверка предиката записывается формой из урока 1.12: `if`
с условием провала и `t.Errorf` в фигурных скобках. Если ожидается `true`,
условие провала — `!inHours(9)`: тело выполнится, когда функция вернула
`false`. Если ожидается `false`, условие провала — `inHours(18)`. Здесь `!`
переворачивает ответ функции: ожидаемое «да» даёт ложное условие, и
`t.Errorf` не вызывается, а неожиданное «нет» даёт истинное условие и провал.
Проверка с допуском из урока 2.5 устроена так же: её условие провала —
отрицание условия «значения достаточно близки».

Тела функций — заглушки: все три возвращают `false`. В каждой функции

## Что проверяется, а что нет

Скрытые тесты вызывают ваши функции и сравнивают возвращённые значения с
ожидаемыми:

- `TestComfortable` — `Comfortable` на обоих краях интервала, внутри него, на
  соседних с краями значениях снаружи и далеко с обеих сторон;
- `TestAlarm` — `Alarm` на тех же температурах;
- `TestVentsOpen` — `VentsOpen` на входах, где исход решает каждая часть
  правила по отдельности, и на крае 26/27 градусов.

Тест получает только то, что функция вернула. Текста решения он не видит.
Поэтому проверка не различает, записали вы решение одним выражением или
вызвали другую функцию пакета. Какие операнды программа вычислила, тест тоже
не показывает: это проверяют вопросы квиза.

Ответ проверки бывает двух видов. Если код не собрался, тесты не запускаются,
и проверка показывает сообщение сборки с местом в файле. Если код собрался, но
функция вернула не то, проверка печатает строку `--- FAIL:` с именем теста и
сообщение: какие аргументы переданы, что функция вернула и что должна была
вернуть.

Прежде чем писать тела, для каждой функции выпишите входы, на которых
правдоподобная ошибка даст другой ответ: неверный знак на крае, `||` вместо
`&&`, пропущенный `!`, скобки не на месте. Сверьте свой список с разбором
после попытки, раздел «Какие входы отличают ошибки».

Во всех остальных случаях функция возвращает `false`.

- `VentsOpen(30, true, false)` возвращает `false`: жарко, но идёт дождь;
- `VentsOpen(26, false, false)` возвращает `false`: 26 градусов ещё не жарко;
- `VentsOpen(20, true, true)` возвращает `true`: ручной режим.

# Подсказки

Подсказки читаются по порядку: сначала первая, и только если она не помогла, —
вторая. Готового решения нет ни в одной из них.

## Comfortable

**Ступень 1.** Сколько условий должна выполнить температура, чтобы быть
комфортной, — одно или сразу оба? Для каждого края решите, входит ли он в
интервал, и проверьте решение на 18 и на 26 по постановке.

**Ступень 2.** Нужны два сравнения, по одному на край, соединённые `&&`, как
в разделе «Интервал: два сравнения через И». Оба края входят, поэтому оба
сравнения нестрогие, `<=`. Ошибаются здесь в двух местах: пишут `<` и теряют
край или соединяют сравнения через `||`, и тогда функция истинна при любой
температуре.

## Alarm

**Ступень 1.** Тревога — отрицание комфорта. Если температура нарушила
интервал, какое из двух его условий она нарушила: оба сразу или хватит
одного? Проверьте свой ответ на 17 и на 35 градусах.

**Ступень 2.** Подойдут два пути. Первый — вызвать `Comfortable` и
перевернуть её ответ через `!`. Второй — вывести отрицание, как в разделе «Как
построить отрицание составного условия»: каждое сравнение заменить
противоположным, а `&&` — на `||`. Ошибаются на краях: 18 и 26 комфортны,
поэтому тревоги на них нет, и противоположные сравнения должны быть строгими.

## VentsOpen

**Ступень 1.** В постановке правило разбито на две пронумерованные части, и
форточки открываются, если выполнена хотя бы одна из них. Какая часть сама
требует двух условий сразу? Что в ней сказано о дожде — дождь есть или его
нет?

**Ступень 2.** Первая часть — «жарче 26 и нет дождя»: сравнение с 26 и `!`
перед `rain`, соединённые `&&`. Вторая часть — `manual`, и её присоединяет

жару. Скобки вокруг части с `&&` группировку не меняют и показывают замысел.

# Разбор неверных решений

Читайте этот разбор после попытки: в нём показаны готовые решения задач
упражнения.

## Какие входы отличают ошибки

<!-- review:separating-inputs -->

Постановка просила до написания тел выписать входы, на которых правдоподобная
ошибка даст другой ответ. Вот такой список и то, что отличает каждый вход.

Для `Comfortable`, верное тело `return 18 <= temp && temp <= 26`:

- 18 и 26, ожидается `true`: отличают строгий знак `<` на крае;
- 17 и 27, ожидается `false`: отличают `||` вместо `&&` — с `||` функция
  истинна при любой температуре, — а также край, сдвинутый наружу, например
  `temp <= 27`;
- 22, ожидается `true`: подтверждает обычный случай, но ни одну из этих ошибок
  не отличает.

Для `Alarm`, верное тело `return temp < 18 || temp > 26` или
`return !Comfortable(temp)`:

- 18 и 26, ожидается `false`: отличают `<=` и `>=` вместо строгих знаков;
- 17 и 27, ожидается `true`: отличают `&&` вместо `||` — такая запись ложна
  всегда;
- любой вход: отличает пропущенный `!`, потому что без него функция отвечает
  противоположно на каждой температуре.

Для `VentsOpen`, верное тело `return temp > 26 && !rain || manual`, то есть
`(temp > 26 && !rain) || manual`:

- `(30, false, false)`, ожидается `true`: отличает пропущенный `!` перед
  `rain`;
- `(30, true, false)`, ожидается `false`: проверяет, что дождь действительно
  закрывает форточки;
- `(26, false, false)`, ожидается `false`: отличает `>=` вместо `>`;
- `(20, false, true)`, ожидается `true`: отличает скобки вокруг `||`;
- `(20, false, false)`, ожидается `false`: отличает `||` вместо первого `&&`.

`TestComfortable`, `TestAlarm` и `TestVentsOpen` проверяют ровно такие входы.
Но зелёный тест доказывает ответы только на своих входах. Что правило верно
для любой температуры, показывает рассуждение: каждое сравнение отвечает за
свой край, а `&&` и `||` соединяют их так, как сказано в правиле.

## Края интервала выпали

<!-- review:comfortable-open-ends -->

Решение `return 18 < temp && temp < 26` выглядит как интервал и верно внутри
него: для 22 градусов оно вернёт `true`. Но строгие знаки выбрасывают оба
края, а постановка называет их комфортными.

Ловит это `TestComfortable` на входе `Comfortable(18)`: тест ждёт `true`, а
получает `false`. Знак `<` не включает край, `<=` включает. Решение о крае
принимает правило задачи, и для каждого края его записывают явно:
`return 18 <= temp && temp <= 26`.

## Интервал через «или»

<!-- review:comfortable-or -->

Решение `return 18 <= temp || temp <= 26` читается почти как постановка, но
говорит другое: «не меньше 18 или не больше 26». Любая температура выполняет
хотя бы одно из двух сравнений: 10 градусов не больше 26, а 40 не меньше 18.
Поэтому функция истинна всегда.

Ловит это `TestComfortable` на первом же входе снаружи: для −5 и для 17 тест
ждёт `false`. Интервал требует обоих условий сразу, и соединяет их `&&`.

## Отрицание с «и»

<!-- review:alarm-and -->

Решение `return temp < 18 && temp > 26` перевернуло оба сравнения, но
оставило `&&`. Температура не бывает одновременно ниже 18 и выше 26, поэтому
функция ложна при любом входе.

Ловит это `TestAlarm` на входе `Alarm(-5)`: тест ждёт тревогу, а получает
`false`. При отрицании условия «оба сравнения выполнены» достаточно нарушить
одно из них, поэтому `&&` становится `||`: `return temp < 18 || temp > 26`.

## Края в отрицании

<!-- review:alarm-endpoints -->

Решение `return temp <= 18 || temp >= 26` поменяло `&&` на `||`, но
перевернуло сравнения неточно. Противоположность `18 <= temp` — это
`temp < 18`, а не `temp <= 18`: при отрицании край переходит на другую
сторону.

Ловит это `TestAlarm` на входе `Alarm(18)`: 18 градусов комфортны, тест ждёт
`false`, а решение включает тревогу. Проверяйте выведенное отрицание на самих
краях интервала: если на краю исходное условие истинно, отрицание там обязано
быть ложным.

## Потерянное отрицание

<!-- review:alarm-missing-not -->

Решение `return 18 <= temp && temp <= 26` в `Alarm` — это тело `Comfortable`,
перенесённое без `!`. Оно отвечает противоположно правилу на каждой
температуре.

Ловит это `TestAlarm` на первом же входе. Тревога — отрицание комфорта, и
короче всего записать её через уже готовую функцию: `return !Comfortable(temp)`.

## Пропущенный ! перед rain

<!-- review:vents-missing-not -->

Решение `return temp > 26 && rain || manual` потеряло `!` и открывает
форточки в жару только под дождём — ровно наоборот.

Ловит это `TestVentsOpen` на входе `VentsOpen(30, false, false)`: жарко, дождя
нет, тест ждёт `true`, а получает `false`. Условие «нет дождя» — это `!rain`:
истинно, когда `rain` ложно.

## Скобки вокруг «или»

<!-- review:vents-grouping -->

Решение `return temp > 26 && (!rain || manual)` на жаре работает верно, и
пример `VentsOpen(30, false, false)` его не ловит. Но скобки изменили правило:
теперь это «жарко, и при этом нет дождя или включён ручной режим». Ручной
режим перестал работать без жары.

Ловит это `TestVentsOpen` на входе `VentsOpen(20, false, true)`: ручной режим
включён, тест ждёт `true`, а получает `false`. Без скобок `&&` забирает свои
операнды в группу раньше `||`, и запись `temp > 26 && !rain || manual` уже
означает то, что нужно. Скобки вокруг части с `&&` делают это видимым:
`return (temp > 26 && !rain) || manual`.

## Край 26 градусов

<!-- review:vents-endpoint -->

Решение `return temp >= 26 && !rain || manual` открывает форточки уже при 26
градусах. По постановке 26 ещё комфортно, а открывать нужно, когда жарче.

Ловит это `TestVentsOpen` на входе `VentsOpen(26, false, false)`: тест ждёт
`false`, а получает `true`. «Жарче 26» — это строгое `temp > 26`.

## Вопрос 1

Какие из четырёх объявлений соберутся?

- A. Только первое.
- B. Первое и четвёртое.
- C. Первое, второе и четвёртое.

```

Варианты ответа:

- A. Программа напечатает истину: ноль считается ложью, а `!` превращает её в

- B. Программа не соберётся: `!` применяется только к `bool`. Верное правило —

**Правильный ответ: B.**

2. `temp <= 37.5`
3. `staff == duty`

- A. Все четыре.
- B. Второе и третье.
- C. Первое, второе и третье.

## Вопрос 4

Функция `check` печатает отметку с именем операнда и возвращает переданное
значение.

```go

```

Что напечатает программа?

Варианты ответа:

- A. Для первой записи — отметки про a, b и c и итог `true`; для второй —
  отметки про a, b и c и итог `false`.
- B. Для первой записи — только отметка про a и итог `true`; для второй —
  отметки про a и c и итог `false`.
- C. Для первой записи — только отметка про a и итог `true`; для второй —
  только отметка про a и итог `true`.
- D. Для первой записи — отметки про b и c, затем про a и итог `true`; для
  второй — отметки про a и c и итог `false`.

Прежде чем смотреть ответ, расставьте скобки в первой записи по приоритету.

**Правильный ответ: B.**

2. `inHours || !holiday || duty` — `||` вместо `&&`;
3. `inHours && (!holiday || duty)` — скобки вокруг `||`.

Для каждой версии нужен вход — значения `inHours`, `holiday`, `duty` по
порядку, — на котором она даёт другой ответ, чем верная запись. Какой набор
входов подходит для всех трёх версий?

Варианты ответа:

- A. 1 — `(true, false, false)`; 2 — `(false, false, false)`;
  3 — `(false, false, true)`.
- B. 1 — `(true, false, true)`; 2 — `(false, false, false)`;
  3 — `(false, false, true)`.
- C. 1 — `(true, false, false)`; 2 — `(true, false, false)`;
  3 — `(false, false, true)`.
- D. 1 — `(true, false, false)`; 2 — `(false, false, false)`;
  3 — `(true, true, true)`.

Прежде чем смотреть ответ, для каждой версии вычислите обе записи на
выбранном входе и назовите часть правила, которая решила исход.

**Правильный ответ: A.**

Версия 1 на рабочем дне без праздника и дежурства даёт ложь, а верная запись
— истину: отличие решает `!holiday`. Версия 2 при нерабочем времени без
праздника и дежурства даёт истину, потому что `!holiday` уже истинно, а
верная запись требует рабочего времени. Версия 3 для дежурного в нерабочее
время даёт ложь: скобки подчинили дежурство рабочему времени. В варианте B
вход для версии 1 содержит дежурство, и обе записи дают истину. В варианте C
для версии 2 выбран рабочий день без праздника, где обе записи истинны. В
варианте D для версии 3 выбран вход, где обе записи тоже истинны: ответ даёт
дежурство, и скобки его не отменяют.
