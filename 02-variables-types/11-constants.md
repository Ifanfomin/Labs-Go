# Константы

Мастерская режет фанеру по чертежам в дюймах, а станок принимает сантиметры.
В одном дюйме ровно 2.54 сантиметра, и это число появляется в расчётах снова и
снова. Написать его цифрами в пяти местах опасно: опечатка в одном из них не
остановит сборку, и программа посчитает одну деталь не так, как остальные.
Поэтому множителю дают имя и объявляют его один раз — словом `const`.

Слово `constant` вы уже видели в сообщениях компилятора в уроках 2.4, 2.5 и
2.9. Этот урок объясняет правило целиком: что разрешено писать справа от знака
равенства, как константа получает тип, почему промежуточное вычисление точно,
а итог обязан поместиться в свой тип, что даёт имя множителю и чего оно не
даёт. Попутно до конца объясняются два опыта — округление дробей из урока 2.5 и
выход за диапазон из урока 2.4.

Код примеров можно изменить и запустить снова.

## Что такое константа

Константа — это имя для значения, которое компилятор вычисляет при сборке и
подставляет в каждое место, где имя написано: `const CmPerInch = 2.54`
обозначает число 2.54, `const Material = "фанера"` — строку.

Переменная из урока 2.1 — это место, куда программа кладёт значение во время
работы. Константа таким местом не является, и присваивать ей нечего. Прежде
чем читать дальше, решите, соберётся ли программа, которая объявляет константу
`K` и тут же пишет в неё двойку.

```go
@broken assign-to-const
```

Не соберётся:
`cannot assign to K (neither addressable nor a map index expression)`.
Слева от знака присваивания обязано стоять место, куда можно записать
значение, — переменная.

Значение константы задаёт **константное выражение**: запись из того списка,
который язык разрешает вычислять при сборке. Вызова обычной функции в этом
списке нет. Прежде чем читать дальше, решите, соберётся ли объявление
константы, справа от которого стоит вызов функции, возвращающей литерал.

```go
@broken call-not-constant
```

Компилятор отвечает `factor() (value of type int) is not constant`. Дело не в
сообразительности компилятора: тело `factor` — один `return 1`, и значение
видно любому читателю. Вызов обычной функции просто не входит в список
константных записей. Отметить неизменяемым значение, посчитанное во время
работы, в Go нечем: для таких величин остаются переменные.

## Как объявляют константы

**Одиночное объявление без типа:** `const Material = "фанера"`.

**Одиночное объявление с типом:** `const MaxLengthMm int32 = 2000`. Тип стоит
между именем и знаком равенства, как в `var`.

**Группа в скобках.** После `const` открывают скобку и пишут по одному имени на
строку. Пока в каждой строке написаны и имя, и значение, группа означает ровно
то же, что те же объявления по отдельности. Другие возможности группы, где это
равенство не выполняется, разбирает урок 2.12.

Правила имён те же, что у переменных и функций.

- Имя вне функций видно всему пакету; имя внутри функции — до конца своего
  блока (урок 2.3).
- Имя на уровне пакета с заглавной первой буквы доступно другим пакетам, как
  экспортируемые функции из урока 1.7; со строчной — только своему пакету.
- Заглавные буквы и подчёркивания вроде `MAX_LENGTH` компилятор не требует и не
  различает. Многословные имена пишут слитно с заглавных: `MaxLengthMm`.

Программа ниже объявляет константы всеми тремя формами и для каждой печатает
`%T`. Нужна оговорка: если тип не написан, а справа стоит литерал или
арифметика над литералами, своего типа у константы нет — он выбирается там, где
её используют. В аргументе `fmt.Printf` тип не назван, поэтому берётся **тип по
умолчанию**, а его задаёт вид записи; подробно — в разделе «Тип по умолчанию».

Прежде чем смотреть вывод, предскажите, какое имя типа напечатает `%T` для
каждой из шести констант. У `MaxLengthMm` тип написан, у остальных работает
правило вида записи.

```go

### Example: `01-forms`

Источник: `examples/01-forms/`

```go
// Три формы объявления константы и то, что печатает %T для каждого имени.
package main

import "fmt"

// Одиночное объявление без типа.
const Material = "фанера"

// Одиночное объявление с явно написанным типом.
const MaxLengthMm int32 = 2000

// Группа: одно имя на строку.
const (
	Thickness = 1.5
	debug     = true
	Step      = 10
)

func main() {
	// Константа, видимая только внутри этой функции.
	const local = 5

	fmt.Printf("Material: %v, тип %T\n", Material, Material)
	fmt.Printf("MaxLengthMm: %v, тип %T\n", MaxLengthMm, MaxLengthMm)
	fmt.Printf("Thickness: %v, тип %T\n", Thickness, Thickness)
	fmt.Printf("debug: %v, тип %T\n", debug, debug)
	fmt.Printf("Step: %v, тип %T\n", Step, Step)
	fmt.Printf("local: %v, тип %T\n", local, local)
	fmt.Printf("Step + local: %v, тип %T\n", Step+local, Step+local)
}

```
```

Для `MaxLengthMm` `%T` напечатал написанный `int32`, для остальных — тип по
умолчанию, который задаёт вид записи; сами константы типа не приобрели.
Последняя строка добавляет ещё одно: сумма двух целых констант — снова
константа целого вида.

## Что может стоять справа от знака равенства

Константное выражение состоит только из константных операндов и вычисляется при
сборке: литералы, имена других констант, арифметика из урока 2.10, сравнения из
урока 2.6 и преобразования `T(x)` из урока 2.9.

Обычный вызов функции константным операндом не является — это вы уже видели. Но
правило «вызовов в константе не бывает» было бы неверным: спецификация языка
перечисляет закрытый список встроенных функций, результат которых на константных
аргументах остаётся константой. В этом уроке нужны два пункта.

- `len(s)` — константа, если `s` **строковая константа**. Длина в байтах, как в
  уроке 2.7.
- `min` и `max` из урока 2.10 — константа, если **все** аргументы константные.
  Тип результата такой же, каким был бы тип суммы тех же аргументов.

Прежде чем смотреть вывод, посчитайте длину строки `"фанера"` в байтах по
правилу урока 2.8 и предскажите `min(3, 7)` и `max(3, 7)` — это первые три
строки. Четвёртую предсказывать не нужно, а для пятой назовите тип, который
`%T` напечатает для `min(2.5, 1)`.

```go

### Example: `02-builtin-const`

Источник: `examples/02-builtin-const/`

```go
// Встроенные вызовы, которые на константных аргументах дают константу.
package main

import "fmt"

const Material = "фанера"

const MaterialLen = len(Material)

const MinStep = min(3, 7)

const MaxStep = max(3, 7)

const MaxStepTyped int32 = max(3, 7)

const MixedMin = min(2.5, 1)

func main() {
	fmt.Printf("MaterialLen: %v, тип %T\n", MaterialLen, MaterialLen)
	fmt.Printf("MinStep: %v, тип %T\n", MinStep, MinStep)
	fmt.Printf("MaxStep: %v, тип %T\n", MaxStep, MaxStep)
	fmt.Printf("MaxStepTyped: %v, тип %T\n", MaxStepTyped, MaxStepTyped)
	fmt.Printf("MixedMin: %v, тип %T\n", MixedMin, MixedMin)

	step := 3
	fmt.Println("min(step, 7) при step := 3:", min(step, 7))
}

```
```

Первые три значения ожидаемы. Четвёртая строка — тот же `max`, но записанный в
константу с написанным типом `int32`: результат `max` от нетипизированных
аргументов сам остаётся нетипизированным, поэтому подстроился под `int32`.

Пятая строка показывает правило урока 2.10 на константах: целая константа рядом
с дробной даёт дробную, а в этом вызове один аргумент дробный. Наименьшее из
двух чисел — единица, и **значение** у неё целое; дробным стал **вид**
константы, а по виду для аргумента `fmt.Printf` был выбран `float64` — его `%T`
и назвал. Вид, значение и тип — три разные вещи, и в этой строке они разошлись.

Последняя строка — та же запись `min`, но с переменной: она законна и считается
во время работы, а константой её результат не будет. Прежде чем читать дальше,
решите, что скажет компилятор на попытку объявить через неё константу.

```go
@broken min-with-variable
```

Ответ — `min(a, 7) (value of type int) is not constant`. Так же устроено и
`len`. Прежде чем читать дальше, решите, какое из двух уже встреченных
сообщений появится для `len` от строковой переменной.

```go
@broken len-of-variable
```

То же по смыслу: `len(s) (value of type int) is not constant`. Одна и та же
запись вызова попадает в обе категории — всё решают аргументы.

У `len` есть особенность: даже от строковой константы результат — константа с
уже выбранным типом `int`. Прежде чем читать дальше, решите, соберётся ли
объявление `const shortLen int8 = len("abc")`, если тройка в `int8` помещается.

```go
@broken len-typed-int
```

Не соберётся:
`cannot use len("abc") (constant 3 of type int) as int8 value in constant declaration`.
Про диапазон здесь нет ни слова: отказ вызван типом, у `len("abc")` он уже
выбран и равен `int`. Сравните с четвёртой строкой примера выше, где `max(3, 7)`
подставился в `int32` без возражений.

## Типизированные и нетипизированные константы

**Типизированная константа** — та, у которой тип уже выбран. Написать его в
объявлении — самый заметный способ, но не единственный:

- `const MaxLengthMm int32 = 2000` — тип написан;
- `const gauge = int32(5)` — тип пришёл от преобразования `T(x)`;
- `const shortLen = len("abc")` — тип пришёл от выражения, у которого он уже был.

Тип такой константы выбран раз и навсегда, и в действиях она ведёт себя как
значение этого типа: правило урока 2.4 про одинаковые типы операндов действует
и на неё. Прежде чем читать дальше, решите, соберётся ли сумма переменной типа
`int` и константы типа `int32`.

```go
@broken typed-const-mismatch
```

Не соберётся: `invalid operation: n + k (mismatched types int and int32)`.
Такое же по форме сообщение урок 2.9 показывал для двух переменных разных
типов: как только у константы есть тип, она перестаёт подстраиваться.

**Нетипизированная константа** — та, у которой типа ещё нет: он не написан и не
пришёл ни от преобразования, ни от выражения, у которого уже был. Так выглядят
`const Step = 10`, `const Half = 1.0 / 2`, `const MaxStep = max(3, 7)`. Такая
константа ведёт себя как литерал из урока 2.1 — подстраивается под место, куда
попадает: в `var length float64 = Step` она станет `float64`, в
`var small int8 = Step` — `int8`. Условие одно: значение должно быть
**представимо** в этом типе, то есть входить в набор его значений.

Подстраивание происходит при сборке и там же заканчивается.
«Нетипизированная» не значит «тип определяется во время работы»: у переменной,
получившей значение константы, тип самый обычный и единственный. Подстраиваться
так умеют только константы — ни переменные, ни результаты обычных вызовов этого
не могут.

Прежде чем смотреть вывод, назовите тип каждой из четырёх переменных. В двух
объявлениях тип написан, в двух других работает правило урока 2.1.

```go

### Example: `03-context-type`

Источник: `examples/03-context-type/`

import "fmt"

const stepCount = 42

func main() {

	b := stepCount
	var c float64 = stepCount

	fmt.Printf("b := stepCount: %v, тип %T\n", b, b)
	fmt.Printf("var c float64 = stepCount: %v, тип %T\n", c, c)
	fmt.Printf("var d int8 = stepCount: %v, тип %T\n", d, d)
}

```
```

Одно и то же имя `stepCount` дало значения трёх разных типов — и само осталось

## Тип по умолчанию

Иногда нетипизированной константе подстраиваться не подо что: в `var a = Step` и
`b := Step` тип переменной не написан, а аргумент `fmt.Printf` принимает значение
любого типа. В таком месте компилятор берёт **тип по умолчанию** — тот, что
задан видом константы:

| Вид константы | Тип по умолчанию |
| --- | --- |
| логическая | `bool` |
| целая | `int` |
| дробная | `float64` |
| строковая | `string` |
| руническая | `rune`, то есть `int32` (урок 2.8) |

Это тот же список, по которому урок 2.1 предсказывал типы переменных,
объявленных без типа. Теперь видно, откуда он берётся: тип выбирается не для
переменной, а для константы, попавшей в место без подсказки. Литерал ведёт себя
так же — он и есть нетипизированная константа.

Прежде чем смотреть вывод, предскажите все пять строк. Особое внимание —
третьей: константа записана как `2.0`.

```go

### Example: `05-default-type`

Источник: `examples/05-default-type/`

```go
// Тип по умолчанию: его выбирают там, где подсказки о типе нет.
package main

import "fmt"

const stepCount = 42

const stepSize = 1.5

const wholeStep = 2.0

const label = "шаг"

const ready = true

func main() {
	fmt.Printf("stepCount: %v, тип %T\n", stepCount, stepCount)
	fmt.Printf("stepSize: %v, тип %T\n", stepSize, stepSize)
	fmt.Printf("wholeStep: %v, тип %T\n", wholeStep, wholeStep)
	fmt.Printf("label: %v, тип %T\n", label, label)
	fmt.Printf("ready: %v, тип %T\n", ready, ready)
}

```
```

Запись `2.0` — дробная константа со значением два: печатается она как `2`, а тип
по умолчанию у неё `float64`, ровно как в уроке 2.1.

Чего `%T` **не** доказывает: что константа «была» значением названного типа. Он
называет тип, выбранный для того значения, которое получил именно этот вызов. В
разделе про нетипизированные константы та же `stepCount` в объявлении
`var d int8 = stepCount` получила `int8` — противоречия нет: в том объявлении
подсказка о типе есть, а в аргументе вызова печати её нет.

## Точные вычисления и границы типа

Константное выражение вычисляется точно, и промежуточные значения могут
требовать куда большей точности, чем даёт любой тип языка. Неограниченной
точности при этом не обещает реализация. Значащие цифры дробного числа хранятся
отдельно от порядка; эту часть называют мантиссой, а их количество урок 2.5
называл точностью. Спецификация требует от реализации не меньше 256 бит для
целых констант и такой же мантиссы для дробных. Целую константу, которую не
удалось представить точно, реализация обязана отвергнуть с ошибкой. Дробную она
округляет до ближайшей представимой, когда не хватает точности, и отвергает,
когда число слишком велико.

Итог выражения — другое дело. Как только константа попадает в переменную, в
типизированную константу или в преобразование, начинает действовать тип
назначения, и значение обязано быть в нём представимо.

Прежде чем смотреть вывод, посчитайте две константы по правилам сдвига и деления
из урока 2.10, считая, что промежуточные значения не переполняются. Обратите
внимание на первую: значение `1 << 62`, умноженное на четыре, в `int64` не
поместилось бы. Первая строка печатает `big` через преобразование `int64(...)`
из урока 2.9: без него константа взяла бы тип по умолчанию `int`, а его
разрядность зависит от платформы.

```go

### Example: `06-exact`

Источник: `examples/06-exact/`

```go
// Промежуточное значение константного выражения не ограничено машинным словом.
package main

import "fmt"

const big = (1 << 62) * 4 / 8

const shiftRoundTrip = (1 << 100) >> 90

func main() {
	var stored int64 = big

	fmt.Printf("big: %v, тип %T\n", int64(big), int64(big))
	fmt.Printf("shiftRoundTrip: %v, тип %T\n", shiftRoundTrip, shiftRoundTrip)
	fmt.Printf("stored: %v, тип %T\n", stored, stored)
}

```
```

Оба значения посчитаны точно, хотя промежуточный результат первого выражения
больше любого целого типа Go. В переменную `int64` итог уложился. А если не
уложится? Прежде чем читать дальше, решите, что произойдёт с той же константой
`big` при попытке положить её в переменную типа `int32`.

```go
@broken const-to-int32
```

Компилятор отвечает:
`cannot use big (untyped int constant 2305843009213693952) as int32 value in variable declaration (overflows)`
— и показывает уже посчитанное значение. Точность вычислений и границы типа не
спорят друг с другом: сначала выражение считается точно, потом результат
проверяют там, где он получает тип.

## Округление константы и округление переменной

Урок 2.5 показал два опыта, которые выглядели противоречиво: сумма двух
переменных `float64` не совпала с третьей, а такая же сумма двух литералов —
совпала. Правило состоит из двух половин.

1. Пока выражение состоит из нетипизированных констант, компилятор считает его
   точно — с тем запасом точности, о котором сказано выше.
2. Округление происходит там, где значение получает дробный тип: при записи в
   переменную `float64`, в преобразовании `float64(...)`, в объявлении константы
   с написанным дробным типом. И дальше — при каждом действии над значениями
   этого типа: сумма двух `float64` сама округляется до `float64`, это урок 2.5.

Сколько таких мест, столько раз округление и случится. Первая программа
складывает **переменные**. Прежде чем смотреть вывод, назовите по этому правилу
все места, где происходит округление.

```go

### Example: `07-vars-rounding`

Источник: `examples/07-vars-rounding/`

```go
// Опыт урока 2.5: сумма двух переменных и сравнение с третьей.
package main

import "fmt"

func main() {
	var a float64 = 0.1
	var b float64 = 0.2
	var c float64 = 0.3

	fmt.Println("a + b:", a+b)
	fmt.Println("c:", c)
	fmt.Println("a + b == c:", a+b == c)
	fmt.Printf("подробно: a=%.17g b=%.17g c=%.17g a+b=%.17g\n", a, b, c, a+b)
}

```
```

Округлений здесь четыре: при записи 0.1 в `a`, 0.2 в `b`, 0.3 в `c` и при
сложении уже округлённых `a` и `b`. Сложение — это четвёртое округление, и
получилось из него не то число, которое дала запись литерала 0.3 в `c`. Поэтому
сравнение вернуло `false`, а строка с `%.17g` показывает, в каких цифрах эти два
числа разошлись.

Вторая программа складывает **литералы**. Прежде чем смотреть вывод,
предскажите ответ каждого из трёх сравнений.

```go

### Example: `08-const-exact`

Источник: `examples/08-const-exact/`

```go
// Опыт урока 2.5: точные дроби и выражения из одних литералов.
package main

import "fmt"

func main() {
	var x float64 = 0.5
	var y float64 = 0.25
	var z float64 = 0.75
	fmt.Println("переменные 0.5 + 0.25 == 0.75:", x+y == z)

	fmt.Println("литералы 0.1 + 0.2 == 0.3:", 0.1+0.2 == 0.3)

	s := 0.1 + 0.2
	fmt.Println("s := 0.1 + 0.2, затем s == 0.3:", s == 0.3)
}

```
```

Во второй строке обе части сравнения — константы, и компилятор посчитал их
точно: 0.1 + 0.2 даёт ровно 0.3. В третьей округлений два: точная сумма
округлилась при записи в переменную `s`, а константа 0.3 справа от `==` рядом с
переменной `float64` тоже стала `float64` и тоже округлилась. Оба округления
начались с одного и того же точного числа 0.3, поэтому дали равные результаты.

Чего правило не утверждает: что вычисление с переменными и константное выражение
всегда дают разные ответы. В первой строке этой программы переменные `float64`
со значениями 0.5, 0.25 и 0.75 сравнились так же, как сравнились бы литералы:
такие числа хранятся в `float64` точно, и округлять нечего.

## Представимость на практике

Число **представимо** в типе `T`, если оно входит в набор значений этого типа.
Для целого типа это два условия сразу: число целое и лежит в диапазоне типа. Для
дробного условие мягче — число округляется до точности типа, лишь бы не вышло за
его край. Отсюда три случая, которые легко перепутать.

**Константа вне диапазона — отказ сборки.** Урок 2.4 показывал его на
`var level int8 = 128`. Прежде чем читать дальше, решите, что изменится, если
такое же значение записать не в переменную, а в объявление типизированной
константы.

```go
@broken const-overflow-decl
```

Сообщение:
`cannot use 200 (untyped int constant) as int8 value in constant declaration (overflows)`.
Слова `in constant declaration` отличают этот случай от объявления переменной,
но причина одна.

**Преобразование константы — тоже отказ сборки.** Урок 2.9 показывал его на
`int8(300)`. Прежде чем читать дальше, решите, будет ли сообщение тем же самым,
что в предыдущем случае, или другим.

```go
@broken const-conv-overflow
```

Ответ — `constant 300 overflows int8`. Сообщение короче: слов про объявление
здесь нет, потому что отвергнуто само преобразование.

**Преобразование переменной — обычное действие во время работы.** Прежде чем
смотреть вывод, предскажите все четыре строки по правилам урока 2.9.

```go

## Деление константы и тип операндов

Деление констант подчиняется правилам урока 2.10: если оба операнда — целые
константы, то и деление целое, с отбрасыванием дроби. Слово «точно» из
предыдущего раздела этого не отменяет. Дробь получают, записав хотя бы один
операнд дробным: не `3 / 2`, а `3.0 / 2`. Написанный тип константы вида деления
не меняет — он применяется уже к готовому результату.

Прежде чем смотреть вывод, предскажите все четыре строки. Особое внимание —
последней: тип `float64` написан, но справа стоит деление двух целых.

## Имя для множителя

В задаче про мастерскую дюйм по определению равен ровно 2.54
сантиметра — это соглашение о единицах, а не измерение, поэтому число можно
записать точно: `const CmPerInch = 2.54`. Что даёт имя:

- множитель записан в одном месте и исправляется в одном месте;
- в расчёте видно, что именно умножается, а не просто «на 2.54»;
- компилятор подставит одно и то же число во все места, где имя написано.

Чего имя **не** даёт. Оно не проверяет единицы измерения: запись
`CmPerInch * grams` соберётся, хотя сантиметры на граммы не умножают. Компилятор
видит число, а не «сантиметр на дюйм»: своего типа у этой константы нет, а
написать ей можно только числовой тип — `float64` или `float32`, тоже не единицу
измерения. За смыслом величин следит человек. Имя не говорит и о происхождении
числа: если множитель взят из измерения или из стандарта, это пишут в
комментарии рядом.

Тип множителю лучше не писать: нетипизированная константа подойдёт и там, где
считают в `float64`, и там, где считают в `float32`. Прежде чем смотреть вывод,
предскажите первые две строки — длину в сантиметрах для двух дюймов и для
половины дюйма.

```go

### Example: `11-factor`

Источник: `examples/11-factor/`

```go

отменяет подстраивание.

Мастерская получает чертежи в дюймах, а станок принимает размеры в

- `func WholeMillimeters(inches float64) int` — в файле
  `wholemillimeters.go`.

Тела функций — заглушки: каждая возвращает 0. Допишите тела так, чтобы каждая

Кроме того, в `constants.go` объявите **свою именованную константу** для числа

нужны, снаружи вызывают только три функции. Комментарии `// TODO` можно
удалить.

Не меняйте `go.mod`, строку `package workshop`, имена функций, списки
параметров и типы результатов: скрытые тесты вызывают функции именно в таком
виде. Функции только возвращают значения, печатать ничего не нужно. Импорты не
нужны: для каждого тела достаточно одного выражения после `return` из

Допустимые значения для всех трёх функций: `inches` — конечное число от 0 до
999 включительно. Другие значения вызывающий код не передаёт, и тесты их не

## Что проверяется, а что нет

Скрытые тесты вызывают ваши функции и сравнивают возвращённые значения с
ожидаемыми:

- `TestCentimeters` — `Centimeters` на нуле, на целом дюйме, на половине, на
  одной восьмой, на длине с дробной частью, на 645 дюймах и на верхнем крае
  области;
- `TestMillimeters` — `Millimeters` на тех же входах;
- `TestWholeMillimeters` — `WholeMillimeters` на тех же входах, среди которых
  есть и длины с дробной частью миллиметра, и длина, попадающая почти точно на
  целое число миллиметров.

Результаты `Centimeters` и `Millimeters` тесты принимают, если это конечное
число, которое отличается от ожидаемого не больше чем на 0.001 — сантиметра у
первой функции и миллиметра у второй. NaN и бесконечность отвергаются. Точного
совпадения до последней цифры эти две функции не требуют: расхождение между
равносильными записями намного меньше допуска.

С `WholeMillimeters` иначе. Её результат — целое число, и тест сравнивает его
точно, поэтому порядок действий здесь входит в условие задачи. Считайте так,
как сказано в разделе «WholeMillimeters»: сначала сантиметры, потом
миллиметры, потом отбрасывание дроби. Любая запись, выполняющая ровно этот
порядок, проходит тест.

Чего тест не видит: **текста вашего решения**. Он получает только
возвращённое число. Именованная константа и то же число, написанное прямо в
выражении, дают результат, который тест не отличит: у `Centimeters` и
`Millimeters` расхождение укладывается в допуск, а у `WholeMillimeters` при
объявленном порядке расчёта его нет вовсе. Требование про именованную
константу проверяется чтением кода, а не запуском.

Ответ проверки бывает двух видов. Если код не собрался, тесты не запускаются,
и проверка показывает сообщение сборки с местом в файле. Если код собрался, но
функция вернула не то, проверка печатает строку `--- FAIL:` с именем теста и
сообщение: какой аргумент передан, что функция вернула и что должна была
вернуть.

Прежде чем писать тела, ответьте себе на три вопроса. Зачем числу 10 имя,
если написать его в выражении короче? Почему константе `cmPerInch` не написан
тип? И что изменится в `WholeMillimeters`, если перевод в миллиметры
записать как деление целых? Сверьте ответы с разбором после попытки, раздел
«Зачем множителю имя».

## Centimeters

`Centimeters` возвращает длину в сантиметрах для длины `inches` в дюймах.
Дробная часть обязана сохраниться.

- `Centimeters(1)` возвращает 2.54;
- `Centimeters(0.5)` возвращает 1.27;
- `Centimeters(0)` возвращает 0.

## Millimeters

`Millimeters` возвращает ту же длину в миллиметрах: сначала дюймы переводятся
в сантиметры, потом сантиметры в миллиметры. В одном сантиметре десять
миллиметров; именно это число и нужно объявить именованной константой в
`constants.go`.

- `Millimeters(1)` возвращает 25.4;
- `Millimeters(0.5)` возвращает 12.7;
- `Millimeters(0.125)` возвращает 3.175.

## WholeMillimeters

Старое табло станка показывает только целое число миллиметров: дробная часть
отбрасывается к нулю, а не округляется. Для 0.5 дюйма это 12.7 миллиметра, и
на табло появится 12, а не 13. `WholeMillimeters` возвращает число, которое
покажет табло.

Порядок расчёта задан условием: сначала перевести дюймы в сантиметры, потом
сантиметры в миллиметры, и только после этого отбросить дробную часть
преобразованием в `int`. Порядок указан не для красоты. Каждое умножение
`float64` округляет результат к ближайшему хранимому значению, и на длинах,
где миллиметры попадают почти точно на целое, два разных порядка дают разные
числа. Пример из проверяемых входов: 645 дюймов — это ровно 16383 миллиметра
на бумаге, но если сначала перемножить множители в одно число 25.4, а потом
умножить на 645, хранимый результат окажется чуть меньше 16383, и отбрасывание
дроби даст 16382.

- `WholeMillimeters(1)` возвращает 25;
- `WholeMillimeters(0.5)` возвращает 12;
- `WholeMillimeters(3.3)` возвращает 83;
- `WholeMillimeters(645)` возвращает 16383.

## Зачем множителю имя

<!-- review:named-factor -->

Вопросы из постановки: зачем числу 10 имя, почему у `cmPerInch` не написан тип
и что изменится, если перевод в миллиметры записать делением целых. Образец
ответа ниже.

Имя даёт три вещи. Во-первых, число записано в одном месте: если завтра
понадобится проверить или исправить множитель, менять придётся одну строку, а
не все выражения, где стоит 10. Во-вторых, в расчёте видно, что происходит:
`inches * cmPerInch * mmPerCm` читается как цепочка единиц, а
`inches * 2.54 * 10` — как два числа без объяснения. В-третьих, компилятор
подставит одно и то же значение везде, где написано имя, так что разойтись
копии не могут.

Чего имя не даёт: оно не следит за единицами. Выражение `cmPerInch * mmPerCm`
соберётся, и `cmPerInch * inches * inches` тоже соберётся, хотя вторая запись
бессмысленна. Компилятор видит число, а не «сантиметр на дюйм»: единицы
остаются на совести человека. Это же относится и к происхождению числа: 2.54
здесь точно, потому что дюйм по определению равен ровно 2.54 сантиметра, и эта
оговорка написана в комментарии рядом с константой.

Тип константе не написан намеренно, а справа от знака равенства стоит литерал
`2.54` — поэтому своего типа у неё нет. Нетипизированная константа получает
тип в том месте, куда попадает: в расчёте с `float64` она становится
`float64`, а в расчёте с `float32` — `float32`. (Отсутствие написанного типа
само по себе этого не гарантирует: у `const shortLen = len("abc")` типа тоже
не написано, но он уже выбран выражением и равен `int`.)
Если написать `const cmPerInch float32 = 2.54`, тип будет выбран сразу и
навсегда, и умножение на переменную `float64` перестанет собираться, как в
примере с сообщением `mismatched types float64 and float32`.

Про деление целых: запись вида `1 / 10` в константном выражении — это деление
двух целых констант, и она даёт ноль, а не одну десятую. Дробным операнд
делает его запись: `1.0 / 10`. Поэтому переход от сантиметров к миллиметрам
здесь записан умножением на 10, где путать нечего.

## Что говорят и чего не говорят тесты

<!-- review:tests-observe -->

Скрытые тесты вызвали ваши функции на семи входах каждая и сравнили
возвращённые числа. Это значит: на этих входах результат принят. Ни одного
слова о том, как решение написано, тест не сказал и сказать не мог.

В частности, `TestMillimeters` не различает три решения: с двумя именованными
константами, с одной именованной и числом 10 в выражении и с числом 25.4,
написанным прямо в коде. Результаты этих записей различаются в последних
цифрах, но намного меньше допуска, поэтому тест принимает все три.
Требование про именованную константу — это требование к тексту программы, и
проверяется оно чтением кода: своего, соседского или на код-ревью.

У `WholeMillimeters` граница другая, и её стоит увидеть отдельно. Там сравнение
точное, а объявленный порядок умножений — часть условия задачи, а не деталь
записи: на входе 645 порядок меняет ответ на единицу. Тест и здесь не читает
текста решения — он ловит разницу в числе, которая из этого текста получилась.

Обратное тоже верно: успешный тест не доказывает, что функция верна на всех
входах. Он доказывает её верность на семи проверенных. Поэтому область
допустимых значений объявлена в постановке, а не выведена из тестов.

## Округлённый множитель

<!-- review:cm-rounded-factor -->

Решение `return inches * 2.5` округляет множитель до 2.5. Для грубой прикидки
этого хватило бы, но дюйм равен ровно 2.54 сантиметра, и разница видна уже на
одном дюйме.

Ловит это `TestCentimeters` на входе `Centimeters(1)`: тест ждёт 2.54 ± 0.001,
а получает 2.5. Верное тело — `return inches * cmPerInch`: константа уже
объявлена с точным значением.

## Забытый переход к миллиметрам

<!-- review:mm-missing-factor -->

Решение `return inches * cmPerInch` верно переводит дюймы в сантиметры, но
функция обязана вернуть миллиметры. Перевод остановился на первом шаге.

Ловит это `TestMillimeters` на входе `Millimeters(1)`: тест ждёт 25.4 ± 0.001,
а получает 2.54 — ровно в десять раз меньше. Нужен второй множитель:
`return inches * cmPerInch * mmPerCm`.

## Округление вместо отбрасывания

<!-- review:whole-rounds -->

Решение `return int(math.Round(inches * cmPerInch * mmPerCm))` возвращает
ближайшее целое число миллиметров. Для 0.5 дюйма это 12.7 миллиметра, и
округление даёт 13, а постановка требует целую часть — 12.

Ловит это `TestWholeMillimeters` на входе 0.5. Преобразование в `int` само
отбрасывает дробную часть к нулю, поэтому `math.Round` здесь лишний:
`return int(inches * cmPerInch * mmPerCm)`.

## Отбрасывание дроби до умножения

<!-- review:whole-integer-division -->

Решение `return int(inches) * 254 / 10` выглядит как честная целая
арифметика, но теряет дробь дважды, и первая потеря происходит намного раньше,
чем нужно.

Разберите запись по приоритету из урока 2.10: `*` и `/` — один уровень, и
считаются они слева направо, то есть как `(int(inches) * 254) / 10`. Отдельной
константы `254 / 10` здесь нет. Первым выполняется `int(inches)` — и вот это
главная ошибка: дробная часть **дюймов** отброшена ещё до всякого умножения,
от 0.5 дюйма остаётся ноль. Последним идёт деление целых, и оно отбрасывает
остаток от десятых долей миллиметра.

Ловит это `TestWholeMillimeters` на входе 0.5: тест ждёт 12, а получает 0.
Отбрасывать дробь нужно один раз и в самом конце, когда длина уже переведена в
миллиметры.

## NaN вместо числа

<!-- review:nan-result -->

Решение, которое возвращает `math.NaN()` из `Centimeters` и `Millimeters`, на
верный ответ не похоже, но оно показывает, почему тесты проверяют конечность.

Ловят это `TestCentimeters` и `TestMillimeters`: они сначала отвергают NaN и
бесконечности, а потом сравнивают ошибку с допуском. Верные тела — из
разделов выше.

## Вопрос 1

В пакете объявлены функция `func rate() int { return 3 }` и переменная
`var s = "abc"`. Какие объявления констант соберутся?

2. `const b = rate()`
3. `const c = len("abc")`
4. `const d = len(s)`
5. `const e = min(4, 9)`

Варианты ответа:

- A. Только 1: вызов в объявлении константы запрещён любой.
- B. Все пять: компилятор посчитает любое выражение до запуска программы.
- C. 1, 3 и 5: в двух остальных строках есть неконстантный операнд.
- D. 1, 2, 3 и 5: `rate` возвращает целое, значит результат константный.

Прежде чем смотреть ответ, для каждой строки скажите, все ли операнды

константу.

**Правильный ответ: C.**

Константное выражение состоит только из константных операндов. `len` от
строковой константы и `min` от константных аргументов входят в закрытый

целиком и поэтому теряет строки 3 и 5. Вариант D смотрит на тип результата вместо

## Вопрос 5

названо, поэтому константа превращается в значение своего типа по умолчанию —
его имя и печатает `%T`. В объявлении с написанным типом условие другое:
значение должно быть представимо, а два в `int8` представимо. Вариант A
принимает наблюдение за свойство самой константы. Вариант D забывает про
целые, строковые и логические константы. Вариант B приписывает подстановке
отбрасывание дроби, которого при представимом значении не происходит.

## Вопрос 6

Объявлено `const big = (1 << 62) * 4 / 8`. Какие утверждения верны?

1. Объявление не соберётся: промежуточное значение больше наибольшего `int64`.
2. `var x int64 = big` соберётся.
3. `var y int32 = big` соберётся.

Варианты ответа:

- A. Верно только 1: переполнение промежуточного значения останавливает
  сборку.
- B. Верны 2 и 3: раз константа посчиталась, она подойдёт любому целому типу.
- C. Верны 1 и 3.
- D. Верно только 2.

Прежде чем смотреть ответ, назовите два разных момента: когда считается
выражение и когда проверяется, помещается ли результат.

**Правильный ответ: D.**

Константное выражение вычисляется точно, и промежуточное значение не
ограничено типами языка, поэтому объявление собирается. Итог помещается в
`int64`, но не в `int32`: на строку 3 компилятор отвечает `cannot use big
(untyped int constant 2305843009213693952) as int32 value in variable
declaration (overflows)`. Вариант A переносит ограничение типа на
промежуточное значение. Вариант B считает успешное вычисление разрешением для
любого типа. Вариант C сочетает обе ошибки.

## Вопрос 7

Две программы раздела «Округление константы и округление переменной»
сравнивали одно и то же по смыслу: сумму 0.1 и 0.2 с числом 0.3. Программа с
переменными `float64` ответила `false`, а сравнение двух литералов во второй
программе — `true`. Какое объяснение верно?

Варианты ответа:

- A. Во второй программе компилятор округлил обе части одинаково, а в первой
  округления не было вовсе.
- B. В первой программе литералы округлились при записи в переменные, и
  сложение округлило результат ещё раз; во второй сложение выполнил
  компилятор точно.
- C. Дело в хранении: переменные лежат в памяти, а константы нет, поэтому
  сравнение переменных `float64` никогда не бывает верным.
- D. Сравнивать `float64` через `==` бессмысленно: такое сравнение всегда
  возвращает `false`.

Прежде чем смотреть ответ, для каждой программы перечислите места, где число
получает тип `float64`, и посчитайте, сколько раз там происходит округление.

**Правильный ответ: B.**

В программе с переменными округлений четыре: три записи литералов в `a`, `b` и
`c` и ещё одно при сложении. Сумма округлённых `a` и `b` — отдельное число, и
с округлённым 0.3 оно не совпало. В сравнении литералов обе части вычислены
точно. Вариант A отменяет округление ровно там, где оно и происходит. Варианты
C и D опровергает первая строка второй программы: там сравниваются переменные
`float64` со значениями 0.5, 0.25 и 0.75, и ответ `true`.

## Вопрос 8

Какие строки соберутся?

1. `const k int8 = 200`
2. `level := 300` и затем `small := int8(level)`
3. `n := int(3.0)`
4. `m := int(2.5)`
5. `var f int = 1.1`

Варианты ответа:

- A. 2 и 3: в остальных строках константа не представима в целевом типе.
- B. 2, 3 и 4: преобразование `int(...)` всегда отбрасывает дробную часть.
- C. 2, 3 и 5: 1.1 лежит между наименьшим и наибольшим `int`, значит
  представимо.
- D. Только 2: в остальных строках стоят константы, а константу преобразовать
  нельзя.

Прежде чем смотреть ответ, для каждой строки сначала скажите, константа или
переменная стоит в скобках, и только потом применяйте правило.

**Правильный ответ: A.**

В строках 1, 3, 4 и 5 стоят константы, и каждая проверяется на
представимость: 200 вне диапазона `int8`, 2.5 и 1.1 не целые, а 3.0
обозначает целое три. В строке 2 в скобках значение переменной, и
преобразование выполняется во время работы. Вариант B применяет к константе
правило переменной. Вариант C проверяет только края диапазона и упускает
второе условие — что число обязано быть целым. Вариант D отменяет
преобразование констант вообще.
