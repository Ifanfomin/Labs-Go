# Сортировка и поиск: sort и slices

## Сортировка на месте: slices.Sort

`slices.Sort(s)` расставляет элементы `s` по возрастанию. Функция лежит в
пакете `slices`, поэтому файлу нужна строка `import "slices"`. Нового slice
она не создаёт: она переставляет значения в тех самых ячейках, на которые
смотрит `s`. Такую сортировку называют сортировкой на месте. Новый порядок
уже лежит в этих ячейках, возвращать функции нечего, и результата у вызова
нет. Поэтому вызов пишут отдельной инструкцией. Урок 4.14 показал: попытка
присвоить результат `slices.Sort` переменной не собирается.

Раз ячейки те же, новый порядок видит и любой другой slice, который делит с
`s` эти ячейки. В программе ниже `top := scores[:2]` взят до сортировки и
смотрит на первые две ячейки `scores`. Прежде чем смотреть вывод, назовите
`scores` и `top` до вызова и после него.

```go

### Example: `01-sort-scores`

Источник: `examples/01-sort-scores/`

```go
// Сортировка на месте: slices.Sort переставляет значения в ячейках scores.
package main

import (
	"fmt"
	"slices"
)

func main() {
	scores := []int{72, 95, 58, 88, 95, 61}
	// top смотрит на ячейки 0 и 1 того же массива, что и scores.
	top := scores[:2]

	fmt.Println("до:", scores, top)
	slices.Sort(scores)
	fmt.Println("после:", scores, top)
}

```
```

`top` сам не менялся, но после сортировки в нём два самых низких балла: он
по-прежнему показывает ячейки 0 и 1, а сортировка записала туда 58 и 61.
Оба балла 95 остались: сортировка переставляет элементы и не убирает
повторы.

## Какие ячейки меняются

`slices.Sort` меняет только ячейки переданного slice — от его первого
элемента до последнего по длине. Остальные ячейки того же массива остаются
прежними. Поэтому для другого slice того же массива возможны три случая:

- он не пересекается с отсортированным — его элементы не меняются;
- он лежит внутри отсортированного — его элементы тоже идут по возрастанию;
- он шире и захватывает отсортированные ячейки вместе с другими — в нём
  поменялись только общие ячейки. Остальные его ячейки сортировка не
  трогала, поэтому по возрастанию целиком он идти не обязан.

В программе ниже `a` — slice из восьми убывающих чисел. `mid`, `wide` и
`tail` взяты от `a`; в комментариях указано, какие индексы `a` покрывает
каждый из них. Сортируется только `mid`. Прежде чем смотреть вывод,
назовите `a`, `wide` и `tail` после вызова и скажите, идёт ли `wide` по
возрастанию.

```go

### Example: `02-sort-part`

Источник: `examples/02-sort-part/`

```go
// slices.Sort меняет только ячейки, на которые смотрит переданный slice.
package main

import (
	"fmt"
	"slices"
)

func main() {
	a := []int{80, 70, 60, 50, 40, 30, 20, 10}
	// mid: ячейки a с индексами 2–5.
	mid := a[2:6]
	// wide: индексы 0–6, то есть ячейки mid и ещё три.
	wide := a[0:7]
	// tail: индексы 6–7, с mid не пересекается.
	tail := a[6:8]

	slices.Sort(mid)

	fmt.Println("mid:", mid)
	fmt.Println("a:", a)
	fmt.Println("wide:", wide)
	fmt.Println("tail:", tail)
}

```
```

Поменялись только ячейки с индексами 2–5: в них теперь 30, 40, 50 и 60.
`tail` покрывает индексы 6 и 7, с `mid` не пересекается, и его элементы
прежние. `wide` включает ячейки `mid` и видит новый порядок в середине, но
80 и 70 в начале и 20 в конце стоят, где стояли. По возрастанию `wide` не
идёт: сортировка упорядочила не его, а только `mid`.

## Числа, строки и одна функция

`slices.Sort` сортирует slice чисел и slice строк одним и тем же вызовом.
Порядок при этом тот же, что у оператора `<` для типа элементов: числа
сравниваются по величине, строки — побайтово, по правилу урока 2.14. В
программе ниже три slice: слова, числа и строки из цифр. Прежде чем
смотреть вывод, расставьте каждый по возрастанию. Где окажется `"Zebra"`
относительно `"apple"`? Где окажется `"100"` среди строк из цифр?

```go

### Example: `03-sort-strings`

Источник: `examples/03-sort-strings/`

```go
// Одна функция slices.Sort для slice разных типов: числа по величине, строки побайтово.
package main

import (
	"fmt"
	"slices"
)

func main() {
	words := []string{"banana", "apple", "Zebra", "cherry", "Apple"}
	nums := []int{10, 9, 100, -5}
	codes := []string{"10", "9", "100"}

	slices.Sort(words)
	slices.Sort(nums)
	slices.Sort(codes)

	fmt.Println("words:", words)
	fmt.Println("nums:", nums)
	fmt.Println("codes:", codes)
}

```
```

`Apple` и `Zebra` стоят раньше `apple`: заглавная латинская буква идёт
раньше строчной. Число 9 стоит раньше 10, потому что оно меньше. А строка
`"9"` оказалась последней: строки сравниваются по первому различающемуся
байту, и у `"9"` первый байт больше, чем у `"10"` и `"100"`. `"10"` идёт
раньше `"100"`, потому что служит её началом.

Почему одна функция принимает и `[]int`, и `[]string`? `slices.Sort` —
функция с параметрами типа. В её объявлении тип slice и тип его элементов
не записаны заранее: на их месте стоят параметры типа. При вызове
`slices.Sort(words)` компилятор видит, что аргумент — `[]string`, и сам
подставляет: slice — `[]string`, элементы — `string`. При вызове
`slices.Sort(nums)` он подставляет `[]int` и `int`. Программист пишет
только имя функции и аргумент, как при вызове любой функции пакета.
Условие одно: значения элементов должны сравниваться оператором `<`, и
числа и строки ему удовлетворяют. Писать такие функции самому научит урок
10.2; здесь они — готовые инструменты.

В чужом коде вам встретятся `sort.Ints(s)` и `sort.Strings(s)` из пакета
`sort`. Это более старые имена той же сортировки по возрастанию: по
документации, начиная с Go 1.22, обе просто вызывают `slices.Sort`.
Результат у них тот же, поэтому в своём коде достаточно `slices.Sort`.

## Равны ли два slice: slices.Equal

Тест сортировки сравнивает полученный slice `got` с ожидаемым `want`.
Записать это как `got != want` нельзя: по уроку 4.7 slice сравнивают
оператором только с `nil`, и сравнение двух slice не собирается. Для этой
задачи есть `slices.Equal(a, b)`. Она возвращает `true`, когда у `a` и `b`
одинаковая длина и элементы попарно равны в одном и том же порядке. Если
длины разные, ответ `false`. nil-slice и пустой slice для неё равны: ни в
одном нет элементов. В тесте проверка выглядит так:
`if !slices.Equal(got, want) { t.Errorf(...) }`.

Не путайте `slices.Equal` со сравнением с `nil`. `s == nil` спрашивает,
равен ли slice нулевому значению своего типа, и отличает nil-slice от
пустого (урок 4.7). `slices.Equal` спрашивает только про элементы.

Прежде чем смотреть вывод, назовите, что напечатает каждая из пяти строк
программы.

```go

### Example: `04-equal`

Источник: `examples/04-equal/`

```go
// slices.Equal сравнивает длину и элементы по порядку; nil и пустой slice для неё равны.
package main

import (
	"fmt"
	"slices"
)

func main() {
	var none []int
	empty := []int{}
	fmt.Println("Equal(none, empty):", slices.Equal(none, empty))
	fmt.Println("none == nil:", none == nil, "empty == nil:", empty == nil)
	fmt.Println("Equal([1 2 3], [3 2 1]):", slices.Equal([]int{1, 2, 3}, []int{3, 2, 1}))
	fmt.Println("Equal([1 2], [1 2 3]):", slices.Equal([]int{1, 2}, []int{1, 2, 3}))

	// Та же проверка, что сделал бы тест: сравнить результат с ожидаемым.
	got := []int{72, 58, 61}
	slices.Sort(got)
	want := []int{58, 61, 72}
	if slices.Equal(got, want) {
		fmt.Println("got совпадает с want:", got)
	} else {
		fmt.Println("got отличается от want:", got, want)
	}
}

```
```

`slices.Equal` сочла nil-slice и пустой slice равными, хотя сравнение с
`nil` их различает. `[1 2 3]` и `[3 2 1]` не равны: элементы те же, но
порядок другой. `[1 2]` и `[1 2 3]` не равны уже по длине. В последней
части программа сортирует `got` и сравнивает его с `want` — так же это
сделал бы тест.

## Есть ли элемент и где он: Contains и Index

Чтобы узнать, есть ли балл 88 в списке, сортировать список не нужно.
`slices.Contains(s, x)` возвращает `true`, если значение `x` есть в `s`.
`slices.Index(s, x)` возвращает индекс первого элемента, равного `x`, или
−1, если такого элемента нет. Индексы начинаются с 0, поэтому −1 не может
быть настоящей позицией и означает «не найдено». Если значение встречается
несколько раз, `Index` отвечает про первое вхождение.

Документация обещает только результат. Текущая реализация получает его
так: просматривает элементы по одному, начиная с первого, и
останавливается на первом совпадении. Если значения нет, она просматривает
все элементы. Порядок элементов для такого поиска не важен.

Прежде чем смотреть вывод, назовите результат каждой из восьми строк
программы.

```go

### Example: `05-contains-index`

Источник: `examples/05-contains-index/`

```go
// slices.Contains и slices.Index: есть ли значение и где его первое вхождение.
package main

import (
	"fmt"
	"slices"
)

func main() {
	s := []int{40, 10, 30, 10, 20}
	fmt.Println("Contains(s, 30):", slices.Contains(s, 30))
	fmt.Println("Index(s, 30):", slices.Index(s, 30))
	fmt.Println("Index(s, 10):", slices.Index(s, 10))
	fmt.Println("Contains(s, 99):", slices.Contains(s, 99))
	fmt.Println("Index(s, 99):", slices.Index(s, 99))

	var none []int
	fmt.Println("Contains(none, 10):", slices.Contains(none, 10))
	fmt.Println("Index(none, 10):", slices.Index(none, 10))

	names := []string{"Go", "Rust", "Zig"}
	fmt.Println(`Contains(names, "go"):`, slices.Contains(names, "go"))
}

```
```

`Index(s, 10)` вернула 1, хотя 10 стоит ещё и под индексом 3: ответ —
первое вхождение. Для nil-slice ответы такие же, какие были бы для
пустого, `false` и −1: элементов нет. Строка `"go"` в `names` не нашлась:
строки сравниваются точно, а `"go"` и `"Go"` — разные строки.

## Двоичный поиск: sort.SearchInts

Пусть баллов сто, они отсортированы по возрастанию, а вопросов «есть ли
балл x» много. `slices.Contains` на каждый вопрос просматривает элементы с
начала, а для отсутствующего балла — все сто. Отсортированный slice
позволяет искать иначе, двоичным поиском.

Двоичный поиск ищет позицию: первую, где элемент не меньше `x`. Ответом
может быть любая позиция от 0 до `len(s)` включительно. Позиция `len(s)`
означает «после последнего элемента»: это ответ, когда все элементы
меньше `x`. Поиск помнит две границы, `i` и `j`: ответ лежит между ними,
включая обе. Сначала `i` равно 0, а `j` равно `len(s)`.

1. Если `i` равно `j`, остановиться: ответ — `i`.
2. Иначе взять середину `m = (i + j) / 2` (целое деление, урок 2.10) и
   сравнить элемент `s[m]` с `x`.
3. Если `s[m]` меньше `x`, то и все элементы левее него меньше `x`: slice
   идёт по возрастанию. Ответ правее `m`, поэтому `i` становится `m + 1`.
4. Иначе ответом может быть сама `m` или позиция левее неё, поэтому `j`
   становится `m`. Вернуться к шагу 1.

Пример: `s` — `[]int{10, 20, 20, 30, 40}`, `x` — 45. Сначала `i` равно 0, а
`j` — 5. Середина 2, `s[2]` равен 20, это меньше 45, и `i` становится 3.
Середина 4, `s[4]` равен 40, тоже меньше 45, и `i` становится 5. Теперь
`i` равно `j`, и ответ — 5, длина slice: 45 больше всех элементов. У
пустого slice обе границы с самого начала равны 0, и ответ сразу 0.

Каждый шаг отбрасывает примерно половину оставшегося участка, поэтому на
длинном slice шагов нужно гораздо меньше, чем элементов. Шаг 3 опирается
на порядок: в неотсортированном slice сравнение с серединой ничего не
говорит о половинах. Документация обещает результат поиска, а не его шаги:
шаги 1–4 описывают текущую реализацию. Их достаточно, чтобы понять, откуда
берётся результат.

В Go двоичный поиск по `[]int` делает `sort.SearchInts(s, x)` из пакета
`sort` (`import "sort"`). Её условие: `s` отсортирован по возрастанию. Её
результат — одно число: наименьший индекс `i`, для которого `s[i] >= x`.
Если все элементы меньше `x`, результат равен `len(s)`. По смыслу это
место, где `x` стоит или куда его пришлось бы вставить, чтобы порядок не
нарушился. Если `x` встречается несколько раз, наименьший такой индекс —
индекс первого из них.

Для строк есть `sort.SearchStrings(s, x)` с тем же условием и тем же смыслом
результата; строки она сравнивает побайтово. В пакете `slices` есть ещё
`slices.BinarySearch`, но она возвращает два значения, а функции с
несколькими результатами разбирает урок 5.2.

## Есть ли значение: проверка после поиска

`sort.SearchInts` не отвечает «есть» или «нет» — она возвращает место. Если
`x` в slice нет, на этом месте стоит больший элемент, а если `x` больше
всех, место равно `len(s)`, и элемента там нет вовсе. Поэтому после поиска
значение проверяют условием `i < len(s) && s[i] == x`.

Порядок частей важен. Если `i` равен `len(s)`, чтение `s[i]` остановило бы
программу паникой (урок 4.1). Но по уроку 2.6 правая часть `&&`
вычисляется, только когда левая истинна, поэтому при `i == len(s)` до
`s[i]` дело не доходит.

Программа ниже ищет в slice из пяти элементов пять значений: значение,
которое есть; значение с повтором; отсутствующее значение между
элементами; значение меньше всех; значение больше всех. Прежде чем
смотреть вывод, найдите для каждого `x` по правилам выше `i` и результат
проверки.

```go

### Example: `06-search-ints`

Источник: `examples/06-search-ints/`

```go
// Двоичный поиск sort.SearchInts и проверка «значение есть» на отсортированном slice.
package main

import (
	"fmt"
	"sort"
)

func main() {
	s := []int{10, 20, 20, 30, 40}
	for _, x := range []int{30, 20, 25, 5, 50} {
		i := sort.SearchInts(s, x)
		// Правая часть && вычисляется, только если i меньше длины.

50 место равно длине, 5: левая часть проверки ложна, и `s[5]` не читался.

## Поиск требует отсортированного slice

Условие `sort.SearchInts` — отсортированный по возрастанию slice —

передать неотсортированный slice, вызов соберётся и вернёт какое-то число,
но какое именно, документация не обещает. Проверка «значение есть» тогда
может ответить «нет» для значения, которое в slice есть. Исправляют не
проверку, а вход: сначала сортируют slice или его копию, если исходный

## Сортировать копию или сам slice

Сортировка на месте переставляет данные того, кто вызвал функцию. Иногда
это нежелательно: например, баллы хранятся в порядке сдачи работ, и этот
порядок нужен в отчёте. Тогда сортируют независимый снимок из урока 4.6:
`make` создаёт slice той же длины с собственным массивом, `copy` переносит
в него значения, и `slices.Sort` вызывают для снимка. Присваивание
`d := s2` снимка не даёт: оно копирует только дескриптор, а ячейки остаются
общими.

Прежде чем смотреть вывод, назовите `s` и `c` после сортировки и после
двух записей, а затем `s2` и `d`.

```go

### Example: `07-copy-then-sort`

Источник: `examples/07-copy-then-sort/`

```go
// Сортировка снимка не трогает исходный slice; присваивание снимка не даёт.
package main

import (
	"fmt"
	"slices"
)

func main() {
	s := []int{30, 10, 20}

	// Снимок из урока 4.6: make нужной длины и copy.
	c := make([]int, len(s))
	copy(c, s)
	slices.Sort(c)
	fmt.Println("s:", s, "c:", c)

	c[0] = 99
	s[1] = 77
	fmt.Println("после записей s:", s, "c:", c)

	// Присваивание копирует дескриптор: ячейки у s2 и d общие.
	s2 := []int{30, 10, 20}
	d := s2
	slices.Sort(d)
	fmt.Println("s2:", s2, "d:", d)
}

```
```

Сортировка снимка `c` не тронула `s`. Запись `c[0] = 99` не видна в `s`, а
запись `s[1] = 77` не видна в `c`: у каждого свой массив. `d` и `s2` делят
ячейки, поэтому `slices.Sort(d)` отсортировала и `s2`.

## Когда сортировать, а когда просто искать

Сортировка стоит работы. Она обязана посмотреть на каждый элемент — иначе
не узнала бы, где ему место, — и переставляет данные или требует копии.
Простой поиск в текущей реализации просматривает элементы по одному, в
худшем случае все, и ничего не переставляет. Отсюда правило выбора:

- искать нужно один раз или несколько раз — достаточно `slices.Contains`
  или `slices.Index`, сортировать не нужно;
- по одним и тем же данным нужно ответить на много вопросов — выгоднее
  один раз отсортировать, копию или сам slice, и отвечать двоичным
  поиском с проверкой присутствия: каждый поиск отбрасывает половину
  участка за шаг.

Результат при этом одинаков: простой поиск и двоичный поиск с проверкой
`i < len(s) && s[i] == x` одинаково правильно отвечают, есть ли значение.
Сам `sort.SearchInts` без проверки возвращает место, а не ответ.
Различаются работа и индексы: после сортировки индекс относится к
отсортированному slice, а не к исходному порядку. Если нужен номер
элемента в исходном порядке, например номер работы в порядке сдачи, его
даёт `slices.Index` по несортированному slice, а `sort.SearchInts` по
отсортированной копии — нет.

## Порядок по убыванию без функции сравнения

`slices.Sort` всегда сортирует по возрастанию. Порядок по убыванию из
отсортированного slice получают средствами, которые у вас уже есть:

1. **Обойти с конца.** Цикл со счётом вниз из урока 3.5,
   `for i := len(s) - 1; i >= 0; i--`, читает элементы от последнего к
   первому. Сам slice при этом не меняется.
2. **Поменять местами концы.** Обмен одной строкой из урока 3.6, только
   для элементов: `s[i], s[j] = s[j], s[i]`. Оба значения справа
   читаются до того, как записывается хотя бы один элемент, — то же
   правило в два шага, что в уроке 3.6 для переменных, поэтому ни одно
   значение не теряется. Сначала меняются первый и последний элементы,
   затем второй и предпоследний, и так до середины. После этого сам slice
   идёт по убыванию.

Прежде чем смотреть вывод, назовите четыре строки программы.

```go

### Example: `08-descending`

Источник: `examples/08-descending/`

```go
// Порядок по убыванию без функции сравнения: обход с конца или обмен концов.
package main

import (
	"fmt"
	"slices"
)

func main() {
	scores := []int{72, 58, 95, 61, 88}
	slices.Sort(scores)
	fmt.Println("по возрастанию:", scores)

	// Способ 1: обойти отсортированный slice с конца; сам slice не меняется.
	fmt.Print("с конца:")
	for i := len(scores) - 1; i >= 0; i-- {
		fmt.Print(" ", scores[i])
	}
	fmt.Println()
	fmt.Println("scores после обхода:", scores)

	// Способ 2: менять местами крайние элементы, двигаясь к середине.
	for i, j := 0, len(scores)-1; i < j; i, j = i+1, j-1 {
		scores[i], scores[j] = scores[j], scores[i]
	}
	fmt.Println("после обмена концов:", scores)
}

```
```

Обход с конца напечатал баллы от высшего к низшему и оставил `scores` по
возрастанию. Обмен концов изменил сам `scores`: обменялись две пары, а
средний элемент 72 остался на месте.

Бывают и другие порядки, например «сначала по числу повторений, затем по
слову». В этом модуле такие порядки строят группировкой: значения
раскладывают по группам в map, сортируют ключи групп и обходят группы в
нужном порядке. Так устроена вторая часть мини-проекта, урок 4.18.
Недоступно пока одно: вызвать `slices.SortFunc` или `sort.Slice`. Этим
функциям нужна функция сравнения, которую программист пишет сам и
передаёт как значение; как это делается, разбирают уроки 5.5–5.6.

## SortedCopy

`SortedCopy` возвращает новый slice с теми же значениями, что у `s`, по
возрастанию; повторы сохраняются. После возврата результат и `s`
независимы: запись в элемент результата не меняет `s`, а запись в элемент
`s` не меняет результат.

- Для `[]int{30, 10, 20}` результат — `[]int{10, 20, 30}`, а `s` остаётся
  `[]int{30, 10, 20}`.
- Для `[]int{5, 1, 5}` результат — `[]int{1, 5, 5}`.
- Для nil-slice и пустого slice результат — slice длины 0; nil-slice
  подходит.

## Median

`Median` возвращает медиану значений `s`: средний элемент, если выстроить
значения по возрастанию. При чётной длине средних элементов два, и
функция возвращает меньший из них.

- Для `[]int{3, 1, 2}` результат — 2.
- Для `[]int{1, 4, 9, 2}` значения по возрастанию — 1, 2, 4, 9; средние —
  2 и 4, результат — 2.
- Для `[]int{7}` результат — 7.
- Для nil-slice и пустого slice результат — 0: так условлено, хотя
  медианы у пустого набора нет.

## Position

`Position` возвращает индекс первого элемента `sorted`, равного `x`, или
−1, если `x` в `sorted` нет. `sorted` отсортирован по возрастанию и может
содержать повторы.

- Для `[]int{10, 20, 20, 30, 40}`: 30 — индекс 3; 20 — индекс 1, первый из
  двух; 25, 5 и 50 — −1.
- Для nil-slice и пустого slice результат — −1 при любом `x`.

## HasDuplicate

`HasDuplicate` возвращает `true`, если хотя бы одно значение встречается в
`s` два раза или больше, и `false` иначе.

- Для `[]int{3, 1, 3}` результат — `true`: тройки стоят не рядом, но
  повтор есть.
- Для `[]int{1, 2, 3}` результат — `false`.
- Для nil-slice, пустого slice и slice из одного элемента результат —
  `false`.

## Как проверить себя

Перед запуском проверки пройдите руками примеры из разделов выше. Можно
написать и собственный тест рядом с заготовкой (урок 1.12). Результат
`SortedCopy` сравнивают через `slices.Equal` — условием, которое вы
записали, отвечая на вопрос 1; файлу теста тогда нужен `import "slices"`
рядом с `"testing"`. Так же через `slices.Equal`
проверяют, что вход после вызова не изменился: сравните его с копией,
сделанной до вызова. Для `Position` полезны значения меньше всех, больше
всех, между элементами и повтор. Проектировать набор на все возможные
реализации не требуется. После попытки сравните рассуждения с разделом
«Разбор после попытки».

**Ступень 1.** Где стоит медиана среди значений, выстроенных по

чётной длине даёт больший из двух средних. Средний элемент самого `s`,

## Position

## HasDuplicate

**Ступень 1.** Где окажутся одинаковые значения, если выстроить значения по

портит вход.

## Независимая копия

<!-- review:sortedcopy-independence -->

Первый вопрос раздела «Что проверяется, а что нет»: что будет, если
`SortedCopy` отсортирует сам `s`. Образец ответа ниже.

`slices.Sort` сортирует на месте, поэтому вызов `slices.Sort(s)`
переставит значения в ячейках вызывающего кода: его slice после вызова
окажется отсортированным, хотя он об этом не просил. Вернуть сам `s` тоже
нельзя: результат и вход будут смотреть на одни ячейки, и запись в один
будет видна в другом. Договор требует обратного: вход прежний, а записи
не видны ни в одну сторону.

Оба условия даёт снимок из урока 4.6. `make([]int, len(s))` создаёт slice
той же длины с собственным массивом, `copy(c, s)` переносит в него
значения, и `slices.Sort(c)` сортирует уже снимок. Решение:
`c := make([]int, len(s))`, `copy(c, s)`, `slices.Sort(c)`, `return c`.
Для nil-slice получится slice длины 0, который не равен `nil`; договор это
разрешает, потому что обещает только длину 0.

Условие собственного теста: `got := SortedCopy([]int{30, 10, 20})`, затем
`if !slices.Equal(got, []int{10, 20, 30}) { t.Errorf(...) }`. Запись
`got != want` не соберётся: slice сравнивают оператором только с `nil`
(урок 4.7). `slices.Equal` проверяет длину и элементы по порядку, поэтому
на неотсортированном результате `[30 10 20]` тест сообщит об ошибке.
nil-slice и пустой slice для неё равны, и для пустого входа годится любой
из них, как и разрешает договор.

## Ход двоичного поиска в Position

<!-- review:position-trace -->

Второй вопрос: что вернут `sort.SearchInts` и `Position` на
`[]int{5, 12, 12, 12, 40}`. Образец ответа ниже.

- Для 12 поиск возвращает 1 — индекс первой из трёх двенадцатых: это
  наименьший индекс, где элемент не меньше 12. Под ним стоит 12, и
  `Position` возвращает 1.
- Для 20 поиск возвращает 4: первый элемент, не меньший 20, — это 40. Под
  индексом 4 стоит 40, а не 20, и `Position` возвращает −1.
- Для 41 все элементы меньше, и поиск возвращает длину, 5. Элемента с
  таким индексом нет, и `Position` возвращает −1.

Часть `i < len(sorted)` нужна для третьего случая: без неё чтение
`sorted[5]` остановило бы программу паникой. Она стоит слева, потому что
`&&` вычисляет правую часть, только когда левая истинна (урок 2.6).
Решение: `i := sort.SearchInts(sorted, x)`, затем
`if i < len(sorted) && sorted[i] == x { return i }` и `return -1`.

`slices.Index(sorted, x)` дала бы те же ответы, и тесты это решение
тоже примут. Двоичный поиск здесь выбран потому, что вход уже
отсортирован, а вопросов к одним и тем же данным обычно много.

## Два способа найти повтор

<!-- review:duplicate-ways -->

Третий вопрос: почему сравнение соседей без сортировки ошибается и чем его
заменить. Образец ответа ниже.

В `[]int{3, 1, 3}` соседние пары — 3 и 1, 1 и 3; одинаковых среди них нет,
хотя тройка встречается дважды. После сортировки одинаковые значения стоят
рядом: `[1 3 3]`, и сравнение соседей находит повтор. Сортировать сам `s`
нельзя: договор запрещает менять вход, поэтому сортируют копию, и её уже
умеет делать `SortedCopy`. Решение: `c := SortedCopy(s)` и цикл
`for i := 1; i < len(c); i++`, который возвращает `true`, если
`c[i] == c[i-1]`; после цикла — `false`.

Второй способ обходится без сортировки: множество `map[int]bool` из урока
4.13. Обходите `s`; если значение уже есть в множестве, верните `true`,
иначе добавьте его. Оба способа верны, и тесты их не различают.

## SortedCopy сортирует сам вход

<!-- review:sortedcopy-in-place -->

Решение вызывает `slices.Sort(s)` и возвращает `s`. Значения в результате
верные, но вход вызывающего кода переставлен, а результат делит с ним

по записи:
`SortedCopy([7]): запись в результат изменила переданный slice, он стал [5000]`.
Исправление — снимок через `make` и `copy`.

## Приёмник длины 0

<!-- review:sortedcopy-empty-receiver -->

Решение создаёт приёмник `make([]int, 0, len(s))`. Ёмкость у него есть,
но длина 0, а `copy` переносит столько элементов, какова меньшая из

Исправление — приёмник длины `len(s)`.

<!-- review:median-upper-middle -->

Решение берёт элемент с индексом `len(c)/2`. При нечётной длине это

<!-- review:median-unsorted -->

Решение берёт средний элемент самого `s`, не выстроив значения по

<!-- review:median-sorts-input -->

Решение вызывает `slices.Sort(s)` и берёт середину. Число верное, но

## Место вместо позиции

<!-- review:position-no-presence-check -->

## Сравнение без проверки длины

<!-- review:position-no-bound-check -->

## Вопрос 3

Одна и та же `slices.Sort` в программе `03-sort-strings` отсортировала
`[]string` и `[]int`: числа по величине, строки побайтово. Как это
возможно?

Варианты ответа:

- A. Она переводит все элементы в строки и сравнивает строки, поэтому тип
  элементов ей безразличен.
- B. Это функция с параметрами типа: тип элементов компилятор берёт из
  аргумента, а сравнивает она оператором `<` этого типа.
- C. Одной функцией можно сортировать slice только одного типа на строку
  программы, и здесь каждый вызов стоит отдельно.
- D. Она принимает элементы любого типа, в том числе `bool`, и
  упорядочивает их по записи в тексте программы.

Прежде чем смотреть ответ, объясните, что пишет в вызове программист и
что делает компилятор.

**Правильный ответ: B.**

Программист пишет только имя и аргумент, а тип элементов (`string` или
`int`) компилятор выводит из аргумента. Сравнение у каждого типа своё,
поэтому 9 раньше 10, а `"10"` раньше `"9"`. Вариант A поставил бы 10
раньше 9. Вариант C придумывает ограничение, которого нет. Вариант D не
учитывает условие: элементы должны сравниваться оператором `<`, а у `bool`
порядка нет (урок 2.6).

- B. false; true false; false; false 1; −1

- D. true; true false; false; false 1; −1

Прежде чем смотреть ответ, заполните таблицу из пяти строк сами и для
каждой назовите правило.

**Правильный ответ: D.**

`slices.Equal` смотрит только на элементы, а их нет ни в одном из двух
slice. Сравнение с `nil` различает nil-slice и пустой литерал. В строке 3
элементы те же, но порядок другой. В строке 4 тройки нет, а первая
четвёрка стоит под индексом 1. В nil-slice ничего нет, и `Index` отвечает
−1. Вариант A переносит равенство из `Equal` на сравнение с `nil`, вариант
B — наоборот. Вариант C не учитывает порядок в `Equal` и даёт 0 — а 0 был
бы настоящим индексом.

## Вопрос 7

Баллы хранятся в порядке сдачи работ: `[]int{72, 95, 58, 88, 61}`.
Функция ищет в них 88 через `sort.SearchInts` с проверкой из вопроса 6.
Что можно сказать об ответе и как исправить программу?

Варианты ответа:

- A. Найдёт 88: `sort.SearchInts`, как `slices.Index`, просматривает все
  элементы по очереди. Исправлять нечего.
- B. Функция заметит, что slice не отсортирован, и вернёт −1. Исправление
  — искать через `slices.Contains`.
- C. Не соберётся: компилятор не пропустит `sort.SearchInts` для slice, о
  котором неизвестно, отсортирован ли он.
- D. Нарушено условие поиска: число не обещано, и проверка может ответить
  «нет». Исправление — отсортировать копию.

Прежде чем смотреть ответ, назовите условие `sort.SearchInts` и того, кто
отвечает за его выполнение.

**Правильный ответ: D.**

Условие выполняет вызывающий код, а функция о нарушении не сообщает: без
порядка сравнение с серединой ничего не говорит о половинах. Копию
сортируют, потому что порядок сдачи ещё нужен. Вариант A описывает простой
поиск. Вариант B приписывает функции проверку, которой нет. Вариант C ждёт
от компилятора знания о данных, которые появятся только во время работы.

## Вопрос 8

Первая программа один раз проверяет, есть ли 100 среди 50 баллов. Вторая
отвечает на 500 вопросов «есть ли балл x» по одним и тем же 100 баллам, а
их исходный порядок нужен для отчёта. Какой способ выбрать для каждой?

Варианты ответа:

- A. Обе — сортировка и `sort.SearchInts`: двоичный поиск быстрее всегда,
  даже вместе с сортировкой.
- B. Обе — `slices.Contains`: сортировка меняет данные, поэтому её здесь не
  применяют.
- C. Первая — `slices.Contains`; вторая — один раз отсортировать копию и
  отвечать `sort.SearchInts` с проверкой.
- D. Первая — сортировка и `sort.SearchInts`; вторая — `slices.Contains`,
  иначе сортировать пришлось бы 500 раз.

Прежде чем смотреть ответ, скажите для каждой программы, сколько раз она
ищет и во что обходится сортировка.

**Правильный ответ: C.**

Верно ответить «есть ли балл» может любой из способов, но двоичный поиск —
только вместе с проверкой `i < len(s) && s[i] == x`: сам `sort.SearchInts`
возвращает место, а не ответ. Вариант C эту проверку называет, варианты A и
D — нет. Различается и работа. Сортировка сама смотрит на каждый элемент,
поэтому ради одного поиска не окупается. Во второй программе одна
сортировка копии обслуживает 500 двоичных поисков, а копия сохраняет
порядок для отчёта. Вариант A сортирует ради единственного поиска.
Вариант B забывает про копию и поэтому 500 раз просматривает баллы с
начала. Вариант D думает, что сортируют перед каждым поиском.

## Вопрос 9

`scores` уже отсортирован по возрастанию. Нужно напечатать баллы от
высшего к низшему, не меняя `scores`. Какой способ доступен уже сейчас и
каким функциям нужна функция сравнения?

Варианты ответа:

- A. Никакой: убывающий порядок даёт только `slices.SortFunc` со своей
  функцией сравнения из уроков 5.5–5.6.
- B. Цикл `for i := len(scores) - 1; i >= 0; i--` с печатью `scores[i]`;
  функция сравнения нужна `slices.SortFunc` и `sort.Slice`.
- C. Ещё раз вызвать `slices.Sort(scores)`: повторная сортировка
  разворачивает порядок отсортированного slice.
- D. Вызвать `sort.Ints(scores)`: старая функция пакета `sort` сортирует
  по убыванию без функции сравнения.

Прежде чем смотреть ответ, запишите заголовок цикла сами и скажите, что он
напечатает для `[58 61 72]`.

**Правильный ответ: B.**

Цикл со счётом вниз (урок 3.5) читает элементы от последнего к первому, и
для `[58 61 72]` печатает 72, 61, 58, не меняя slice. Функцию сравнения
принимают `slices.SortFunc` и `sort.Slice`; её передачу разбирают уроки
5.5–5.6. Вариант A объявляет невозможным обход с конца. Вариант C не
учитывает, что отсортированный slice после повторной сортировки остаётся
прежним. Вариант D путает старое имя с другим порядком: `sort.Ints` тоже
сортирует по возрастанию.
