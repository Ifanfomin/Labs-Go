# nil-срез против пустого

Датчик температуры присылает показания за день, а программа хранит их в
`[]int`. Отчёту нужно первое показание дня, а если показаний нет — запасное
значение, например `-1`. «Показаний нет» в программе выглядит по-разному:

- переменную `var day []int` объявили, но ничего в неё не записали;
- день завели литералом `[]int{}`, а показаний не добавили;
- под показания заранее отвели место: `make([]int, 0, 3)`.

Элементов нет во всех трёх случаях. Но не всякая проверка перед `s[0]`
замечает, что элементов нет: например, проверка `s != nil` пропустит пустой
литерал к `s[0]`, и программа аварийно завершится. В этом уроке вы разберёте,
чем эти slice различаются, какой вопрос задаёт каждая проверка и что функция
должна обещать коду, который её вызывает.

Понадобится уже пройденное: нулевые значения переменных (урок 2.1),
короткое объявление `:=` (урок 2.2), сравнения и `if` (уроки 2.6 и 3.1),
цикл `for` из трёх частей (урок 3.5), допустимые индексы (урок 4.1), длина,
ёмкость и массив, лежащий в основе slice (уроки 4.2–4.4), литералы и
срез-выражения `d[a:b]` (урок 4.3), `make` (урок 4.4), `append` с
присваиванием результата и накопление элементов в `var out []int`
(урок 4.5), `copy` в приёмник нужной длины (урок 4.6).

К концу урока вы сможете:

- для slice из объявления `var`, литерала, `make` или срез-выражения назвать
  длину, ёмкость и то, равен ли он `nil`;
- объяснить, почему slice нельзя сравнить с другим slice, а с `nil` можно,
  и исправить такое сравнение;
- выбрать условие, которое защищает обращение к `s[0]`, и объяснить, почему
  `s != nil` для этого не годится;
- предсказать, как `len`, индексный цикл, `copy`, `append` и `s[:0]` ведут
  себя на nil-slice и на пустом slice;
- прочитать договор функции о пустом результате и назвать проверки, которые
  этот договор разрешает.

## Пустой slice и nil-slice

**Пустой** slice — slice, в котором нет элементов: его длина равна 0, и
условие `len(s) == 0` истинно. Это утверждение о количестве элементов, и
только о нём.

**nil-slice** — нулевое значение типа slice. В уроке 2.1 переменная без
начального значения получала нулевое значение своего типа: `0` для `int`,
`""` для `string`, `false` для `bool`. У типов slice нулевое значение
записывается словом `nil`. Урок 4.5 уже назвал его, когда накапливал
элементы в `var out []int`: до первого `append` такая переменная равна
`nil`. `nil` — не число и не пустая строка, а предобъявленное имя нулевого
значения. Равен ли slice нулевому значению, проверяет сравнение `s == nil`.

Спецификация языка говорит, что длина и ёмкость nil-slice равны 0. Значит,
nil-slice всегда пустой. Обратное неверно: пустой slice не обязан быть nil.
Литерал `[]int{}` и вызов `make([]int, 0)` дают пустые slice, которые с
`nil` не совпадают. У пустого slice может быть и ненулевая ёмкость: у
`make([]int, 0, 3)` длина 0, а ёмкость 3.

Программа ниже создаёт четыре slice: три способа из начала урока и один
непустой. Для каждого она печатает сам slice, его длину, ёмкость и результат
сравнения с `nil`. Прежде чем смотреть вывод, для каждой из четырёх
переменных назовите длину, ёмкость и результат сравнения с `nil`.

```go

### Example: `01-four-slices`

Источник: `examples/01-four-slices/`

```go
package main

import "fmt"

func main() {
	var a []int            // нулевое значение типа []int
	b := []int{}           // литерал без элементов
	c := make([]int, 0, 3) // длина 0, ёмкость 3
	d := []int{4, 7}       // два элемента

	fmt.Println("a:", a, "len", len(a), "cap", cap(a), "nil", a == nil)
	fmt.Println("b:", b, "len", len(b), "cap", cap(b), "nil", b == nil)
	fmt.Println("c:", c, "len", len(c), "cap", cap(c), "nil", c == nil)
	fmt.Println("d:", d, "len", len(d), "cap", cap(d), "nil", d == nil)
}

```
```

Сравнение с `nil` истинно только у `a`: её объявили без значения, и она
осталась нулевым значением своего типа. У `b` и `c` длина тоже 0, но это не
nil. `c` отличается от `b` ещё и ёмкостью: место под три элемента отведено,
а самих элементов нет.

Посмотрите и на сами slice в выводе. `a`, `b` и `c` напечатаны одинаково —
пустыми квадратными скобками. По обычной печати `fmt.Println` не видно, nil
перед вами или нет, и ёмкость тоже не видна. На вопрос «nil ли это»
отвечает сравнение с `nil`, а не печать.

## Пустой кусок другого slice

Пустой slice может дать и срез-выражение (урок 4.3). Длина и ёмкость
считаются как в уроке 4.4: у `d[a:b]` длина `b-a`, ёмкость `cap(d)-a`.
Равен ли результат `nil`, решает правило спецификации:

- срез-выражение от nil-slice даёт nil-slice;
- срез-выражение от slice, который не равен nil, даёт slice, который делит
  с ним массив, лежащий в основе. Такой slice не равен nil, даже если его
  длина и ёмкость равны 0.

В программе ниже `d` содержит два элемента. `e` берёт от `d` кусок после
последнего элемента, `f` — кусок нулевой длины в начале, `g` — кусок от
nil-slice `n`. Последняя строка печатает `f[:1]` — slice длины 1, взятый от
`f` в пределах его ёмкости (урок 4.4). Прежде чем смотреть вывод, назовите
длину, ёмкость и результат сравнения с `nil` для `e`, `f` и `g` и скажите,
что напечатает `f[:1]`.

```go

### Example: `02-empty-views`

Источник: `examples/02-empty-views/`

```go
package main

import "fmt"

func main() {
	d := []int{4, 7}
	e := d[2:] // от конца d до конца d
	f := d[:0] // от начала d, ни одного элемента
	var n []int
	g := n[:0] // срез-выражение от nil-slice

	fmt.Println("e:", e, "len", len(e), "cap", cap(e), "nil", e == nil)
	fmt.Println("f:", f, "len", len(f), "cap", cap(f), "nil", f == nil)
	fmt.Println("g:", g, "len", len(g), "cap", cap(g), "nil", g == nil)
	fmt.Println("f[:1]:", f[:1])
}

```
```

`e` и `f` пустые, но не nil: они получены от `d`, а `d` не nil. `g` получен
от nil-slice и поэтому сам равен `nil`. Ёмкости у пустых кусков разные: `e`
начинается в конце массива, и места за ним нет, а `f` начинается в его
начале, и места хватает на два элемента.

Последняя строка вывода показывает важное следствие. `f` пуст, но массив `d`
ему по-прежнему доступен: взяв `f[:1]` в пределах ёмкости, программа снова
видит первый элемент `d`. Длина 0 не означает, что за slice нет данных. Она
означает только, что по индексу к самому `f` обратиться нельзя.

## Что можно сравнивать

Slice можно сравнить с `nil`: `s == nil` и `s != nil` собираются для slice
любого типа. С другим slice — нельзя, даже если оба пусты или оба равны
`nil`. Урок 4.2 уже показал, что `==` между двумя slice не собирается.
Отсюда частая ошибка: проверять пустоту сравнением с пустым литералом.
Соберётся ли программа ниже?

```go
@broken compare-literal
```

Не соберётся. Компилятор сообщает:
`invalid operation: s == []int{} (slice can only be compared to nil)`,
то есть slice можно сравнить только с `nil`. На вопрос «есть ли элементы»
отвечает длина: `len(s) == 0`. Заменять эту проверку сравнением `s == nil`
нельзя: в первом примере оно ложно для `[]int{}`, хотя элементов там нет.

Второе ограничение касается самого слова `nil`. Этим словом записывают
нулевое значение разных типов: например, тем же словом записывается нулевое
значение `map` (урок 4.11). А короткое объявление `:=` берёт тип новой
переменной из значения справа (урок 2.2). Соберётся ли программа ниже?

```go
@broken untyped-nil
```

Не соберётся: `use of untyped nil in assignment`. Одно слово `nil` не
называет никакого типа — в сообщении оно так и названо: нетипизированное
(untyped). Вывести из него тип переменной компилятор не может, и
спецификация прямо запрещает инициализировать словом `nil` переменную без
явного типа. Поэтому тип записывают в объявлении: `var s []int` — такая
переменная уже равна `nil`. Сравнение `s == nil` спецификация разрешает
отдельным правилом, и тип в нём задаёт переменная `s`.

Здесь речь о slice. Не переносите выводы урока на другие виды
значений без их уроков: `nil` у `map` разбирают уроки 4.11 и 4.12, `nil` у
интерфейсов — урок 8.4.

## Какой вопрос задаёт проверка

Две проверки отвечают на разные вопросы:

- `len(s) == 0` — есть ли в `s` элементы;
- `s == nil` — равен ли `s` нулевому значению своего типа.

Для обращения `s[0]` важен только первый вопрос. По правилу из урока 4.1 индекс
допустим, если он не меньше 0 и меньше длины. Значит, `s[0]` допустим ровно
тогда, когда `len(s) > 0`. Обращение по недопустимому индексу язык не
пропускает: программа аварийно завершается во время выполнения. Ёмкость
на допустимость индекса не влияет: место, отведённое за длиной, в допустимые
индексы не входит.

Функция `firstReading` ниже должна вернуть первое показание или `fallback`,
но перед `s[0]` проверяет `s != nil`. `main` вызывает её с днём, который
завели литералом `[]int{}`. Прежде чем смотреть вывод, скажите: что
`firstReading` вернула бы для nil-slice и что произойдёт при вызове из
`main`?

```go

### Example: `03-nil-guard`

Источник: `examples/03-nil-guard/`

```go
package main

import "fmt"

// firstReading должна вернуть первое показание или fallback,
// но перед s[0] проверяет s != nil, а не длину.
func firstReading(s []int, fallback int) int {
	if s != nil {
		return s[0]
	}
	return fallback
}

func main() {
	day := []int{} // день заведён, показаний нет
	fmt.Println(firstReading(day, -1))
}

```
```

Для nil-slice `firstReading` вернула бы `fallback`: условие `s != nil`
ложно. Но `day` не nil, поэтому проверка пропустила выполнение к `s[0]`, а
длина `day` равна 0. Индекс 0 вне допустимого диапазона, и программа
завершилась аварийно; в её выводе есть строка с
`index out of range [0] with length 0`. Язык гарантирует само аварийное
завершение, а точный текст сообщения — то, что печатает текущая реализация
Go.

Такую ошибку легко пропустить: если проверять функцию только на
`var s []int`, она работает. Проверка `s != nil` не доказывает, что `s[0]`
существует.

Функция `lastReading` ниже возвращает последнее показание, `s[len(s)-1]`.
Этот индекс допустим при том же условии, что и `s[0]`: когда длина больше 0.
Поэтому перед обращением функция проверяет длину. Прежде чем смотреть
вывод, назовите результат каждого из пяти вызовов.

```go

### Example: `04-len-guard`

Источник: `examples/04-len-guard/`

```go
package main

import "fmt"

// lastReading возвращает последнее показание или fallback,
// если показаний нет.
func lastReading(s []int, fallback int) int {
	if len(s) == 0 {
		return fallback
	}
	return s[len(s)-1]
}

func main() {
	var none []int           // nil-slice
	day := []int{}           // пустой литерал
	buf := make([]int, 0, 3) // место под три показания
	week := []int{4, 7}

	fmt.Println("none:", lastReading(none, -1))
	fmt.Println("day:", lastReading(day, -1))
	fmt.Println("buf:", lastReading(buf, -1))
	fmt.Println("week[:0]:", lastReading(week[:0], -1))
	fmt.Println("week:", lastReading(week, -1))
}

```
```

Все четыре пустых входа — nil-slice, пустой литерал, `make` с ёмкостью 3 и
пустой кусок `week[:0]` с ёмкостью 2 — дали `fallback`: длина у каждого 0, а
про nil и про ёмкость проверка не спрашивает. Для `week` функция вернула
последний элемент.

Когда же нужна проверка `s == nil`? Только когда договор функции прямо
различает nil-slice и пустой slice, который не равен nil. Такой договор
разобран ниже, в разделе «Что обещает функция». Чтобы узнать, есть ли
элементы, спрашивают длину.

## Общие результаты и разное представление

У nil-slice и любого пустого slice длина равна 0. Поэтому результаты
операций, которые здесь зависят от длины, совпадают:

- `len(s)` даёт 0;
- индексный цикл `for i := 0; i < len(s); i++` не выполняет ни одного
  прохода: условие ложно уже при первой проверке (урок 3.5);
- `copy(dst, src)` переносит столько элементов, какова меньшая из длин `dst`
  и `src`, и возвращает это число. Если одна из длин равна 0, переносится
  0 элементов. Ёмкость в этом расчёте не участвует: `copy` в
  `make([]int, 0, 3)` тоже перенесёт 0 элементов;
- `append` может добавить элемент и к nil-slice, и к пустому slice (урок
  4.5). В обоих результатах после такого вызова есть элемент, поэтому оба
  не равны `nil`.

Совпадение длины не делает представление одинаковым. Срез-выражение
`s[:0]` законно для обоих входов, но от nil-slice оно снова даёт nil-slice,
а от slice, который не равен nil, — результат, который тоже не равен nil.
Это правило из раздела «Пустой кусок другого slice». Совпадение элементов
после `append` не говорит, что ёмкости результатов равны или что у них
общий массив. Повторное использование массива каждого исходного slice
определяют по его длине, ёмкости и числу добавленных элементов (урок 4.5).

Программа ниже проверяет эти операции на nil-slice `n` и пустом литерале
`e`. Прежде чем смотреть вывод, назовите каждое число, которое она
напечатает, и каждый результат сравнения с `nil`.

```go

### Example: `05-same-ops`

Источник: `examples/05-same-ops/`

```go
package main

import "fmt"

func main() {
	var n []int  // nil-slice
	e := []int{} // пустой, но не nil

	// Индексный цикл: условие i < len(s) ложно уже при первой проверке.
	loopsN := 0
	for i := 0; i < len(n); i++ {
		loopsN++
	}
	loopsE := 0
	for i := 0; i < len(e); i++ {
		loopsE++
	}
	fmt.Println("проходов цикла:", loopsN, loopsE)

	// copy переносит min(len(dst), len(src)) элементов и возвращает это число.
	dst := make([]int, 2)
	fmt.Println("copy из n:", copy(dst, n), "copy в e:", copy(e, []int{1, 2}))

	// append добавляет элемент и к nil-slice, и к пустому.
	n = append(n, 7)
	e = append(e, 7)
	fmt.Println("append к n:", n, "nil", n == nil)
	fmt.Println("append к e:", e, "nil", e == nil)

	// Срез-выражение сохраняет различие между nil и не-nil.
	var m []int
	fmt.Println("m[:0] nil:", m[:0] == nil)
	fmt.Println("e[:0] nil:", e[:0] == nil)
}

```
```

Цикл не выполнил ни одного прохода ни для `n`, ни для `e`. Оба вызова
`copy` перенесли 0 элементов: из `n` нечего брать, в `e` некуда класть.
После `append` в каждом slice по одному элементу, и ни один не равен `nil`.
`m[:0]` от nil-slice снова nil, а `e[:0]` от slice, который не равен nil,
остаётся не nil. Числа проходов цикла и скопированных элементов совпали;
сравнение результатов с `nil` различает два срез-выражения.

Одна операция требует осторожности: `append` без новых элементов, например
`append(s)`. Длина результата остаётся прежней. Что при этом происходит с
nil-slice, спецификация отдельно не описывает и не обещает, что результат
перестанет быть nil. Вывод для вашего кода: не рассчитывайте на `append`
без элементов, чтобы получить slice, который не равен `nil`. На `s[:0]`
тоже не рассчитывайте: от nil-slice оно даёт nil по правилу языка.

## Что обещает функция

Код, который вызывает функцию, опирается на её договор — на то, что обещает
её комментарий-документация (урок 1.10). О пустом результате функция может
честно обещать одно из двух.

**Договор об элементах.** «Если чётных элементов нет, возвращает slice
длины 0». Равен ли результат `nil`, такой договор оставляет открытым.
Вызывающий код проверяет `len(r) == 0`, а тест функции смотрит только на
длину и элементы. Тест, который требует `r == nil` или `r != nil`, отверг
бы верную реализацию: договор этого не обещал.

**Договор о представлении.** «Результат никогда не равен nil; если чётных
элементов нет, возвращает slice длины 0». Такой договор пишут, когда
вызывающему коду действительно важно, nil перед ним или нет. Тогда
обещание обязана выполнить каждая ветка функции, в том числе на входе,
который сам равен `nil`, а тест вправе проверить `r != nil`. Наличие
элементов вызывающий код по-прежнему проверяет длиной: slice, который не
равен nil, не обязан содержать `r[0]`.

Две функции ниже собирают чётные элементы. `evensAppend` начинает сборку с
nil-slice, как в уроке 4.5, `evensLiteral` — с пустого литерала. Прежде чем
смотреть вывод, скажите: какие напечатанные значения у двух функций
совпадут, какие различатся и какая проверка в вызывающем коде различит их
результаты для входа без чётных чисел.

```go

### Example: `06-two-contracts`

Источник: `examples/06-two-contracts/`

```go
package main

import "fmt"

// evensAppend возвращает чётные элементы s по порядку.
// Сборка начинается с nil-slice.
func evensAppend(s []int) []int {
	var out []int
	for i := 0; i < len(s); i++ {
		if s[i]%2 == 0 {
			out = append(out, s[i])
		}
	}
	return out
}

// evensLiteral возвращает те же элементы.
// Сборка начинается с пустого литерала.
func evensLiteral(s []int) []int {
	out := []int{}
	for i := 0; i < len(s); i++ {
		if s[i]%2 == 0 {
			out = append(out, s[i])
		}
	}
	return out
}

func main() {
	odd := []int{1, 3}
	mixed := []int{1, 2, 4}

	a := evensAppend(odd)
	b := evensLiteral(odd)
	fmt.Println("нечётные:", a, b, "len", len(a), len(b))
	fmt.Println("нечётные, == nil:", a == nil, b == nil)

	c := evensAppend(mixed)
	d := evensLiteral(mixed)
	fmt.Println("смешанные:", c, d)
	fmt.Println("смешанные, == nil:", c == nil, d == nil)
}

```
```

Элементы и длины совпали для обоих входов. Для входа без чётных чисел
`evensAppend` ни разу не вызвала `append`, и её `out` остался nil-slice. У
`evensLiteral` результат пустой, но не nil. Договор об элементах выполняют
обе функции. Договор о представлении выполняет только `evensLiteral`.
Различит результаты этих функций сравнение с `nil`, а проверка длины для
обеих даёт один и тот же ответ.

Какой договор выбрать, язык не решает за вас: общего правила «всегда
возвращайте не nil» или «всегда возвращайте nil» нет. Если вызывающему коду
нужны только элементы, достаточно договора об элементах: он обещает ровно
то, что нужно. Договор о представлении пишут, когда кто-то действительно
различает эти два случая, и называют это в документации прямо.

Внутри программы nil-slice и пустой slice различает сравнение с `nil`, а
обычная печать через `fmt.Println`, как вы видели, их не различает. Разница
может проявиться и тогда, когда результат покидает программу, например
записывается в формат обмена данными для другой программы. Как принимать
такое решение на границе программы, разбирают уроки 14.13 «JSON и пустота»
и 15.10 «Пустые коллекции в ответе». В этом уроке достаточно знать, что такой
выбор есть и что его записывают в договор функции.

## FirstOr

`FirstOr` возвращает первый элемент `s`, если в `s` есть хотя бы один
элемент, и `fallback`, если элементов нет. Равен ли `s` значению `nil` и
какая у него ёмкость, на результат не влияет.

- `FirstOr([]int{4, 7}, -1)` возвращает 4;
- `FirstOr([]int{0}, -1)` возвращает 0: ноль — законное показание, а не
  признак пустоты;
- для `var none []int` вызов `FirstOr(none, -1)` возвращает -1;
- `FirstOr([]int{}, 42)` возвращает 42;
- `FirstOr(make([]int, 0, 3), -1)` возвращает -1: ёмкость 3, а элементов
  нет.

## EnsureNonNil

`EnsureNonNil` выполняет узкий договор о представлении: её результат никогда
не равен `nil`.

- Если `s` равен `nil`, функция возвращает slice длины 0, который не равен
  `nil`.
- Во всех остальных случаях функция возвращает сам `s`: ту же длину, ту же
  ёмкость и те же элементы, без копирования. Запись через результат видна
  в переданном slice.

Примеры:

- для `var none []int` результат `EnsureNonNil(none)` не равен `nil` и имеет
  длину 0;
- для `buf := make([]int, 0, 3)` результат `r` имеет длину 0 и ёмкость 3.
  Если взять от него slice длины 1 в пределах ёмкости (урок 4.4) и записать
  42 в первый элемент этого slice, `r[:1][0] = 42`, то `buf[:1][0]` тоже
  равен 42;
- для `week := []int{3, 1, 4}` результат `EnsureNonNil(week[1:3])` содержит
  1 и 4, а после записи 99 в его первый элемент `week[1]` тоже равен 99.

Это упражнение на договор, а не совет для любых функций. Если вызывающему
коду важны только элементы, функции достаточно обещать длину 0 и ничего не
обещать про `nil` (раздел теории «Что обещает функция»). `EnsureNonNil`
нужна там, где вызывающий код по договору различает nil-slice и пустой slice.

## Какое условие защищает s[0]

<!-- review:guard-choice -->

Первый вопрос из раздела упражнения «Что проверяется, а что нет»: что
вернёт `FirstOr(make([]int, 0, 3), -1)` и какое условие защищает `s[0]`.
Образец ответа ниже.

`make([]int, 0, 3)` даёт slice длины 0 и ёмкости 3. Элементов в нём нет,
поэтому ответ — запасное значение -1. Этот slice не равен `nil`, и проверка
`s != nil` пропустила бы выполнение к `s[0]`. Индекс 0 допустим только при
длине больше 0, и обращение к `s[0]` завершило бы программу аварийно.
Защищает условие на длину: при `len(s) == 0` функция возвращает `fallback`,
иначе `s[0]`. Ёмкость и сравнение с `nil` на вопрос «есть ли элементы» не
отвечают.

## Что различают проверки EnsureNonNil

<!-- review:contract-checks -->

Второй вопрос: какие проверки отличают верное решение `EnsureNonNil` от
неверного на трёх входах. Образец ответа ниже.

- Вход nil-slice. Договор обещает результат, который не равен `nil`, и
  длину 0. Проверка `r != nil` здесь обязательна: она ловит решение,
  которое вернуло `s` как есть или `s[:0]`.
- Вход `make([]int, 0, 3)`. Договор велит вернуть сам `s`. Снаружи это
  проверяют так: у результата длина 0 и ёмкость 3; затем от него берут
  slice длины 1 в пределах ёмкости, записывают в его первый элемент и
  проверяют, что значение видно через `s[:1]`. Одна только ёмкость 3 не
  доказывает общий массив: независимый `make([]int, 0, 3)` тоже имеет
  ёмкость 3. А вариант, который возвращает `make([]int, len(s))`, уже
  отличается ёмкостью 0.
- Вход `[]int{}`. Ёмкость 0, писать через результат некуда. Сам `s` и
  другой `[]int{}` выглядят снаружи одинаково: не nil, длина 0, ёмкость 0.
  Поэтому тест проверяет здесь только то, что результат не равен `nil` и
  имеет длину 0, и не утверждает, что копирования не было.

Отсюда общий вывод: договор задаёт, какие проверки законны. Договор о
представлении разрешает проверку `r != nil`; договор, который обещает
только длину 0, её бы не разрешал. Проверить можно лишь то, что видно
снаружи функции. Ещё одно место, где различие nil и пустого slice
становится заметным, — граница программы, когда результат уходит другой
программе; этот выбор разбирают уроки 14.13 и 15.10.

## Почему s[:0] и append(s) не помогают

<!-- review:normalization -->

Третий вопрос: почему `s[:0]` и `append(s)` не превращают nil-slice в
slice, который не равен `nil`. Срез-выражение от nil-slice по правилу языка
снова даёт nil-slice. `append` без новых элементов ничего не добавляет, и
спецификация не обещает, что для nil-slice его результат перестанет быть
nil. Надёжный способ — вернуть литерал `[]int{}` или `make([]int, 0)`: оба
дают пустой slice, который не равен `nil`. Верное решение целиком: при
`s == nil` вернуть `[]int{}`, иначе вернуть `s`.

## Проверка nil вместо длины

<!-- review:first-nil-guard -->

Решение проверяет `s != nil` и при истинном условии возвращает `s[0]`. На
nil-slice оно возвращает `fallback`, но `[]int{}`, `make([]int, 0, 3)` и
`week[:0]` не равны `nil`, и обращение к `s[0]` завершает функцию
аварийно.

Ловит это `TestFirstOr`: для пустого литерала тест сообщает
`FirstOr([]int{}, -1) завершилась аварийно, а должна была вернуть -1`.
Верная запись — проверка длины: при `len(s) == 0` функция возвращает `fallback`.

## Проверка ёмкости вместо длины

<!-- review:first-cap-guard -->

Решение возвращает `fallback` при `cap(s) == 0`, а иначе `s[0]`. Для
nil-slice и `[]int{}` ёмкость 0, и ответ верный. Но у `make([]int, 0, 3)`
ёмкость 3 при длине 0: место отведено, а элементов нет, и `s[0]` завершает

Ловит это `TestFirstOr`: тест сообщает, что `FirstOr(make([]int, 0, 3), -1)`

элементов есть. Верная запись — проверка длины.

## Вход возвращается как есть

<!-- review:ensure-returns-input -->

Решение всегда возвращает `s`. На всех входах, кроме nil-slice, это и есть
договор. Но на входе nil-slice результат тоже равен `nil`, а договор обещал
обратное.

Ловит это `TestEnsureNonNilFromNil`: тест сообщает, что
`EnsureNonNil(nil-slice)` вернула nil. Для nil-slice нужна отдельная ветка,
которая возвращает новый пустой slice.

## Пустой кусок от nil-slice

<!-- review:ensure-reslice-nil -->

Решение для nil-slice возвращает `s[:0]`, рассчитывая получить пустой slice,
который не равен `nil`. Но срез-выражение от nil-slice снова даёт nil-slice,
и результат по-прежнему равен `nil`.

Ловит это `TestEnsureNonNilFromNil`. Пустой slice, который не равен `nil`,
дают литерал `[]int{}` или `make([]int, 0)`.

## Любой пустой вход заменяется литералом

<!-- review:ensure-new-empty -->

Решение проверяет `len(s) == 0` вместо `s == nil` и для любого пустого
входа возвращает `[]int{}`. На nil-slice и на `[]int{}` ответ выглядит
верным. Но пустой slice с запасом ёмкости договор велит вернуть как есть, а
решение отдаёт другой slice с ёмкостью 0.

Ловит это `TestEnsureNonNilKeepsEmptyInputs`: для `make([]int, 0, 3)` тест
ждёт ёмкость 3 и получает 0. Договор различает случаи по `nil`, а не по
длине, поэтому и проверка в решении — `s == nil`.

## Копия «на всякий случай»

<!-- review:ensure-copies -->

Это решение создаёт результат через `make([]int, len(s))` и вызывает `copy`.
На непустом входе элементы оказываются в независимом массиве, хотя договор
требует вернуть сам переданный slice. Для входа длины 0 `copy` переносит
0 элементов, а `make([]int, len(s))` теряет запас ёмкости пустого входа.
Совпадение ёмкостей не доказывает общий массив: другой вариант мог бы
создать независимый `make([]int, 0, 3)` с той же ёмкостью, что и у входа.
У пустого входа с ёмкостью 3 общий массив проверяют записью через
допустимое расширение результата до длины 1 и чтением через исходный slice.

Ловит это `TestEnsureNonNilKeepsElements`: после записи 99 в первый
элемент результата тест ждёт 99 в `week[1]`, а там по-прежнему 1. На
`make([]int, 0, 3)` то же решение проваливает и
`TestEnsureNonNilKeepsEmptyInputs` из-за ёмкости 0. Здесь договор требует
вернуть вход без копирования.

## Вопрос 7
