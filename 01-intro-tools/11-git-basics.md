# Git в рабочем цикле

В уроке 1.2 рабочий цикл выглядел так: правка → `go run` → `go test`. Этот цикл
отвечает на вопрос, работает ли программа прямо сейчас. Через неделю работы над
проектом появляются другие вопросы. В каком виде были файлы, когда всё
работало? Какие изменения сделаны после этого и зачем? Цикл их не запоминает.

Эти ответы хранит **git** — программа, которая по вашей команде записывает
состояние файлов проекта вместе с коротким описанием сделанного. С git рабочий
цикл продолжается: правка → `go run` → `go test` → `git add` → `git commit`.

Код писать не нужно. Примеры урока — программы курса: каждая создаёт во
временном каталоге маленький проект `hello-git`, выполняет в нём команды `git`
и печатает, что изменилось после каждой команды. Одна из программ перед этим
ещё и собирает проект командой `go build`. Разбирать запись
этих программ не нужно: для урока важны команды и их вывод. Сами команды вы
выполняете у себя в терминале (урок 1.2). Как подготовить для этого git,
сказано в первом разделе.

## Репозиторий и история

Проект урока — модуль `hello-git`. В его каталоге лежат `go.mod` со строкой
`module hello-git` (урок 1.4) и `main.go` с программой, которая печатает одну
строку. Допустим, программа уже собирается и работает. Это состояние стоит
записать, прежде чем что-то менять.

Три слова понадобятся с самого начала.

- **Репозиторий** — хранилище истории проекта. Git держит его в каталоге `.git`
  внутри каталога проекта.
- **Коммит** — одна запись в репозитории. В неё входят файлы с тем содержимым,
  которое вы выбрали для записи, короткое сообщение о сделанном, а также имя и
  e-mail автора.
- **История** — цепочка коммитов проекта от первого до последнего.

**Git на вашем компьютере.** Сначала проверьте, что git установлен: выполните в
терминале `git --version`. Если git есть, команда напечатает одну строку,
которая начинается словами `git version`; дальше идёт номер версии, у каждого
свой. Если терминал сообщил, что такой команды нет, откройте официальную
страницу установки git
[https://git-scm.com/install/](https://git-scm.com/install/), выберите там свою
операционную систему и следуйте её инструкциям. Установка может добавить
каталог в `PATH`, а окно терминала, открытое до установки, этого не увидит
(урок 1.2). Поэтому после установки откройте новое окно терминала и снова
выполните `git --version`.

Затем один раз на компьютере сообщите git своё имя и e-mail. Это две команды:

- `git config --global user.name "Имя Фамилия"`;
- `git config --global user.email "you@example.com"`.

В этих командах `config` — подкоманда git, которая записывает настройку. Флаг
`--global` записывает её не в один проект, а в файл настроек вашего
пользователя. Поэтому настройка действует во всех ваших репозиториях на этом
компьютере. `user.name` и `user.email` — имена настроек. Значение в кавычках
замените своим; кавычки нужны, потому что в имени бывает пробел. При успехе
обе команды ничего не печатают.

Зачем это нужно: имя и e-mail автора записываются в каждый коммит. Если они не
заданы, git может отказаться создать коммит.

**Как завести репозиторий.** Репозиторий заводят командой `git init` в каталоге
проекта. Подкоманда `init` создаёт пустой репозиторий, то есть каталог `.git` в
текущем каталоге. Файлы проекта она в историю не записывает: сразу после неё
история пуста. Флаг `-b` задаёт имя, под которым git ведёт историю, — в уроке
это `main`. Без флага git берёт имя из своих настроек, а если имя там не
задано, — встроенное; на разных компьютерах оно может отличаться. Веток как
темы в курсе нет, и больше это имя в уроке не понадобится.

**Репозиторий и модуль — разные области.** После `git init -b main` в каталоге
`hello-git` лежат признаки двух областей, и у каждой свой файл и своя команда.

- `go.mod` создала команда `go mod init hello-git`. Этот файл делает каталог
  корнем модуля: модулю принадлежат файлы, для которых этот `go.mod` —
  ближайший вверх по дереву (урок 1.4).
- Каталог `.git` создала команда `git init -b main`. Он делает каталог корнем
  репозитория, историю которого ведёт git.

`go mod init` не заводит `.git`, а `git init` не заводит `go.mod`. Области
могут и не совпадать: в одном репозитории бывает несколько модулей, а модуль
может жить вовсе без репозитория. Для учебного модуля проще всего завести один
репозиторий в том же каталоге, где лежит `go.mod`. Тогда все файлы модуля
находятся внутри одного репозитория. Это соглашение курса, а не правило Go или
git.

**Форматирование и история.** `gofmt -w` из урока 1.10 тоже меняет файлы
проекта, но по-другому. Эта команда переписывает файл на диске, и в историю
ничего не попадает. Коммит, наоборот, файлы на диске не меняет: он записывает в
историю их выбранное содержимое. Одна команда не заменяет другую:
отформатированный файл окажется в истории только со следующим коммитом.

## Что попадает в коммит

Коммит записывает не весь каталог проекта, а только то, что вы заранее
подготовили. Чтобы видеть, что попадёт в следующий коммит, нужны три термина.

- **Рабочее дерево** — файлы проекта на диске: те, что вы правите в редакторе и
  видите в каталоге. Каталог `.git` к ним не относится.
- **Неотслеживаемый файл** — файл рабочего дерева, которого нет в истории и
  который вы ещё не подготовили к коммиту. Новый файл сначала неотслеживаемый:
  сам git его никуда не записывает.
- **Подготовленное изменение** — то, что команда `git add` отметила для
  следующего коммита. Для нового файла это его содержимое в момент `git add`.

Путь нового файла в историю один: неотслеживаемый файл → `git add` делает его
подготовленным изменением → `git commit` записывает подготовленное в новый
коммит. Три команды этого пути:

- `git add go.mod main.go` — подкоманда `add` готовит к следующему коммиту
  файлы, имена которых перечислены после неё через пробел. Готовится только то,
  что вы назвали. Файл, которого нет в списке, остаётся неотслеживаемым.
- `git commit -m "каркас проекта"` — подкоманда `commit` создаёт коммит из
  подготовленных изменений. Флаг `-m` задаёт **сообщение коммита** — строку в
  кавычках сразу после флага. В этом уроке сообщение всегда состоит из одной
  строки, и эта строка — тема коммита. Зачем она нужна, объясняет раздел «Тема
  коммита».
- `git status --porcelain` — подкоманда `status` сообщает состояние файлов, а
  флаг `--porcelain` выбирает короткий формат: по строке на файл. По
  документации git этот формат предназначен для программ и не меняется ни от
  версии git, ни от ваших настроек. Поэтому состояние файлов в этом уроке
  показано только в этом формате.

Каждая строка `git status --porcelain` — это код и имя файла. В уроке
встречаются два кода:

- `??` — неотслеживаемый файл; после кода один пробел и имя, например
  `?? main.go`;
- `A` — подготовленный новый файл; после буквы два пробела и имя, например
  `A  main.go`.

Пустой вывод значит, что подготовленных изменений нет и неотслеживаемых файлов
git не показывает. В примере ниже в каталоге всего два файла, `go.mod` и
`main.go`; после коммита оба записаны в историю, и вывод пуст. Какие файлы
может скрывать от этого вывода `.gitignore`, разобрано в разделе «Бинарник и
.gitignore».

Программа ниже создаёт проект `hello-git` из `go.mod` и `main.go` и печатает
список файлов в каталоге. Затем выполняет `git init -b main` и печатает список
ещё раз. После этого она по очереди выполняет `git status --porcelain`,
`git add go.mod main.go`, снова `git status --porcelain`,
`git commit -m "каркас проекта"`, ещё раз `git status --porcelain` и в конце
`git log --pretty=%s`. Каждая строка вывода начинается с метки — названия шага.
Сообщений самих команд программа не печатает, только завершилась ли команда без
ошибки. Имя и e-mail автора коммитов программа задаёт для своих команд сама и
отключает системные и пользовательские настройки git компьютера, на котором
запущена, поэтому эти настройки не влияют на то, что она печатает.

```go
// Программа создаёт во временном каталоге проект hello-git, заводит в нём
// репозиторий, делает первый коммит и печатает содержимое каталога и
// состояние файлов на каждом шаге.
package main

import (
	"fmt"
	"os"
	"os/exec"
	"path/filepath"
	"strings"
)

// goMod — go.mod подготовленного проекта.
const goMod = `module hello-git

go 1.27
`

// mainSource — main.go подготовленного проекта.
const mainSource = `package main

import "fmt"

func main() {
	fmt.Println("привет из репозитория")
}
`

// isolation добавляется к окружению каждой команды: автор коммитов задан
// явно, системный и пользовательский файлы настроек git отключены, поэтому
// эти настройки не влияют на то, что печатает программа.
var isolation = []string{
	"GIT_AUTHOR_NAME=go-course",
	"GIT_AUTHOR_EMAIL=go-course@example.com",
	"GIT_COMMITTER_NAME=go-course",
	"GIT_COMMITTER_EMAIL=go-course@example.com",
	"GIT_CONFIG_NOSYSTEM=1",
	"GIT_CONFIG_GLOBAL=/dev/null",
}

func main() {
	if err := run(); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}

// run создаёт проект, выполняет в нём команды и удаляет временный каталог.
func run() error {
	dir, err := os.MkdirTemp("", "git-basics-")
	if err != nil {
		return err
	}
	defer os.RemoveAll(dir)

	p := &project{dir: dir}
	p.write("go.mod", goMod)
	p.write("main.go", mainSource)
	p.list("в каталоге до git init")
	p.step("git init -b main", "git", "init", "-b", "main")
	p.list("в каталоге после git init")
	p.git("состояние до git add", "status", "--porcelain")
	p.step("git add go.mod main.go", "git", "add", "go.mod", "main.go")
	p.git("состояние после git add", "status", "--porcelain")
	p.step("git commit", "git", "commit", "-m", "каркас проекта")
	p.git("состояние после коммита", "status", "--porcelain")
	p.git("тема коммита", "log", "--pretty=%s")
	return p.err
}

// project — каталог проекта и первая ошибка; после ошибки шаги не выполняются.
type project struct {
	dir string
	err error
}

// command готовит команду в каталоге проекта с окружением isolation.
func (p *project) command(name string, args ...string) *exec.Cmd {
	cmd := exec.Command(name, args...)
	cmd.Dir = p.dir
	cmd.Env = append(os.Environ(), isolation...)
	return cmd
}

// write записывает файл проекта.
func (p *project) write(name, content string) {
	if p.err == nil {
		p.err = os.WriteFile(filepath.Join(p.dir, name), []byte(content), 0o644)
	}
}

// quiet выполняет команду и не печатает её сообщений.
func (p *project) quiet(name string, args ...string) {
	if p.err != nil {
		return
	}
	if _, err := p.command(name, args...).CombinedOutput(); err != nil {
		p.err = fmt.Errorf("%s %s: %w", name, strings.Join(args, " "), err)
	}
}

// step выполняет команду и печатает только, завершилась ли она с кодом 0.
func (p *project) step(label, name string, args ...string) {
	if p.err != nil {
		return
	}
	p.quiet(name, args...)
	fmt.Println(label+" завершилась без ошибки —", p.err == nil)
}

// list печатает имена в каталоге проекта через запятую.
func (p *project) list(label string) {
	if p.err != nil {
		return
	}
	entries, err := os.ReadDir(p.dir)
	if err != nil {
		p.err = err
		return
	}
	names := make([]string, 0, len(entries))
	for _, entry := range entries {
		names = append(names, entry.Name())
	}
	fmt.Println(label+":", strings.Join(names, ", "))
}

// git печатает вывод команды git по строке на запись, каждую со своей меткой.
func (p *project) git(label string, args ...string) {
	if p.err != nil {
		return
	}
	out, err := p.command("git", args...).Output()
	if err != nil {
		p.err = fmt.Errorf("git %s: %w", strings.Join(args, " "), err)
		return
	}
	text := strings.TrimRight(string(out), "\n")
	if text == "" {
		fmt.Println(label + ": (пусто)")
		return
	}
	for _, line := range strings.Split(text, "\n") {
		fmt.Println(label + ": " + line)
	}
}

Первые три строки вывода относятся к разделу «Репозиторий и история». До
`git init` в каталоге лежали только `go.mod` и `main.go`. После команды

До `git add` оба файла показаны кодом `??`: они есть в рабочем дереве, но в
истории их нет и к коммиту они не подготовлены. После
`git add go.mod main.go` у обоих код `A`: теперь это подготовленные изменения.
Строки в обоих случаях идут по имени файла. `git commit` записал
подготовленное в первый коммит, и вывод `git status --porcelain` стал пустым.
Последняя строка — тема единственного коммита, `каркас проекта`.

У себя вы увидите ещё и сообщения `git init` и `git commit`. Их текст зависит
от компьютера, поэтому в выводе примера их нет. Коды `??` и `A`, порядок строк и
тема коммита у вас будут такими же.

**Коммит берёт подготовленное, а не весь каталог.** Если в рабочем дереве есть
новый файл, не названный в `git add`, коммит создаётся без него. Сам файл
остаётся неотслеживаемым и дождётся своего `git add`. Правка уже подготовленного
файла тоже не попадёт в коммит сама. По документации `git add` запоминает
содержимое файла в момент своего запуска, и в следующий коммит войдёт именно оно. Если после `git add` файл
изменился — например, его переписал `gofmt -w`, — новое содержимое попадёт в
коммит, только если перед `git commit` снова выполнить `git add` для этого
файла.

**Повторите у себя.** Создайте пустой учебный каталог `hello-git` — в файловом
менеджере или командой `mkdir hello-git` — и перейдите в него командой `cd`
(урок 1.2). Выполните `go mod init hello-git`, создайте в редакторе `main.go` с
программой, которая печатает любую строку, и проверьте её командой `go run .`.
Затем выполните по порядку `git init -b main`, `git status --porcelain`,
`git add go.mod main.go`, `git status --porcelain`,
`git commit -m "каркас проекта"` и ещё раз `git status --porcelain`. Коды и
порядок строк должны совпасть с выводом примера. Если `git commit` отказался
создать коммит, проверьте, что выполнены обе команды `git config` из раздела
«Репозиторий и история». Не удаляйте этот каталог: он понадобится в следующем
разделе.

## Бинарник и .gitignore

`go build` без аргументов кладёт в текущий каталог исполняемый файл и при
успехе ничего не печатает (урок 1.5). Для проекта `hello-git`, где `main.go`
лежит в корне модуля, этот файл называется `hello-git`. Для git это просто
новый файл рабочего дерева. Git не знает, что файл собран из исходников, и сам
его не игнорирует.

Записывать собранный файл в историю незачем. Он целиком получается из
исходников, которые в истории уже есть: имея `go.mod` и `main.go`, его
собирают заново одной командой `go build`. Каждая сборка создаёт файл заново,
а сборка под другую систему даёт другой файл (урок 1.5). Поэтому бинарник
сборки — первый кандидат в `.gitignore`. Другие кандидаты — локальные
артефакты, то есть файлы, нужные только на вашем компьютере; в этом уроке их нет.

**`.gitignore`** — обычный текстовый файл в каталоге проекта. Каждая его строка
описывает неотслеживаемые файлы, которые git должен не замечать:
`git status --porcelain` их не показывает. В примере в `.gitignore` одна строка:
`/hello-git`. Косая черта в начале привязывает строку к каталогу, где лежит
`.gitignore`, поэтому строка называет файл `hello-git` в корне репозитория.
По документации команды `go` в Windows собранный файл называется
`hello-git.exe` (урок 1.5), и строка была бы `/hello-git.exe`. Другие правила
записи строк `.gitignore` в уроке не нужны.

Сам `.gitignore` — файл проекта, как `main.go`. После записи он новый и
неотслеживаемый и проходит тот же путь: `git add .gitignore`, затем
`git commit`. Строка начинает действовать сразу после записи файла, коммита
для этого не требуется. Но пока `.gitignore` не закоммичен, правила нет в
истории проекта: оно есть только в вашем рабочем дереве.

Программа ниже без вывода повторяет шаги предыдущего примера до первого коммита
включительно. Печатать она начинает с двух признаков исходного состояния:
пустого вывода `git status --porcelain` и темы `каркас проекта`. Затем
выполняет `go build`, печатает список файлов и состояние. После этого
записывает `.gitignore` со строкой `/hello-git` и снова печатает состояние.
Потом выполняет `git add .gitignore`, `git commit -m "добавлен .gitignore"` и
печатает состояние и все темы истории. Собранный файл программа не запускает.

// project — каталог проекта и первая ошибка; после ошибки шаги не выполняются.
type project struct {
	dir string
	err error
}

// command готовит команду в каталоге проекта с окружением isolation.
func (p *project) command(name string, args ...string) *exec.Cmd {
	cmd := exec.Command(name, args...)
	cmd.Dir = p.dir
	cmd.Env = append(os.Environ(), isolation...)
	return cmd
}

// write записывает файл проекта.
func (p *project) write(name, content string) {
	if p.err == nil {
		p.err = os.WriteFile(filepath.Join(p.dir, name), []byte(content), 0o644)
	}
}

// quiet выполняет команду и не печатает её сообщений.
func (p *project) quiet(name string, args ...string) {
	if p.err != nil {
		return
	}
	if _, err := p.command(name, args...).CombinedOutput(); err != nil {
		p.err = fmt.Errorf("%s %s: %w", name, strings.Join(args, " "), err)
	}
}

func (p *project) step(label, name string, args ...string) {

		return
	}
	p.quiet(name, args...)
	fmt.Println(label+" завершилась без ошибки —", p.err == nil)
}

func (p *project) list(label string) {

		return

	entries, err := os.ReadDir(p.dir)
	if err != nil {
		p.err = err
		return

	names := make([]string, 0, len(entries))
	for _, entry := range entries {
		names = append(names, entry.Name())
	}
	fmt.Println(label+":", strings.Join(names, ", "))
}

// git печатает вывод команды git по строке на запись, каждую со своей меткой.
func (p *project) git(label string, args ...string) {
	if p.err != nil {
		return
	}
	out, err := p.command("git", args...).Output()
	if err != nil {
		p.err = fmt.Errorf("git %s: %w", strings.Join(args, " "), err)
		return
	}
	text := strings.TrimRight(string(out), "\n")
	if text == "" {
		fmt.Println(label + ": (пусто)")
		return
	}
	for _, line := range strings.Split(text, "\n") {

После `go build` в каталоге появился `hello-git`, и `git status --porcelain`
показал его кодом `??`, как любой новый файл. Git не отличил собранный файл от
исходника. Решать, что записывать в историю, приходится вам: `hello-git` собран
из `go.mod` и `main.go`, которые уже есть в первом коммите, и `go build`
соберёт его из них заново. Поэтому истории он не нужен, и его прячут строкой
`.gitignore`.

Когда записан `.gitignore`, строки с `hello-git` в выводе больше нет, а сам
`.gitignore` показан кодом `??`. Правило подействовало ещё до коммита.
`.gitignore` подготовили командой `git add .gitignore` — код `A` — и записали
вторым коммитом. После коммита вывод снова пуст. Две последние строки — темы

**Что значит пустой вывод после этого коммита.** Файл `hello-git` по-прежнему
лежит в каталоге, но в истории его нет: два коммита записали только `go.mod`,
`main.go` и `.gitignore`. Пустой `git status --porcelain` не значит, что всё из
каталога сохранено в истории. Файлы, скрытые `.gitignore`, он просто не
показывает.

**Обратная ловушка: файл, уже записанный в коммит.** `.gitignore` действует
только на неотслеживаемые файлы. Допустим, `hello-git` назвали в `git add` и
закоммитили раньше, чем появилась строка `/hello-git`. Тогда эта строка не
уберёт файл из истории, и git продолжит его отслеживать. При этом
`git status --porcelain` может оставаться пустым. Значит, по пустому выводу
нельзя заключить, что собранного файла нет в истории. Отслеживаемые файлы
проверяет отдельный пункт чек-листа мини-проекта урока 1.13, и команду для этой
проверки даёт сам чек-лист. Как убрать уже записанный файл из истории, курс не
разбирает.

`git status --porcelain`: вывод должен стать пустым.

## Тема коммита

Подкоманда `log` показывает историю репозитория. Флаг `--pretty=%s` выбирает
формат: `%s` означает тему коммита. С ним `git log` печатает по одной строке на
коммит — только тему, без автора, даты и списка файлов. Строки идут от новых
коммитов к старым: первой стоит тема последнего коммита. По документации git
это порядок `git log` по умолчанию. В примере `02-ignore-binary` первой
напечатана тема `добавлен .gitignore`, а второй `каркас проекта`, хотя
`каркас проекта` записан раньше.

Через месяц темы коммитов — главное, по чему видно, что происходило в проекте.
Представьте два проекта с одинаковыми изменениями. В первом
`git log --pretty=%s` печатает `добавлен .gitignore`, под ней
`каркас проекта`. Во втором — `правки`, под ней снова `правки`. Первую
историю можно прочитать как рассказ: сначала записали каркас проекта, потом
добавили `.gitignore`. Вторая не говорит ничего — ни что изменилось, ни зачем. Узнать это по второй истории
можно, только разбирая содержимое коммитов, а `git log --pretty=%s` его не
показывает. Полную проверку содержимого коммитов в мини-проекте 1.13 задаёт
его чек-лист.

**Содержательная тема** называет, что изменилось, а если причина не очевидна —
то и зачем. `каркас проекта` называет, что записано первым коммитом. Тема
`исправлена строка приветствия, чтобы в ней было имя модуля` называет и
изменение, и его причину. **Пустая тема** вроде `правки` подходит к любому
коммиту любого проекта и поэтому ничего не сообщает. Проверка простая:
прочитайте тему и спросите себя, поймёт ли её человек, который не видел
изменений.

В примерах урока темы написаны по-русски, строчными буквами, без точки в конце
и в одну строку. В `git commit -m` тему берут в двойные кавычки, потому что в
ней есть пробелы.

## Границы урока и что дальше

В уроке был один репозиторий в одном каталоге и одна цепочка коммитов. Ветки,
слияния, удалённые репозитории и работа в команде — вне курса, продолжения этой
темы нет. Изменение уже закоммиченного файла, откат изменений и удаление файлов
из истории урок не разбирает. Из форм `git status` и `git log` урок использует
только `git status --porcelain` и `git log --pretty=%s`.

  печатается от новых коммитов к старым.
- B. Первой строкой `каркас проекта`, второй `добавлен .gitignore`: история
  печатается от старых коммитов к новым.

Прежде чем смотреть ответ, назовите, какой из двух коммитов новее и на какой
строке вывода стоит тема последнего коммита.

**Правильный ответ: A.**

Новее коммит `добавлен .gitignore`, и его тема стоит первой: по умолчанию
`git log` идёт от последнего коммита к первому. Вариант B читает историю как
дневник, сверху вниз по времени, но в примере `02-ignore-binary` первой
напечатана тема второго коммита, `добавлен .gitignore`.

## Вопрос 5

Вы создали пустой каталог, выполнили в нём `go mod init hello-git`, а затем
`git init -b main`. Какая команда создала репозиторий, и значит ли это, что
репозиторий и модуль — одно и то же?

Варианты ответа:

- A. Репозиторий создала уже `go mod init`: `go.mod` и есть репозиторий, а
  `git init -b main` только дал истории имя `main`.
- B. Репозиторий создала `git init -b main`, появился `.git`; модуль задаёт
  `go.mod` от другой команды, а в один каталог их кладут по соглашению курса.
- C. Репозиторий создала `git init -b main`, и он же стал модулем: репозиторий
  и модуль — одно и то же, а `go.mod` только хранит имя.

Прежде чем смотреть ответ, назовите файл или каталог, который создала каждая из
двух команд.

**Правильный ответ: B.**

`go mod init hello-git` создала `go.mod`, а `git init -b main` — каталог
`.git`. Вариант A принимает файл модуля за репозиторий, но в примере `01-first-commit` каталога
`.git` до `git init` не было, хотя `go.mod` уже лежал. Вариант C видит один
каталог и заключает, что область одна, но области могут расходиться: в одном
репозитории бывает несколько модулей, а модуль может жить без репозитория.

## Вопрос 6

Вы закоммитили `.gitignore`, который скрывает собранный файл. Через месяц вы
читаете историю командой `git log --pretty=%s`. Какая тема этого коммита
скажет, что и зачем было сделано?

Варианты ответа:

- A. `правки`
- B. `fix`
- C. `добавлен .gitignore для бинарника сборки`
- D. `коммит 2`

Прежде чем смотреть ответ, объясните, что должна сообщать тема, если
`git log --pretty=%s` не показывает ни файлов, ни самих изменений.

**Правильный ответ: C.**

Тема C называет изменение и его причину, а кроме темы `git log --pretty=%s` о
коммите ничего не печатает. Варианты A и B кажутся достаточными, раз git всё
равно хранит изменения, но такая тема подходит к любому коммиту любого проекта.
Вариант D называет только порядковый номер, а не то, что сделано.
