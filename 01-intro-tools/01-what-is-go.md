Ты получаешь материалы одного урока курса по Go.

Твоя задача — **не пересказать исходный материал целиком**, а подготовить

1. понять основные концепции урока;
2. вспомнить синтаксис и правила Go, которые здесь изучаются;
3. ответить на проверочные вопросы из раздела «Проверочные вопросы»;
4. решить типовые практические задачи по этой теме;
5. не перепутать похожие понятия и исключения.

### Правила подготовки ответа

- Сохраняй техническую точность.
- Не выкидывай правила, которые могут быть проверены в quiz.
- Особое внимание уделяй причинам: **почему ответ правильный**, а остальные
  варианты неправильны.
- Если в quiz есть конкретный сценарий, команду, код или вывод программы —
  обязательно объясни соответствующее правило.
- Не пересказывай очевидные вводные фразы и организационную информацию.
- Не добавляй информацию, которой нет в предоставленных материалах, если она
  не нужна для объяснения приведённого материала.
- Код из примеров используй как источник конкретных правил и поведения Go.
- Не нужно разбирать каждую строку примера, если это не помогает ответить
  на вопрос quiz.
- Сохраняй названия команд, функций, типов, операторов и других сущностей
  точно.
- Если есть важное исключение или типичная ошибка — вынеси её отдельно.

# Что такое Go и зачем он нужен

Вы прочитаете две короткие готовые программы на Go и проследите путь такой
программы: от текста в файле до запуска на другом компьютере. По дороге станет
видно, какие трудности авторы Go хотели убрать и чем за устройство языка
приходится платить. Писать и запускать код пока не нужно: Go вы установите в
уроке 1.2, а первую собственную программу напишете в уроке 1.3.

## От текста в файле до работающей программы

Представьте: вы написали программу и хотите, чтобы она работала на сервере —
удалённом компьютере, который отвечает на запросы пользователей. На этом пути
программа существует в нескольких видах, и у каждого вида своё название.

**Исходный текст** — то, что пишет программист: обычный текстовый файл с
программой на языке Go, например `main.go`. Процессор такой текст выполнить не
может. Он выполняет только машинный код — команды, записанные для его типа
процессора.

**Компилятор** переводит исходный текст в машинный код заранее, до запуска.
Работу, которая превращает исходный текст в готовую к запуску программу,
называют **сборкой**. Компилятор входит в **тулчейн** — набор инструментов Go
для сборки и другой работы с исходным текстом. Один из этих инструментов —
команда `go`: через неё собирают программу и выполняют другую работу с
исходным текстом на Go. Тулчейн нужен на том компьютере, где программу
собирают.

**Исполняемый файл** — результат сборки: файл с машинным кодом, который
запускает операционная система. Когда команда `go` собирает программу для
Windows, она добавляет к имени файла окончание `.exe`.

Компьютер, на котором программа потом работает, выполняет исполняемый файл, а
не исходный текст. Программа на Go заранее скомпилирована в машинный код.
Некоторые языки устроены иначе: например, программы на Java работают внутри
виртуальной машины — программы-посредника, которая исполняет промежуточный
код. Внутри каждой программы на Go тоже работает служебная часть — среда
исполнения Go, её разбирает раздел «Что лежит в исполняемом файле и где он
запустится». Но виртуальной машины среда исполнения Go не содержит.

Чтобы понять, где исполняемый файл сможет запуститься, понадобятся ещё два
понятия. **Операционная система** — программа, которая запускает другие
программы и даёт им доступ к файлам, сети и памяти: например, Linux, macOS или Windows. **Архитектура процессора** — тип процессора
вместе с набором машинных команд, которые он понимает. Например, Go называет
архитектуры именами `amd64` и `arm64`.

## Минимальная программа строка за строкой

Вот программа целиком, а под ней — то, что она печатает.

```go

### Example: `01-hello`

Источник: `examples/01-hello/`

```go
// Минимальная программа: пакет main, импорт fmt и функция main.
package main

import "fmt"

func main() {
	fmt.Println("Привет, Go!")
}

```
```

- Первая строка — комментарий: текст после `//` до конца строки служит
  пояснением для человека, и компилятор его пропускает.
- `package main` говорит, к какому пакету относится файл. **Пакет** — единица
  кода Go: компилятор переводит пакет целиком, а программа собирается из своего
  пакета и тех пакетов, которые она подключает. У этой программы собственный
  пакет состоит из одного файла.
- `import "fmt"` — **импорт**: программа подключает пакет `fmt` из стандартной
  библиотеки Go — набора пакетов, который поставляется вместе с Go, — чтобы
  печатать текст.
- `func main() {` начинает **функцию** `main` — именованную группу инструкций.
  Пустые круглые скобки означают, что функция не принимает входных значений
  (аргументов). После скобок не записан результат: функция ничего не
  возвращает. Инструкции функции стоят между фигурными скобками.
- `fmt.Println(...)` — вызов функции `Println` из пакета `fmt`. Она печатает
  текст, записанный в кавычках.
- Последняя строка `}` закрывает функцию `main`.

Запущенная программа сначала проходит подготовку (инициализацию), а затем
выполняет функцию `main` из пакета `main`. Когда `main` заканчивает работу,
программа завершается.

Отсюда два условия, без которых программа на Go не запускается. Оба записаны в
спецификации языка — официальном описании его правил:

1. пакет называется `main`;
2. в этом пакете объявлена функция `main` без аргументов и без результата.

Условия независимы: выполнение одного не заменяет другое. Исполняемый файл
получается только из пакета `main`. Если заменить в этой программе `package main` на
`package hello`, сборка проверит, что код компилируется, но исполняемого файла
не создаст. А пакет `main` без функции `main` нарушает второе условие и не
собирается: текущий тулчейн сообщает, что функция `main` не объявлена, и
исполняемого файла не создаёт.

Импорт `fmt` условием не является. Он нужен этой программе только потому, что
она печатает текст средствами пакета `fmt`. Запускаемая программа, которая
ничего не печатает, может обойтись совсем без импорта.

Писать такую программу самостоятельно сейчас не нужно. Пакеты и импорты
разбирает урок 1.6, форму объявления функции — урок 1.7, а похожую программу
своими руками вы напишете в уроке 1.3.

## Зачем авторы создали Go

Авторы Go работали в Google над очень большими программами. Над каждой такой
программой трудились большие команды, и она зависела от множества других
пакетов. Цель проекта, по словам авторов, — убрать медлительность и
неуклюжесть разработки таких программ. Язык должен был выдерживать большие
команды и большие программы с большим числом зависимостей — пакетов, без
которых программа не собирается.

Что именно мешало, авторы называют сами:

- сборка шла медленно;
- зависимости разрастались без контроля;
- большую программу было трудно понять;
- писать инструменты, которые сами разбирают и обрабатывают код, было трудно;
- сборка больших проектов на тогдашних языках и системах сборки требовала
  чрезмерной сложности.

Ещё одну трудность авторы описывают как вынужденный выбор. Приходилось выбирать
между быстрой компиляцией, быстрым выполнением программы и удобством
программирования: все три качества сразу не давал ни один распространённый
язык. Вдобавок процессоры с несколькими ядрами — вычислителями, каждый из
которых выполняет свою последовательность команд, — стали обычными. А языки
почти не помогали писать программы, которые выполняют несколько задач
одновременно.

Go часто описывают набором свойств: компилируемый, со сборщиком мусора, со
встроенной поддержкой конкурентной работы, то есть выполнения нескольких задач
одновременно. Такой набор описывает, каким язык получился, но не объясняет,
зачем его создали. Поводом авторы называют описанные выше трудности больших
программ, а многие решения в устройстве Go они связывают с конкретной
трудностью:

- **Медленная сборка.** Неиспользованный импорт компилятор считает ошибкой, а
  не мелочью: иначе лишние импорты копятся по мере роста кода и команды и
  замедляют сборку. Как выглядит этот отказ, показывает раздел «Компилятор
  отказывается, а не предупреждает».
- **Большой код трудно понимать и обрабатывать.** В тулчейн входят инструменты
  для работы с большими объёмами кода, например автоматическое форматирование.
  Их разбирает урок 1.10.
- **Многоядерные процессоры и сетевые серверы, которые выполняют много работы
  одновременно.** Конкурентная работа встроена в сам язык. В этом уроке она не
  разбирается.
- **Большие программы, где много задач идёт одновременно.** В Go есть сборщик
  мусора — механизм, который сам находит память, больше не нужную программе, и
  освобождает её. Управлять ресурсами в такой программе с ним проще. Его цена —
  в разделе «Где применяют Go и чем платят за сборщик мусора».

Все эти связи между трудностями и решениями — слова самих авторов о целях
языка, а не результаты замеров. Из того, что авторы хотели быстрой сборки, не
следует, сколько будет собираться ваш проект.

## Что лежит в исполняемом файле и где он запустится

Вернёмся к серверу из раздела «От текста в файле до работающей программы».
Путь программы до него состоит из трёх отдельных шагов:

1. на компьютере с установленным тулчейном Go исходный текст собирают;
2. получается исполняемый файл;
3. этот файл копируют на сервер и запускают там.

Сборку выполняет команда `go build`: из пакета `main` она получает исполняемый
файл. Запускать её самостоятельно вы будете в уроке 1.5.

**Что попадает в файл.** В каждой программе на Go работает **среда исполнения
Go** — часть библиотеки Go, которая выполняет для программы служебную работу:
сборку мусора, поддержку конкурентной работы и другие важные механизмы. Среда
исполнения не запускается отдельной программой рядом с вашей. По документации Go,
стандартный тулчейн по умолчанию кладёт внутрь исполняемого файла весь Go-код:
код самой программы, нужных ей пакетов Go и среды исполнения. Библиотеки самой
операционной системы в этот файл не входят: при запуске файл может обращаться к
ним, как описано в условии 3 ниже.

**Что нужно на сервере.** Отсюда следствие: чтобы запустить такой файл,
устанавливать Go на сервер не нужно. Go нужен там, где программу собирают, а не
там, где её запускают. Но «Go не нужен» не значит «файл запустится где угодно».
Следствие верно при четырёх условиях.

1. **Файл собран для системы и архитектуры сервера.** Цель сборки задают две
   настройки тулчейна: `GOOS` — операционная система и `GOARCH` — архитектура
   процессора. Они описывают машину запуска, а не машину сборки. Например,
   файл для `linux/arm64` и файл для `windows/amd64` — разные результаты сборки.
   Если система или архитектура сервера отличаются, программу собирают заново
   под сервер. Некоторые системы умеют запускать чужой машинный код через
   эмуляцию или перевод команд, но рассчитывать на эту возможность при
   доставке программы не стоит.
2. **Версия операционной системы поддерживается.** У каждого выпуска Go есть
   минимальные поддерживаемые версии систем. Поэтому совпадение системы и
   архитектуры ещё не означает, что файл заработает на любой их версии.
3. **Нужные системные библиотеки есть на сервере.** Программа может обращаться
   к библиотекам самой операционной системы. Они не входят в исполняемый файл
   Go и обычно поставляются вместе с системой.
4. **Программа написана на чистом Go, без cgo.** Механизм cgo позволяет
   программе на Go вызывать код на языке C. Для такой программы могут
   понадобиться дополнительные библиотеки C. Здесь речь о программе без cgo.

Итак, сервер получает исполняемый файл, а не исходный текст и не тулчейн. Если
программа написана на чистом Go, этому файлу нужны подходящая пара «система +
архитектура», поддерживаемая версия системы и библиотеки самой системы.
Установленный Go ему не нужен. Установка Go на сервер и не поможет запустить файл, собранный для другой пары: пару файла
выбирают при сборке.

## Компилятор отказывается, а не предупреждает

Инструменты разработки сообщают о проблемах в коде по-разному.
**Предупреждение** — замечание, после которого программа всё равно собирается.
**Ошибка компиляции** — сообщение, после которого компилятор программу не
создаёт. Компилятор Go, по его документации, предупреждений не выдаёт вовсе:
только ошибки, которые не дают скомпилировать программу.

Вот программа, которая не собирается. Она импортирует два пакета: `fmt` и `os`
(стандартный пакет с операциями операционной системы, например с удалением
файлов). Пользуется она только пакетом `fmt`.

```go
@broken unused-import
```

Под кодом — сообщение, которое напечатала сборка этого примера:
`./main.go:6:2: "os" imported and not used`. Оно указывает файл `main.go`,
строку 6 и позицию 2 в этой строке, а затем говорит: пакет `"os"` импортирован и
не используется. Точная формулировка сообщения зависит от тулчейна. Сам запрет
записан в спецификации языка: пакет нельзя импортировать, не обратившись ни к
одному имени из него.

**Почему исполняемого файла нет.** Компилятор встретил ошибку, которая не даёт
скомпилировать программу, и сборка остановилась раньше, чем появился бы
исполняемый файл. Так ведёт себя текущий тулчейн на примере выше: после
сообщения о неиспользованном импорте исполняемый файл не появляется. Чтобы
программа собралась, лишний импорт убирают или действительно пользуются пакетом.

**Зачем такая строгость.** Авторы Go объясняют правило скоростью сборки: лишние
импорты замедляют компиляцию, а по мере того как растут код и команда, они
копятся. Мгновенное удобство «пусть пока полежит» авторы сознательно обменяли
на быструю и понятную сборку в будущем.

У запрета есть предусмотренный спецификацией выход — импорт с пустым именем:
`import _ "путь/к/пакету"`. Так подключают пакет только ради подготовительной
работы, которую он выполняет при запуске программы. Неиспользованным такой
импорт не считается. Зачем он нужен, разбирает урок 1.6.

**Чего компилятор не ловит.** Отказ компилятора означает, что программа
нарушает правило языка. Он не означает, что в собранной программе нет ошибок.
Вот два случая, в которых компилятор собирает программу, хотя с ней не всё в
порядке:

- **Выброшенная ошибка.** Многие функции сообщают о неудаче отдельным
  результатом — значением-ошибкой. Например, функция удаления файла из пакета
  `os` возвращает такое значение, если удалить файл не получилось. Язык не
  заставляет программу этот результат забирать. Программа, которая его просто
  не берёт, собирается и молча работает, даже когда файла не было.
  Руководство Effective Go называет отбрасывание ошибки очень плохой практикой,
  но компилятор такую программу пропускает. Работу со значениями-ошибками
  разбирает урок 5.11.
- **Подозрительное место.** `go vet` — отдельная команда тулчейна. Она читает
  исходный текст и сообщает о подозрительных местах: например, о вызове печати,
  где в шаблоне вывода указано число, а передан текст. Такая программа
  компилируется и запускается, а `go vet` о ней сообщает. Её сообщение —
  результат отдельной проверки, а не отказ компилятора: сборку оно не
  останавливает. `go vet` опирается на приблизительные признаки, поэтому не
  каждое её сообщение указывает на настоящую ошибку, и находит она не всё.
  Команду разбирает урок 1.10.

Ни компилятор, ни `go vet` не обещают найти все ошибки в программе.

## Где применяют Go и чем платят за сборщик мусора

Проект Go на своём сайте называет области, где применяют язык: облачные и
сетевые сервисы, программы для командной строки, веб-разработку, а также DevOps
и SRE — работу по развёртыванию и сопровождению работающих систем. Эти страницы
проекта рекламируют язык: они показывают, где Go используют, но не доказывают,
что он подойдёт именно вашей задаче.

Возьмём одну такую область — сетевой сервис: программу на сервере, которая
принимает запросы и отвечает на них. У сервиса есть две разные меры скорости.
**Пропускная способность** — сколько запросов сервис успевает обработать за
единицу времени. **Задержка** — сколько ждёт ответа каждый отдельный запрос.
Руководство Go по сборщику мусора отмечает, что для веб-сервиса задержка
каждого отдельного запроса часто важнее пропускной способности.

**Сборщик мусора** — часть среды исполнения, которая находит память, больше не
нужную программе, и возвращает её для повторного использования. Его работа не
бесплатна:

- сборщик мусора расходует процессорное время и память, и соотношение этих
  затрат зависит от того, как часто он запускается;
- большую часть работы сборщик мусора Go выполняет одновременно с программой,
  чтобы меньше влиять на задержку, но в его работе есть короткие паузы, во время
  которых программа останавливается целиком;
- при резком росте нагрузки сборка мусора может запускаться чаще, и частые
  сборки увеличивают задержку;
- документация Go пишет, что паузы часто короче миллисекунды, — именно «часто»:
  числовой гарантии паузы она не даёт;
- сборщик мусора не отменяет необходимости думать о памяти.

Отсюда вывод для сервиса со строгим требованием к задержке. То, что сетевые
сервисы — одна из областей Go, само по себе ничего не решает. Сказать «Go
подойдёт в любом случае» нельзя: у сборщика мусора есть затраты и паузы.
Сказать «со сборщиком мусора быстрых ответов не будет» тоже нельзя: большую
часть работы он делает одновременно с программой, а общего правила «всегда
быстрее» или «всегда медленнее» документация не даёт. Решение принимают,
сверив задержку на своей нагрузке со своим требованием.

# Проверочные вопросы

## Вопрос 1

Коллега объясняет, откуда взялся Go: «Авторы хотели компилируемый язык со
сборщиком мусора и встроенной конкурентной работой — ради этих свойств язык и
создали». Какое объяснение ближе к тому, что пишут сами авторы?

Варианты ответа:

- A. Авторы сначала выбрали компиляцию, сборщик мусора и конкурентную работу
  как желаемые свойства нового языка. Работа над большими программами дала им
  возможность применить эти свойства на практике.
- B. Авторы столкнулись с медленной сборкой, разросшимися зависимостями и
  сложностью больших программ. Решения в языке отвечали этим трудностям:
  например, запрет лишних импортов помогал не замедлять сборку.
- C. Авторы столкнулись с трудностями проверки больших программ. Основным
  решением стало перенести поиск ошибок в компилятор: успешная сборка должна
  подтверждать, что программа работает правильно.
- D. Авторы столкнулись с трудностями работы больших команд. Основным решением
  стал сборщик мусора: освобождение памяти должно было избавить разработчиков
  от необходимости продумывать расход памяти программы.

Прежде чем смотреть ответ, назовите одну трудность разработки и объясните,
какое решение в Go с ней связано.

**Правильный ответ: B.**

Вариант A меняет местами причину и результат: авторы описывают трудности
разработки, а свойства языка — как решения этих трудностей. Вариант C
приписывает успешной сборке проверку правильности программы: компилятор
пропускает, например, отбрасывание значения-ошибки. Вариант D преувеличивает
пользу сборщика мусора: он освобождает ненужную память, но расход памяти
программы по-прежнему нужно продумывать.

## Вопрос 2

Вы собрали программу на чистом Go, без cgo, для системы и архитектуры своего
компьютера. Её нужно запустить на сервере с другой операционной системой и
другой архитектурой процессора. Go на сервере не установлен. Версию системы
сервера ваш выпуск Go поддерживает, и нужные программе системные библиотеки на
сервере есть. Какое действие надёжно даст работающую программу на сервере?

Варианты ответа:

- A. Скопировать уже собранный файл: среда исполнения лежит внутри него,
  значит, он запустится на любой машине.
- B. Установить Go на сервер и запустить там скопированный файл.
- C. Заново собрать программу из исходного текста для пары `GOOS`/`GOARCH`
  сервера и скопировать на сервер новый файл.
- D. Скопировать на сервер файл `main.go` и запустить его без сборки.

**Правильный ответ: C.**

Вариант A верно помнит, что установленный Go файлу не нужен, но делает лишний
вывод: файл собран для одной пары «система + архитектура», и на машине с другой
парой он может не запуститься вовсе. Рассчитывать на то, что сервер выполнит
чужой файл через эмуляцию, нельзя. Вариант B путает машину сборки с машиной
запуска: Go нужен там, где собирают, а его установка на сервер не меняет пару,
для которой файл уже собран. Вариант D считает, что сервер выполняет исходный текст, хотя программа
на Go заранее компилируется в машинный код, и сервер запускает исполняемый
файл.

## Вопрос 3

Программа из урока импортирует пакеты `fmt` и `os`, а пользуется только
пакетом `fmt`.

```go
@quiz _broken/unused-import
```

Какое утверждение о её сборке верно целиком?

Варианты ответа:

- A. Сборка закончится: компилятор напечатает предупреждение о лишнем импорте,
  и исполняемый файл появится.
- B. Компилятор соберёт программу, а о лишнем импорте потом сообщит отдельная
  команда `go vet`.
- C. Компилятор сообщит об ошибке, и сборка остановится раньше, чем появился бы
  исполняемый файл. Любая программа, которую компилятор всё же собрал, ошибок
  не содержит.
- D. Компилятор сообщит об ошибке, и сборка остановится раньше, чем появился бы
  исполняемый файл. Чтобы программа собралась, лишний импорт убирают.

**Правильный ответ: D.**

Вариант A ждёт предупреждения, а компилятор Go предупреждений не выдаёт: только
ошибки, которые не дают скомпилировать программу. Вариант B путает отказ
компилятора с отдельной проверкой: `go vet` сообщает о подозрительных местах в
программах, которые компилируются, а эта программа не компилируется. Вариант C
верно описывает отказ, но во втором предложении обобщает его: программа,
которая выбрасывает значение-ошибку, собирается, и ни компилятор, ни `go vet`
не обещают найти все ошибки.

## Вопрос 4

Команда пишет сетевой сервис. Главное требование — задержка каждого отдельного
запроса должна оставаться малой, в том числе при резком росте нагрузки. Команда
рассматривает Go. Какой вывод следует из этого урока?

Варианты ответа:

- A. Проверить задержку отдельных запросов на ожидаемой нагрузке и сравнить
  её с требованием. Сборщик мусора расходует ресурсы и ненадолго останавливает
  программу; эти затраты нужно учитывать вместе с остальной её работой.
- B. Проверить число запросов в секунду на ожидаемой нагрузке и сравнить его
  с требованием. Если сервис успевает обрабатывать поток запросов, этого
  достаточно, чтобы оценить задержку каждого отдельного запроса.
- C. Измерить длительность одной паузы сборщика мусора при небольшой нагрузке
  и сравнить её с требованием. Если пауза мала, этого достаточно для оценки
  задержки запросов при резком росте нагрузки.
- D. Взять из документации описание типичных пауз сборщика мусора и сравнить
  его с требованием. Если типичная пауза мала, этого достаточно для выбора Go
  без проверки задержки на нагрузке сервиса.

Прежде чем смотреть ответ, объясните, почему числа запросов в секунду или
длительности одной паузы недостаточно для требования из условия.

**Правильный ответ: A.**

Вариант B подменяет задержку пропускной способностью: сервис может обрабатывать
много запросов, но отдельный запрос при этом ждёт долго. Вариант C переносит
наблюдение при небольшой нагрузке на резкий её рост: расход ресурсов и работа
сборщика мусора могут измениться. Вариант D принимает описание типичных пауз
за гарантию для конкретного сервиса. Документация такой гарантии не даёт;
задержку проверяют на своей нагрузке.

## Вопрос 5

Ниже — программа из раздела «Минимальная программа строка за строкой». Сравните
в ней три части: строку `package main`, импорт `import "fmt"` и функцию `main`.

```go
@quiz 01-hello
```

Какие из этих частей нужны любой запускаемой программе на Go, а какая нужна
только этому примеру?

Варианты ответа:

- A. Нужны все три: без импорта `fmt` запускаемой программы на Go не бывает.
- B. Достаточно строки `package main`: если пакет назван `main`, функцию `main`
  можно не объявлять.
- C. Достаточно функции `main` без аргументов и без результата: имя пакета не
  важно, и с `package hello` из этой программы тоже получится исполняемый файл.
- D. Нужны две: пакет называется `main`, и в нём объявлена функция `main` без
  аргументов и без результата. Импорт `fmt` нужен только потому, что эта
  программа печатает текст.

**Правильный ответ: D.**

Вариант A принимает потребность примера за общее правило: пакет `fmt` здесь
подключён ради печати, а запускаемая программа, которая ничего не печатает,
может обойтись без импорта. Вариант B оставляет только условие об имени пакета:
пакет `main` без функции `main` не собирается, и текущий тулчейн сообщает, что
функция `main` не объявлена. Вариант C оставляет только условие об объявленной
функции: исполняемый файл получается только из пакета `main`, а с
`package hello` сборка проверит, что код компилируется, но исполняемого файла
не создаст.
