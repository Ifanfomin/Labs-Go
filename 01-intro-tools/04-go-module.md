## Инструкция для нейросети

Ты получаешь материалы одного урока курса по Go.

Твоя задача — **не пересказать исходный материал целиком**, а подготовить
компактный, точный конспект, по которому студент сможет:

1. понять основные концепции урока;
2. вспомнить синтаксис и правила Go, которые здесь изучаются;
3. ответить на проверочные вопросы из раздела «Проверочные вопросы»;
4. решить типовые практические задачи по этой теме;
5. не перепутать похожие понятия и исключения.

### Правила подготовки ответа

- Сохраняй техническую точность.
- Не выкидывай правила, которые могут быть проверены в quiz.
- Особое внимание уделяй причинам: **почему ответ правильный**, а остальные
  варианты неправильны.
- Если в quiz есть конкретный сценарий, команду, код или вывод программы —
  обязательно объясни соответствующее правило.
- Не пересказывай очевидные вводные фразы и организационную информацию.
- Не добавляй информацию, которой нет в предоставленных материалах, если она
  не нужна для объяснения приведённого материала.
- Код из примеров используй как источник конкретных правил и поведения Go.
- Не нужно разбирать каждую строку примера, если это не помогает ответить
  на вопрос quiz.
- Сохраняй названия команд, функций, типов, операторов и других сущностей
  точно.
- Если есть важное исключение или типичная ошибка — вынеси её отдельно.

# Модуль и go mod init

Представьте, что вы начинаете проект — программу для заметок — в новом каталоге
`notes`. Чтобы собирать пакеты этого проекта, команде `go` нужны два ответа.
Первый: каким полным именем называть каждый пакет проекта. Второй: по правилам
какой версии языка Go компилировать эти пакеты. Оба ответа записаны в файле
`go.mod`. Каталог с этим файлом и подкаталоги под ним образуют **модуль** —
набор пакетов, которые команда `go` рассматривает как одно целое.

В уроке 1.2 модуль был рабочим определением: каталог с `go.mod` вместе со всем
содержимым. Там же `go env GOMOD` показывала, какой `go.mod` команда нашла,
поднимаясь от текущего каталога вверх. В уроке 1.3 заготовка пришла с готовым
`go.mod`, а сообщение `package lesson/first-program is not a main package`
назвало пакет путём, взятым из этого файла. Остаются три вопроса: откуда
`go.mod` берётся, что означают его строки и где кончается модуль.

Код в этой теме писать не нужно. Команды `go mod init` и `go list -m` можно
выполнить у себя, если Go установлен. Программы примеров уже готовы: каждая
создаёт временный каталог, запускает в нём команды `go`, печатает ответы и
удаляет каталог. Для урока важны командные строки и вывод, а не код самих
программ.

## Откуда берётся go.mod

Пока ни в каталоге проекта, ни выше по дереву нет `go.mod`, модуля у проекта
нет. Команде `go` неоткуда взять ни имя для его пакетов, ни версию языка, а
`go env GOMOD`, как вы видели в уроке 1.2, печатает значение, которое не
является путём к `go.mod`.

Новый `go.mod` создаёт команда `go mod init`. Она записывает файл в текущий
каталог, и этот каталог становится **корнем модуля** — верхним каталогом, с
которого модуль начинается. Аргументом команде передают **путь модуля** (его
ещё называют именем модуля) — имя, которое вы выбрали для проекта. Для проекта
`notes` команда могла бы быть такой: `go mod init example.com/notes`.

Отсюда правило запуска: команду выполняют один раз, в верхнем каталоге нового
проекта. Пустым этот каталог быть не обязан: документация такого требования не
ставит, а пустой каталог в примере ниже — просто удобная обстановка. Условие
другое: `go.mod` в этом каталоге ещё не должно быть. Если файл уже есть,
`go mod init` завершится ошибкой.

В подкаталогах того же проекта и в каждом новом окне терминала `go mod init`
повторять не нужно. `go.mod` — обычный текстовый файл на диске, и каждая
команда `go` заново находит его, поднимаясь от текущего каталога вверх. Запуск
`go mod init` в подкаталоге существующего модуля модуль не «обновляет»:
команда создаёт в подкаталоге новый `go.mod`, то есть второй, вложенный модуль.
Документация не описывает для этого случая ни отказа, ни предупреждения, и
текущая реализация команды предупреждения не печатает, поэтому вложенный модуль
легко завести незаметно. Что меняет вложенный модуль, разобрано в разделе
«Модуль — область ближайшего go.mod».

Программа ниже создаёт пустой временный каталог и запускает в нём команду
`go mod init example.com/notes`. Затем она печатает три ответа о результате:
появился ли `go.mod`, какая в нём первая непустая строка и есть ли в нём
строка `go`. В конце программа удаляет каталог.

```go

### Example: `01-mod-init`

Источник: `examples/01-mod-init/`

```go
// Программа создаёт пустой временный каталог, запускает в нём
// go mod init example.com/notes и печатает, что команда записала в go.mod.
package main

import (
	"fmt"
	"os"
	"os/exec"
	"path/filepath"
	"strings"
)

// goCommand запускает команду go с аргументами args в каталоге dir и
// возвращает её стандартный вывод без завершающего перевода строки. Поток
// ошибок команды не печатается: важен только код возврата.
func goCommand(dir string, args ...string) (string, error) {
	command := exec.Command("go", args...)
	command.Dir = dir
	// Одинаковые условия запуска на любой машине.
	command.Env = append(os.Environ(), "GOWORK=off", "GO111MODULE=on", "GOTOOLCHAIN=local")
	out, err := command.Output()
	if err != nil {
		return "", fmt.Errorf("не удалось выполнить go %s: %w", strings.Join(args, " "), err)
	}
	return strings.TrimSuffix(string(out), "\n"), nil
}

// run выполняет пример во временном каталоге и удаляет каталог перед
// возвратом, в том числе при ошибке.
func run() error {
	// Пустой временный каталог: go.mod в нём пока нет.
	root, err := os.MkdirTemp("", "go-module-init-")
	if err != nil {
		return fmt.Errorf("не удалось создать каталог: %w", err)
	}
	defer os.RemoveAll(root)

	if _, err := goCommand(root, "mod", "init", "example.com/notes"); err != nil {
		return err
	}

	manifest := filepath.Join(root, "go.mod")
	_, statErr := os.Stat(manifest)
	fmt.Println("файл go.mod создан —", statErr == nil)

	content, err := os.ReadFile(manifest)
	if err != nil {
		return fmt.Errorf("не удалось прочитать go.mod: %w", err)
	}
	lines := strings.Split(string(content), "\n")

	// Первая непустая строка файла, дословно.
	first := ""
	for _, line := range lines {
		if strings.TrimSpace(line) != "" {
			first = line
			break
		}
	}
	fmt.Println("строка module —", first)

	// Первая строка, которая начинается с "go ": номер в ней зависит от
	// установленного Go, поэтому печатается только, найдена ли она.
	directive := ""
	for _, line := range lines {
		if strings.HasPrefix(line, "go ") {
			directive = line
			break
		}
	}
	fmt.Println("директива go найдена —", directive != "")
	return nil
}

func main() {
	// Выход с ошибкой — только здесь, после того как run удалила каталог.
	if err := run(); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}

```
```

Вторая строка вывода повторяет строку, которую команда записала в файл: слово
`module` и переданный аргумент. Временный каталог, в котором программа
запустила команду, называется не `notes`, а путь модуля в файле всё равно равен
аргументу. Значит, путь модуля берётся из аргумента команды, а не из имени
каталога.

В этом примере созданный файл состоит из трёх строк: `module example.com/notes`,
пустая строка и строка `go` с номером версии. Каждая строка `go.mod` с
содержимым — **директива**: ключевое слово, за которым идут его аргументы. В
созданном файле директив две: `module` и `go`. Номер в директиве `go` зависит
от версии Go, которой выполнили `go mod init`. Поэтому третья строка вывода
сообщает только, что директива `go` в файле нашлась, а номера не печатает. Когда
вы выполните команду у себя, номер в созданном файле определит ваша версия Go.

Строк о зависимостях (они начинаются словом `require`) в этом файле нет, и
`go.mod` из двух директив — полноценный файл. Модулю он нужен и без
зависимостей: обе директивы команда `go` применяет к пакетам самого модуля.
Зависимости разбирают уроки 11.6 и 11.10–11.11.

Готовый `go.mod` в заготовке урока 1.3 тоже не появился сам. Модуль для
заготовки заранее, один раз, создали авторы курса и выбрали ему путь
`lesson/first-program`. Поэтому создавать модуль в заготовке было не нужно, а
`go mod init` в её каталоге завершилась бы ошибкой: `go.mod` там уже есть.
Файл `go.mod` — обычный текст, поэтому для запуска упражнения 1.3 на своём
компьютере его содержимое можно было и скопировать. В собственном новом
проекте готового файла не будет: `go mod init` в верхнем каталоге проекта
выполняете вы, один раз, и путь модуля тоже выбираете вы.

## Строка module: путь модуля

Директива `module` объявляет путь модуля — имя, под которым команда `go` знает
модуль. Путь выбирает автор проекта: `go mod init` записывает в файл ровно ту
строку, которую получила аргументом. От этой строки команда `go` строит имена
всех пакетов модуля; как именно, объясняет раздел «Путь модуля — префикс пути
импорта».

В проекте легко спутать три разных имени:

- имя каталога — как каталог называется на диске, например `notes`;
- имя пакета — слово после `package` в файлах пакета, например `main` у
  запускаемой программы из урока 1.3;
- путь модуля — строка после `module` в `go.mod`, например `example.com/notes`.

Путь модуля команда `go` берёт из `go.mod`. Имя каталога и строка `package`
его не задают. Совпадать с ними путь при этом может: путь `example.com/notes`
для каталога `notes` — нормальный выбор. Но определяет путь аргумент
`go mod init`, а совпадение выбрал автор, когда этот аргумент писал.

Какую строку выбрать? Если модуль никто не будет скачивать как зависимость,
подойдёт любое уникальное имя, которым вы распоряжаетесь. Части пути
составляют из ограниченного набора символов ASCII, поэтому путь с пробелом,
например `my notes`, команда отвергнет. Модулю, который будут скачивать другие
проекты, нужен путь, по которому его можно скачать; как выбрать такой путь,
разбирают уроки 11.10–11.11.

Модули в примерах урока названы `example.com/notes` и `example.com/other`. В
такой форме, с доменом в начале, документация Go показывает модуль, который
мог бы быть опубликован. Путь заготовки урока 1.3, `lesson/first-program`,
точки не содержит и для модуля, который никто не скачивает, тоже годится.

Этот путь вы уже видели в сообщении урока 1.3
`package lesson/first-program is not a main package`. Там команда `go` назвала
пакет не словом из строки `package`, а путём, построенным от пути модуля
заготовки.

## Как спросить у команды, в каком модуле вы

Путь модуля не обязательно искать глазами в `go.mod`. Команда `go list -m` без
аргументов печатает путь модуля, в котором находится текущий каталог. Эта
команда только спрашивает: модуль она не создаёт и `go.mod` не меняет. Создаёт
модуль `go mod init`, а узнаёт его путь `go list -m`.

Команда из урока 1.2, `go env GOMOD`, отвечает на соседний вопрос: где лежит
`go.mod` этого модуля. Она печатает абсолютный путь к файлу.

Обе команды находят `go.mod` одинаково: проверяют текущий каталог, затем
родительские и берут первый найденный файл. Так они работают при двух
условиях. Первое — включён модульный режим, а по умолчанию он включён. При
`GO111MODULE=off` команда `go` файлы `go.mod` не учитывает, и пути модуля такой
запуск не покажет. Второе — нет рабочей области: если в текущем или
родительском каталоге лежит файл `go.work`, команда работает в режиме рабочей
области, и ответ может быть другим. Рабочие области этот урок не разбирает.
Программы примеров запускают команды именно так: с включённым модульным
режимом и без рабочей области.

Программа ниже создаёт временный каталог и запускает в нём ту же команду
`go mod init example.com/notes`. Затем она спрашивает из того же каталога
`go list -m` и `go env GOMOD` и печатает ответы. Путь к `go.mod` на каждой
машине свой, поэтому вместо самого пути программа печатает только, оканчивается
ли он файлом `go.mod`. По документации Go пути файлов в Linux и macOS
разделяются прямой косой чертой, а в Windows — обратной. Перед проверкой
окончания пути программа приводит разделители к прямой косой черте, поэтому её
ответ одинаков во всех трёх системах. В конце программа удаляет каталог.

```go

### Example: `02-list-m`

Источник: `examples/02-list-m/`

```go
// Программа создаёт временный каталог с модулем example.com/notes и
// спрашивает у команды go, в каком модуле она находится.
package main

import (
	"fmt"
	"os"
	"os/exec"
	"path/filepath"
	"strings"
)

// goCommand запускает команду go с аргументами args в каталоге dir и
// возвращает её стандартный вывод без завершающего перевода строки. Поток
// ошибок команды не печатается: важен только код возврата.
func goCommand(dir string, args ...string) (string, error) {
	command := exec.Command("go", args...)
	command.Dir = dir
	// Одинаковые условия запуска на любой машине.
	command.Env = append(os.Environ(), "GOWORK=off", "GO111MODULE=on", "GOTOOLCHAIN=local")
	out, err := command.Output()
	if err != nil {
		return "", fmt.Errorf("не удалось выполнить go %s: %w", strings.Join(args, " "), err)
	}
	return strings.TrimSuffix(string(out), "\n"), nil
}

// run выполняет пример во временном каталоге и удаляет каталог перед
// возвратом, в том числе при ошибке.
func run() error {
	root, err := os.MkdirTemp("", "go-module-init-")
	if err != nil {
		return fmt.Errorf("не удалось создать каталог: %w", err)
	}
	defer os.RemoveAll(root)

	// Та же команда, что в первом примере: теперь каталог — модуль.
	if _, err := goCommand(root, "mod", "init", "example.com/notes"); err != nil {
		return err
	}

	modulePath, err := goCommand(root, "list", "-m")
	if err != nil {
		return err
	}
	fmt.Println("путь модуля по go list -m —", modulePath)

	// Путь к go.mod абсолютный и на каждой машине свой, поэтому печатается
	// только, чем он оканчивается. Разделители приводятся к "/", чтобы ответ
	// не зависел от системы.
	gomod, err := goCommand(root, "env", "GOMOD")
	if err != nil {
		return err
	}
	fmt.Println("go env GOMOD оканчивается на /go.mod —", strings.HasSuffix(filepath.ToSlash(gomod), "/go.mod"))
	return nil
}

func main() {
	// Выход с ошибкой — только здесь, после того как run удалила каталог.
	if err := run(); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}

Команда `go list -m` напечатала ровно строку из директивы `module`. Для
заготовки урока 1.3 та же команда напечатала бы `lesson/first-program` — путь
из сообщения о пакете, который не является пакетом `main`.

Вне всякого модуля `go list -m` тоже ничего не создаёт. Текущая команда `go`
печатает там `command-line-arguments` вместо пути модуля и завершается без
ошибки. Это поведение текущей реализации, а не гарантия, поэтому опираться на
эту строку не стоит: увидев её, проверьте, из какого каталога вы запускаете
команду.

## Модуль — область ближайшего go.mod

Рабочее определение из урока 1.2 — каталог с `go.mod` вместе со всем
содержимым — верно, пока внутри нет другого `go.mod`. Общий случай описывает
**область модуля** — дерево каталогов под его `go.mod`, кроме подкаталогов, в
которых лежит свой `go.mod`, и всего, что под ними. Файл относится к модулю
ближайшего `go.mod`, если идти от каталога файла вверх.

Правило следует из того, как команда `go` находит модуль: она проверяет
текущий каталог, затем родительские и останавливается на первом `go.mod`.
Поэтому вложенный `go.mod` — корень другого модуля. Подкаталог с этим файлом и
всё под ним выпадают из области внешнего модуля: команда, запущенная из корня
внешнего модуля, не считает пакеты этого подкаталога пакетами внешнего модуля.
Условия те же, что в разделе «Как спросить у команды, в каком модуле вы»:
модульный режим включён, файла `go.work` нет.

Область нужна команде `go`, потому что для каждого пакета она берёт у модуля
две вещи. Первая — путь модуля, с которого начинается полное имя пакета.
Вторая — версия языка, по правилам которой пакет компилируется. Обе разобраны
в двух следующих разделах.

Возьмём такое дерево:

- в корне лежит `go.mod` модуля `example.com/notes`;
- в подкаталоге `sub/deep` своего `go.mod` нет;
- в подкаталоге `other` лежит свой `go.mod` модуля `example.com/other`.

// спрашивает go list -m из трёх мест этого дерева.

// возвращает её стандартный вывод без завершающего перевода строки. Поток
// ошибок команды не печатается: важен только код возврата.
func goCommand(dir string, args ...string) (string, error) {
	command := exec.Command("go", args...)
	command.Dir = dir
	// Одинаковые условия запуска на любой машине.
	command.Env = append(os.Environ(), "GOWORK=off", "GO111MODULE=on", "GOTOOLCHAIN=local")
	out, err := command.Output()
	if err != nil {
		return "", fmt.Errorf("не удалось выполнить go %s: %w", strings.Join(args, " "), err)
	}
	return strings.TrimSuffix(string(out), "\n"), nil
}

// возвратом, в том числе при ошибке.

		return fmt.Errorf("не удалось создать каталог: %w", err)

	defer os.RemoveAll(root)

		return err

## Путь модуля — префикс пути импорта

У каждого пакета есть **путь импорта** — полное имя пакета. Этим именем пакет
называет команда `go`, и по нему пакет подключают другие пакеты. Путь импорта
пакета из модуля строится так: путь модуля, косая черта и путь каталога пакета
от корня модуля. Поэтому путь модуля — префикс путей импорта всех пакетов
модуля. Части пути импорта разделяет прямая косая черта в любой системе, в том
числе в Windows.

Пример из документации Go: у модуля `github.com/google/go-cmp` есть каталог
`cmp`, и путь импорта пакета в нём — `github.com/google/go-cmp/cmp`.

То же правило в модуле `example.com/notes`. Пакет из подкаталога `sub/deep`
получает путь импорта `example.com/notes/sub/deep`. Имя пакета в правило не
входит. Если файлы в каталоге `tags` этого модуля начинаются строкой
`package labels`, путь импорта пакета — `example.com/notes/tags`: он следует за
каталогом, а не за строкой `package`. Правило действует внутри области модуля.
Пакет из `other`, где лежит свой `go.mod`, получает путь от `example.com/other`.

У пакета в самом корне модуля путь каталога пустой, поэтому его путь импорта
равен пути модуля. Этим объясняется сообщение урока 1.3. Пакет заготовки
лежал в корне модуля `lesson/first-program`, и команда `go` назвала его путём
`lesson/first-program`, а не словом из строки `package`.

У пакетов стандартной библиотеки, например у `fmt` из урока 1.3, префикса
модуля нет: правило описывает пакеты модулей.

Пакет в подкаталоге модуля — самостоятельный пакет, а не часть пакета из
каталога выше. Общий префикс пути не даёт ему ни наследования, ни особого
доступа к пакету из родительского каталога.

**Граница.** Пока путь импорта для вас — имя пакета. Что такое импорт,
разбирает урок 1.6. Как разложить свои пакеты по подкаталогам и записать их
импорт, разбирает урок 1.8.

## Строка go: версия языка

Вторая директива — `go`, за которой идёт номер версии. Она задаёт **версию
языка** для пакетов модуля, которому принадлежит этот `go.mod`. Компилятор
проверяет эти пакеты по правилам названной версии языка и отвергает возможности
языка, которые появились в более поздних версиях. Версия языка — первые две
части номера из строки `go`: третья часть номера, если она есть, версию языка
не меняет.

Эту версию легко спутать с версией установленного Go — той, что печатает
`go version`. Это разные величины: установленный Go — свойство вашего
компьютера, директива — свойство модуля. Например, в строке `go` модуля
записана более старая версия языка, чем у установленного Go. Модуль можно
собирать этой более новой установкой, и `go version` покажет её номер. Но
пакеты модуля компилятор всё равно проверит по правилам старой версии языка из
строки `go`: возможность, которая появилась в языке позже, в таком модуле будет
отвергнута. Если поднять номер в строке `go` до версии, в которой эта
возможность появилась, та же установка её примет.

У директивы есть и вторая роль. Начиная с Go 1.21 она задаёт ещё и минимальную
версию Go, которую требует модуль, причём требование обязательное. Как команда
`go` поступает, когда установленный Go ниже этой версии, этот урок не
разбирает.

Какая директива `go` действует, решает область модуля. Для пакета в `sub/deep`
действует строка `go` корневого `go.mod`, а для пакета в `other` — строка `go`
из `other/go.mod`. Одно исключение: отдельный файл может задать себе свою
версию языка особой строкой условия сборки в начале файла. Как её записывать,
этот урок не учит.

Директива `go` значима и в `go.mod` без единой зависимости: она действует на
пакеты самого модуля.

**Граница.** Чем версии языка отличаются друг от друга и как команда `go`
выбирает, какой версией Go собирать модуль, этот урок не разбирает.

## Вопрос 2

В строке `go` файла `go.mod` модуля записана более старая версия, чем версия
установленного Go, которую на том же компьютере печатает `go version`. Что
обозначает строка `go` этого модуля?

Варианты ответа:

- A. Версию установленного Go: строка должна повторять число, которое печатает
  `go version`.
- B. Номер для зависимостей: строка нужна, только когда в `go.mod` есть строки
  `require`.
- C. Справочную пометку: `go mod init` записала номер, а компилятор строку не
  читает.
- D. Версию языка: по её правилам компилируются пакеты этого модуля, даже когда
  установлен более новый Go.

Сначала скажите одним предложением, свойство чего описывает эта строка —
модуля или компьютера, — и только потом сверяйтесь с ответом.

**Правильный ответ: D.**

Директива `go` задаёт версию языка для пакетов модуля, которому принадлежит
`go.mod`, а начиная с Go 1.21 — ещё и обязательную минимальную версию Go для
модуля. Вариант A ждёт, что число повторит вывод `go version`, но
установленный Go — свойство компьютера, директива — свойство модуля, и в
условии они уже разошлись. Вариант B исходит из того, что `go.mod` нужен только
ради зависимостей, а директива действует на пакеты самого модуля и значима без
единой строки `require`. Вариант C принимает строку за справку, а компилятор по
ней решает, какие возможности языка разрешены в пакетах модуля.

  `go list -m` в `notes`, с путём из имени каталога; так же он появился и в
  заготовке урока 1.3.
- C. `go mod init example.com/notes` повторяют в каждом подкаталоге и в каждом
  новом терминале, иначе `go list -m` модуля не найдёт; в заготовке урока 1.3
  каталог один, поэтому хватило одного запуска.
- D. Путь модуля задаёт имя каталога, а `go mod init` лишь переписывает его в
  файл; узнать путь можно только чтением `go.mod`; путь заготовки урока 1.3
  тоже взят из имени каталога.

**Правильный ответ: A.**

`go mod init` один раз записывает `go.mod` в верхний каталог проекта, а
`go list -m` из подкаталога находит этот файл, поднимаясь вверх, и только
печатает путь; заготовка урока 1.3 пришла уже модулем, поэтому `go.mod` в ней
был. Вариант B опирается на то, что `go list -m` работает с модулем, но она
только спрашивает и `go.mod` не создаёт, а путь приходит из аргумента
`go mod init`. Вариант C путает поиск модуля с его созданием: повторный
`go mod init` в `notes` завершится ошибкой, потому что `go.mod` уже есть, а в
подкаталоге заведёт второй, вложенный модуль. Вариант D выводит путь из имени
каталога, хотя путь `lesson/first-program` выбрали авторы заготовки, а
прочитать путь модуля без открытия файла позволяет `go list -m`.
