# Теория

# gofmt, go vet и go doc

Тулчейн Go не только собирает и запускает программы. Ещё три его команды
работают с исходным текстом программы. `gofmt` приводит отступы и пробелы в
файле к стандартному виду. `go vet` ищет подозрительные места в программе,
которую компилятор уже принял. `go doc` печатает документацию пакета, собранную
из комментариев в его исходниках.

Код писать не нужно. Примеры урока — программы курса: каждая создаёт во
временном каталоге маленький проект, выполняет в нём команды и печатает, что
они сообщили. Разбирать запись этих программ не нужно: для урока важны файлы
проекта и вывод команд. Те же команды вы можете выполнить у себя, в каталоге
своего модуля — там, где лежит `go.mod` (урок 1.4).

## Один формат: gofmt

В уроке 1.9 форматная строка `Printf` задавала, как значения попадут в
напечатанный текст. Здесь речь о другом — о **форматировании кода**: расстановке
отступов и пробелов в самом исходном файле.

Представьте проект, над которым работают двое. Один делает отступы табуляцией и
ставит пробелы вокруг `+`, другой пишет вплотную и без отступов. Код с разной
расстановкой труднее читать. А правки, которые только двигают пробелы, мешают
увидеть в проекте правки по существу.

`gofmt` расставляет отступы и пробелы в файле по одним и тем же правилам, кто бы
этот файл ни написал. Это отдельная программа тулчейна, она лежит
рядом с `go` (урок 1.2). По документации `gofmt` форматирует программы на Go:
отступы делает табуляцией, а выравнивание — пробелами. Получается стандартная
расстановка, и ею отформатирован весь код стандартной библиотеки Go. Большую
часть вопросов о расстановке решает инструмент, а не договорённость в команде.
Редакторы с `gopls` (урок 1.2) обычно настроены форматировать файл при
сохранении тем же алгоритмом.

`gofmt` запускают с одним из двух флагов:

- `gofmt -l .` — проверка без правки. Точка означает текущий каталог. Если
  расстановка файла `.go` отличается от той, что выдаёт `gofmt`, команда
  печатает имя этого файла. Сами файлы она не переписывает: это делает только
  флаг `-w`. Пустой вывод значит, что переформатировать нечего.
- `gofmt -w main.go` — правка. Если расстановка `main.go` отличается от
  стандартной, `gofmt` перезаписывает файл своей версией. Прежний текст файла
  при этом не сохраняется.

Программа ниже создаёт проект из двух файлов: `go.mod` с модулем `hello-gofmt`
и `main.go`, записанный нарочно небрежно. В `main.go` нет ни одного отступа,
пробелы стоят где попало, а функция называется `tool_name`. В каталоге проекта
программа выполняет `gofmt -l .`, затем `gofmt -w main.go`, читает `main.go` и
ещё раз выполняет `gofmt -l .`. Текст `main.go` до форматирования записан в
программе, после — стоит в её выводе.

Прежде чем смотреть вывод, предскажите: что напечатает первый `gofmt -l .` и
что — последний?

```go

### Example: `01-gofmt`

Источник: `examples/01-gofmt/`

```go
// Программа создаёт во временном каталоге проект с неотформатированным
// main.go, выполняет в нём gofmt и печатает, что сообщила команда и каким
// стал файл.
package main

import (
	"errors"
	"fmt"
	"os"
	"os/exec"
	"path/filepath"
	"strings"
)

// goMod — файл go.mod подготовленного проекта.
const goMod = `module hello-gofmt

go 1.27
`

// mainSource — main.go до форматирования.
const mainSource = `package main

import   "fmt"

func   tool_name(name string)string{
return "инструмент: "+name
}

func main(){
fmt.Println(  tool_name( "gofmt" )  )
}
`

func main() {
	if err := show(); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}

// show создаёт проект, выполняет в нём команды и печатает результат.
func show() error {
	dir, err := os.MkdirTemp("", "gofmt-")
	if err != nil {
		return err
	}
	defer os.RemoveAll(dir)
	if err := os.WriteFile(filepath.Join(dir, "go.mod"), []byte(goMod), 0o644); err != nil {
		return err
	}
	mainPath := filepath.Join(dir, "main.go")
	if err := os.WriteFile(mainPath, []byte(mainSource), 0o644); err != nil {
		return err
	}

	out, _, err := run(dir, "gofmt", "-l", ".")
	if err != nil {
		return err
	}
	fmt.Println("gofmt -l . напечатала:", strings.TrimRight(out, "\n"))

	out, ok, err := run(dir, "gofmt", "-w", "main.go")
	if err != nil {
		return err
	}
	fmt.Println("gofmt -w main.go завершилась без ошибки —", ok)
	fmt.Println("gofmt -w main.go ничего не напечатала —", out == "")

	formatted, err := os.ReadFile(mainPath)
	if err != nil {
		return err
	}
	fmt.Println("main.go после gofmt:")
	fmt.Print(string(formatted))

	out, _, err = run(dir, "gofmt", "-l", ".")
	if err != nil {
		return err
	}
	fmt.Println("gofmt -l . после форматирования ничего не напечатала —", out == "")
	return nil
}

// run выполняет команду в каталоге dir и возвращает её вывод вместе с потоком
// ошибок и признак завершения с кодом 0. Ошибка возвращается, только если
// команду не удалось запустить.
func run(dir, name string, args ...string) (string, bool, error) {
	cmd := exec.Command(name, args...)
	cmd.Dir = dir
	out, err := cmd.CombinedOutput()
	var exitErr *exec.ExitError
	if errors.As(err, &exitErr) {
		return string(out), false, nil
	}
	if err != nil {
		return "", false, fmt.Errorf("не удалось запустить %s: %w", name, err)
	}
	return string(out), true, nil
}

```

Первый `gofmt -l .` назвал `main.go`: этот файл `gofmt` переписал бы. `go.mod` в
список не попал, потому что это не файл `.go`. `gofmt -w main.go` завершилась
без ошибки и ничего не напечатала, но файл изменился — его новый текст стоит в
выводе. Последний `gofmt -l .` не напечатал ничего: расстановка `main.go` теперь
стандартная.

Имя файла в выводе `gofmt -l` — не сообщение об ошибке и не отчёт о сделанной
работе. Это ответ на вопрос «какие файлы изменились бы при форматировании».
О самой правке `gofmt -w` в примере ничего не сообщила: результат виден только
в файле. Пустой список говорит только о расстановке. Делает ли программа то,
что нужно, `gofmt` не проверяет.

## Что gofmt меняет и чего не трогает

Сравните текст `main.go` в программе с текстом в выводе. Изменилась
расстановка:

- строки тела обеих функций получили отступ — одну табуляцию;
- после `import`, а также после `func` в объявлении `tool_name` осталось по
  одному пробелу вместо трёх;
- в объявлении `tool_name` появились пробелы перед типом результата `string` и
  перед `{`, в объявлении `main` — пробел между `()` и `{`;
- вокруг `+` появились пробелы;
- внутри скобок вызова `fmt.Println` лишние пробелы исчезли.

Не изменилось ни одно имя и ни один символ внутри кавычек:

- функция по-прежнему называется `tool_name`;
- строка `"инструмент: "` сохранила пробел после двоеточия, строка `"gofmt"`
  тоже осталась прежней;
- объявления стоят в прежнем порядке: сначала `tool_name`, потом `main`;
- в файле, как и до форматирования, одиннадцать строк.

Имя `tool_name` выбрано нарочно. По Effective Go имена из нескольких слов в Go
принято писать слитно, выделяя слова заглавной буквой: `toolName`, а не
`tool_name`. `gofmt` имя не исправил: переименование — не расстановка. Так же
пережили бы форматирование опечатка внутри кавычек и функция, которая
возвращает не ту строку. `gofmt` меняет вид записи, а не то, что программа
делает. Стиль имён и программы, которые его проверяют, разбирает урок 11.12.

В этом файле `gofmt` поменял только отступы и пробелы. На других файлах он
может сделать и другие правки; списки выше описывают только этот файл.

В своём модуле порядок тот же. `gofmt -l .` в каталоге модуля показывает,
какие файлы изменились бы. `gofmt -w` с именем файла переписывает этот файл на
месте, поэтому результат смотрят уже в самом файле. Повторный `gofmt -l .` с
пустым выводом подтверждает, что переписывать больше нечего.

## go vet: замечание о программе, которую компилятор принял

Компилятор проверяет, соблюдены ли правила языка. Но программа может соблюдать
все правила и всё равно делать не то, что задумал её автор. Часть таких мест
видна уже по исходному тексту. **Статическая проверка** — проверка исходного
текста без запуска программы. Такую проверку выполняет `go vet` — отдельная
команда тулчейна из урока 1.1. По документации она сообщает о подозрительных
конструкциях, например о вызовах `Printf`, в которых аргументы не согласуются с
форматной строкой. Так она находит ошибки, которых не ловит компилятор. Если
команда сообщила о проблеме, она завершается ненулевым кодом.

Вспомните правило урока 1.9: каждый глагол `%s` в форматной строке по порядку
подставляет следующий строковый аргумент. Значит, строке `"%s %s\n"` нужны два
строковых аргумента.

Программа ниже создаёт проект с модулем `hello-vet`. В его `main.go` функция
`main` делает один вызов: `fmt.Printf("%s %s\n", "один")`. Глаголов `%s` два, а
строковый аргумент один. В каталоге проекта программа выполняет `go run .`,
затем `go vet .`.

Прежде чем смотреть вывод, предскажите: соберёт ли `go run .` эту программу и
что окажется в напечатанной строке на месте второго `%s`?

```go

### Example: `02-go-vet`

Источник: `examples/02-go-vet/`

// больше, чем аргументов, выполняет в нём go run и go vet и печатает, что
// сообщили команды.
package main

import (
	"errors"
	"fmt"
	"os"
	"os/exec"
	"path/filepath"
	"strings"
)

// goMod — файл go.mod подготовленного проекта.
const goMod = `module hello-vet

go 1.27
`

// mainSource — main.go: два глагола %s и один строковый аргумент.
const mainSource = `package main

import "fmt"

func main() {
	fmt.Printf("%s %s\n", "один")
}
`

func main() {
	if err := show(); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}

// show создаёт проект, выполняет в нём команды и печатает результат.

	dir, err := os.MkdirTemp("", "vet-")

	}
	defer os.RemoveAll(dir)
	if err := os.WriteFile(filepath.Join(dir, "go.mod"), []byte(goMod), 0o644); err != nil {
		return err
	}
	if err := os.WriteFile(filepath.Join(dir, "main.go"), []byte(mainSource), 0o644); err != nil {
		return err
	}

	if err != nil {
		return err
	}

		return err
	}
	fmt.Println("go vet . завершилась ненулевым кодом —", !ok)
	fmt.Println("go vet . напечатала:")
	fmt.Print(out)
	return nil
}

```

`go run .` завершилась без ошибки: компилятор принял программу, и она
выполнилась. Напечатано `один %!s(MISSING)`. Первый `%s` получил аргумент
`"один"`, второму аргумента не досталось. Пакет `fmt` отметил это прямо в
напечатанной строке: по его документации пометка `%!s(MISSING)` означает, что
для глагола `%s` не хватило аргумента. Компилятор такой вызов не
останавливает: число глаголов в форматной строке он с числом аргументов не
сверяет.

`go vet .` завершилась ненулевым кодом и напечатала одну строку. Её читают по
частям, разделённым двоеточиями:

- `main.go` — файл, о котором замечание;
- `6` — номер строки в этом файле; шестая строка `main.go` — как раз вызов
  `fmt.Printf`;
- `17` — позиция внутри этой строки, к которой относится замечание;
- дальше идёт текст замечания. Начало `fmt.Printf format %s` говорит о глаголе
  `%s` в форматной строке вызова `fmt.Printf`. Продолжение
  `reads arg #2, but call has 1 arg` значит: глагол читает аргумент № 2, а в
  вызове один аргумент.

Замечание называет ту же нехватку, которую вы нашли по правилу урока 1.9.
Разница в том, когда и как её увидели. `fmt` обнаружил нехватку во время
выполнения и напечатал пометку вместе с результатом. `go vet` нашла её по
исходному тексту, без запуска программы, и указала файл и строку.

## Отказ компилятора и замечание vet

Сообщение компилятора и замечание `go vet` похожи на вид: файл, строка,
позиция, текст. Различают их по тому, какая команда напечатала строку и
собралась ли программа. От этого зависит следующий шаг.

**Отказ компилятора.** В уроке 1.1 программа импортировала пакет и не
пользовалась им. Неиспользованный импорт нарушает правило языка, поэтому
компилятор программу не собирает: исполняемого файла нет, запускать нечего.
Пока строку не исправить, программа не заработает вовсе.

**Замечание `go vet`.** Программа с лишним `%s` правил языка не нарушает.
Компилятор её собрал, она выполнилась и напечатала строку с пометкой. `go vet`
запускают отдельно от сборки, и её замечание ничего не отменяет: программа уже
была собрана и выполнена. Ненулевой код `go vet` означает, что команда нашла, о
чём сообщить. Это повод открыть названную строку и решить, что исправить. В
примере можно добавить второй строковый аргумент или убрать лишний `%s`.

У обеих реакций есть граница. Программа, которую компилятор принял, не
обязательно верна — это вывод урока 1.1. Молчание `go vet` тоже не
доказательство. По документации её сообщения — подсказка, а не твёрдый признак
правильности программы, и находит она не все ошибки. Программа, которая
аккуратно печатает не тот текст, может пройти и компилятор, и `go vet`.

## Комментарий, который становится документацией

Чтобы вызвать функцию чужого пакета, нужно знать, что она делает, — лучше без
чтения её тела. Такое описание в Go пишут прямо в исходниках, комментариями
перед объявлениями.

**Документирующий комментарий** — комментарий из строк, начинающихся с `//`,
который стоит непосредственно перед объявлением на уровне файла или перед
предложением `package`. Объявление на уровне файла — это, например, объявление
функции из урока 1.7. По документации Go между таким комментарием и объявлением
нет пустой строки. Комментарий перед функцией описывает эту функцию, и начинать
его принято с имени объявленного: перед объявлением `Greeting` стоит
комментарий, который начинается словом `Greeting`. Комментарий перед
предложением `package` описывает пакет целиком.

Пример следующего раздела показывает документацию проекта с модулем
`example.com/profile`. Функции в нём те же, что в пакетах `profile` и `label`
урока 1.8, с теми же телами. Разложены файлы иначе, и путь модуля другой:

- `go.mod` лежит в корне проекта, путь модуля — `example.com/profile`;
- `profile.go` тоже лежит в корне: это пакет `profile` с функциями `Greeting` и
  `Card`; файл `profile.go` импортирует подпакет по пути
  `example.com/profile/label`, а функция `Card` вызывает `label.Label`;
- `label/label.go` — пакет `label` с функцией `Label`.

Путь подпакета составлен по правилу урока 1.8: путь модуля плюс каталог
`label`.

Тела функций не изменились. Добавлены пять документирующих комментариев:

- перед предложением `package` в `profile.go` — о том, что пакет собирает
  строки карточки;
- перед объявлением `Greeting` — комментарий, который начинается словом
  `Greeting` и говорит, что функция возвращает приветствие для имени `name`;
- перед объявлением `Card` — `// Card возвращает приветствие вместе с меткой роли.`;
- перед предложением `package` в `label/label.go` — о том, что пакет оформляет
  роль как метку;
- перед объявлением `Label` — `// Label возвращает role в квадратных скобках.`.

Все пять стоят вплотную к своему объявлению или предложению `package`. Их точный
текст виден в программе примера следующего раздела: она записывает файлы
проекта.

Прежде чем смотреть вывод следующего раздела, решите: какой из пяти
комментариев напечатает команда, которая спрашивает только о функции
`Greeting`?

## go doc: документация из исходников

`go doc` печатает документацию, собранную из исходников. Что именно показать,
задаёт аргумент команды. В примере используются три формы:

- `go doc .` — пакет из текущего каталога;
- `go doc Greeting` — одно имя из пакета, здесь функция. По документации
  команды аргумент, который начинается с заглавной буквы, она ищет как имя в
  пакете текущего каталога;
- `go doc example.com/profile/label` — пакет по полному пути импорта из урока
  1.8. Так можно спросить о подпакете, не переходя в его каталог.

Программа ниже записывает проект из предыдущего раздела во временный каталог.
Сначала она выполняет `go build ./...`. Шаблон `./...` означает текущий каталог
и все каталоги ниже, поэтому команда собирает оба пакета — `profile` и `label`.
Раз сборка прошла, компилятор принял оба пакета, а подпакет нашёлся по пути
импорта `example.com/profile/label`. Затем программа выполняет из корня
проекта три команды `go doc` и печатает вывод каждой целиком.

```go

Источник: `examples/03-go-doc/`

// Программа создаёт во временном каталоге проект из пакета profile и
// подпакета label с документирующими комментариями, собирает его и печатает
// вывод трёх команд go doc.
package main

import (
	"errors"
	"fmt"
	"os"
	"os/exec"
	"path/filepath"
	"strings"
)

// goMod — файл go.mod подготовленного проекта.
const goMod = `module example.com/profile

go 1.27
`

// profileSource — profile.go в корне проекта.
const profileSource = `// Пакет profile собирает строки карточки: приветствие и метку роли.
package profile

import "example.com/profile/label"

// Greeting возвращает приветствие для имени name.
func Greeting(name string) string {
	return "Здравствуйте, " + name
}

// Card возвращает приветствие вместе с меткой роли.
func Card(name, role string) string {
	return Greeting(name) + " " + label.Label(role)
}
`

// labelSource — label/label.go в подкаталоге label.
const labelSource = `// Пакет label оформляет роль как метку в квадратных скобках.
package label

// Label возвращает role в квадратных скобках.
func Label(role string) string {
	return "[" + role + "]"
}
`

func main() {
	if err := show(); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}

// show создаёт проект, выполняет в нём команды и печатает результат.
func show() error {
	dir, err := os.MkdirTemp("", "doc-")
	if err != nil {
		return err
	}
	defer os.RemoveAll(dir)
	files := [][2]string{
		{"go.mod", goMod},
		{"profile.go", profileSource},
		{"label/label.go", labelSource},
	}
	for _, file := range files {
		if err := write(dir, file[0], file[1]); err != nil {
			return err
		}
	}

	_, ok, err := run(dir, "go", "build", "./...")
	if err != nil {
		return err
	}
	fmt.Println("go build ./... завершилась без ошибки —", ok)

	commands := [][]string{
		{"doc", "."},
		{"doc", "Greeting"},
		{"doc", "example.com/profile/label"},
	}
	for _, args := range commands {
		out, _, err := run(dir, "go", args...)
		if err != nil {
			return err
		}
		fmt.Println("go", strings.Join(args, " "), "напечатала:")
		fmt.Print(out)
	}
	return nil
}

// write создаёт файл name с текстом text внутри каталога dir вместе с
// недостающими каталогами.
func write(dir, name, text string) error {
	path := filepath.Join(dir, filepath.FromSlash(name))
	if err := os.MkdirAll(filepath.Dir(path), 0o755); err != nil {
		return err
	}
	return os.WriteFile(path, []byte(text), 0o644)
}

// run выполняет команду в каталоге dir и возвращает её вывод вместе с потоком
// ошибок и признак завершения с кодом 0. Ошибка возвращается, только если
// команду не удалось запустить.
func run(dir, name string, args ...string) (string, bool, error) {
	cmd := exec.Command(name, args...)
	cmd.Dir = dir
	out, err := cmd.CombinedOutput()
	var exitErr *exec.ExitError
	if errors.As(err, &exitErr) {
		return string(out), false, nil
	}
	if err != nil {
		return "", false, fmt.Errorf("не удалось запустить %s: %w", name, err)
	}
	return string(out), true, nil
}

Вывод `go doc .` читается сверху вниз. Первая строка называет пакет `profile`, а
после `// import` — путь, по которому этот пакет импортируют. Дальше идёт текст
комментария, стоявшего перед предложением `package`, уже без `//`. Последние
строки — объявления функций пакета без тел, по строке на функцию. Комментариев
к функциям здесь нет. В этом выводе `Card` стоит перед `Greeting`, хотя в
`profile.go` первой объявлена `Greeting`: объявления перечислены по алфавиту.

Вывод `go doc Greeting` рассказывает об одном имени. После той же первой строки
идёт объявление `Greeting` без тела, а под ним, с отступом, — текст
комментария, стоявшего перед этим объявлением. Комментарий к `Card` сюда не
попал: он относится к другому объявлению.

Вывод `go doc example.com/profile/label` устроен так же, как вывод `go doc .`,
но для подпакета. Первая строка называет пакет `label` и его путь импорта
`example.com/profile/label`. Дальше идут комментарий из `label/label.go` и
объявление `Label`. Команда выполнялась из корня проекта, а не из каталога
`label`: пакет нашёлся по полному пути импорта.

Объявления в выводе читаются как в уроке 1.7: имя функции, параметры в скобках,
тип результата. У `Card` параметры `name` и `role` записаны через запятую с
общим типом `string` — это сокращённая запись из того же урока.

Весь напечатанный текст взят из исходников: объявления — из кода, пояснения — из
документирующих комментариев. В проекте примера нет ничего, кроме `go.mod` и
двух файлов `.go`, и весь вывод собран из них. Поэтому, если пояснение в выводе `go doc` неточное, исправляют комментарий перед
объявлением в исходнике.

# Проверочные вопросы

## Вопрос 1

В проекте из примера `01-gofmt` функция в `main.go` называется `tool_name`,
хотя в Go принято писать `toolName`. Вы выполнили в каталоге проекта
`gofmt -w main.go`. Что стало с именем функции?

Варианты ответа:

- A. Осталось `tool_name`: `gofmt` меняет отступы и пробелы, а имена в файле не
  переписывает.
- B. Стало `toolName`: `gofmt` приводит к стилю Go и расстановку, и имена
  функций.
- C. Осталось `tool_name`, а файл не отформатирован: `gofmt` не правит файл,
  пока в нём есть имя не в стиле Go.

Прежде чем смотреть ответ, назовите, что именно `gofmt` поменял в `main.go`
этого примера.

**Правильный ответ: A.**

Вариант B считает форматирование проверкой стиля вообще, но в примере урока
после `gofmt -w` имя осталось `tool_name`. Вариант C приписывает `gofmt` отказ
из-за имени, а в примере файл с этим именем получил отступы и пробелы, и
повторный `gofmt -l .` его уже не назвал.

## Вопрос 2

В каталоге проекта лежат `go.mod`, `main.go` и `names.go`. Вы выполнили
`gofmt -l .`, и команда напечатала одну строку: `names.go`. Что это значит?

Варианты ответа:

- A. Расстановка в `names.go` отличается от стандартной; после
  `gofmt -w names.go` повторный `gofmt -l .` этот файл не назовёт.
- B. В `names.go` ошибка, из-за которой файл не соберётся; `gofmt -l` называет
  файлы, которые нужно исправить вручную.
- C. `gofmt` только что переформатировал `names.go`; флаг `-l` сообщает, какие
  файлы команда изменила.

Прежде чем смотреть ответ, объясните, чем флаг `-l` отличается от флага `-w`.

**Правильный ответ: A.**

Вариант B читает список как сообщение об ошибке, но в примере урока
`gofmt -l .` назвал файл `main.go`, который затем без ошибки переписала команда
`gofmt -w`.
Вариант C путает проверку с правкой: файлы перезаписывает только `-w`, а `-l`
лишь называет те, что изменились бы.

## Вопрос 3

В `main.go` проекта функция `main` делает один вызов:
`fmt.Printf("%s %s\n", "один")`. Других ошибок в файле нет. Вы выполняете в
каталоге проекта `go run .`, а затем `go vet .`. Что произойдёт?

Варианты ответа:

- A. `go run .` соберёт и запустит программу; `go vet .` напечатает замечание
  о вызове `Printf` и завершится ненулевым кодом.
- B. `go run .` откажется собирать программу, как при неиспользованном
  импорте; до запуска дело не дойдёт.
- C. `go run .` запустит программу, а `go vet .` — это сборка компилятором с
  замечаниями: после её замечания программа больше не соберётся.
- D. Обе команды завершатся без замечаний: аргументов меньше, чем глаголов, и
  второй `%s` просто ничего не напечатает.

Прежде чем смотреть ответ, объясните, какая из двух команд проверяет правила
языка при сборке, а какая ищет подозрительные места в уже принятой программе.

**Правильный ответ: A.**

Вариант B переносит отказ компилятора на всё подозрительное, но нехватка
аргумента правила языка не нарушает, и в примере урока `go run .` завершилась
без ошибки. Вариант C считает `go vet` частью сборки, а это отдельная команда:
её замечание ничего не собирает и сборку не останавливает. Вариант D ошибается
дважды: второй глагол не пропадает молча — программа напечатала
`один %!s(MISSING)`, а `go vet .` сообщила о вызове и завершилась ненулевым
кодом. Неиспользованный импорт, в отличие от этого
случая, ловит компилятор, и программа не собирается (урок 1.1).

## Вопрос 4

В корне проекта с модулем `example.com/profile` из примера `03-go-doc` вы
выполнили `go doc Greeting`. Под объявлением функции напечатан текст о том, что
она возвращает приветствие для имени. Откуда `go doc` взял этот текст?

Варианты ответа:

- A. Из комментария `//`, который стоит в `profile.go` непосредственно перед
  объявлением `Greeting` и начинается с её имени.
- B. Из отдельного файла документации, который автор пишет рядом с исходниками
  и который `go doc` находит по имени пакета.
- C. С сайта документации Go: `go doc` загружает описание пакета из сети и без
  сети ничего не напечатает.

Прежде чем смотреть ответ, назовите место в исходнике, откуда берётся
пояснение к одной функции. Затем, оставаясь в корне проекта, назовите команду,
которая напечатает документацию: (1) всего пакета `profile`; (2) только функции
`Greeting`; (3) подпакета `label`, не переходя в его каталог.

**Правильный ответ: A.**

Вариант B ищет документацию отдельно от кода, но в проекте примера, кроме
`go.mod`, лежат только два файла `.go`, и напечатанный текст совпал с
комментарием перед `Greeting`. Вариант C ищет текст в сети, но всё, что
напечатал `go doc` в примере урока, уже было в исходниках проекта: объявления —
в коде, пояснения — в комментариях.

Команды из корня проекта: (1) `go doc .` — точка означает текущий каталог, а в
корне лежит пакет `profile`; (2) `go doc Greeting` — по документации команды
аргумент с заглавной буквы она ищет как имя в пакете текущего каталога;
(3) `go doc example.com/profile/label` — подпакет называют полным путём
импорта. По правилу урока 1.8 этот путь складывается из пути модуля и каталога
`label`; по нему же подпакет импортирует `profile.go`.
