# AI-конспект урока

## Инструкция для нейросети

Ты получаешь материалы одного урока курса по Go.

Твоя задача — **не пересказать исходный материал целиком**, а подготовить
компактный, точный конспект, по которому студент сможет:

1. понять основные концепции урока;
2. вспомнить синтаксис и правила Go, которые здесь изучаются;
3. ответить на проверочные вопросы из раздела «Проверочные вопросы»;
4. решить типовые практические задачи по этой теме;
5. не перепутать похожие понятия и исключения.

### Правила подготовки ответа

- Сохраняй техническую точность.
- Не выкидывай правила, которые могут быть проверены в quiz.
- Особое внимание уделяй причинам: **почему ответ правильный**, а остальные
  варианты неправильны.
- Если в quiz есть конкретный сценарий, команду, код или вывод программы —
  обязательно объясни соответствующее правило.
- Не пересказывай очевидные вводные фразы и организационную информацию.
- Не добавляй информацию, которой нет в предоставленных материалах, если она
  не нужна для объяснения приведённого материала.
- Код из примеров используй как источник конкретных правил и поведения Go.
- Не нужно разбирать каждую строку примера, если это не помогает ответить
  на вопрос quiz.
- Сохраняй названия команд, функций, типов, операторов и других сущностей
  точно.
- Если есть важное исключение или типичная ошибка — вынеси её отдельно.

# Сборка: go build и go install

Представьте: вы написали небольшую программу и хотите отдать её коллеге, у
которого Go не установлен. В примерах урока 1.2 вы видели команду
`go run .`. Она собирает исполняемый файл во временном каталоге, запускает его
и удаляет каталог, поэтому в проекте файла не остаётся. Передать коллеге
нечего. А из урока 1.1 вы знаете, что на другом компьютере запускают именно
исполняемый файл, собранный для пары «система + архитектура» этого компьютера.
Если выполнены и остальные условия урока 1.1, ставить Go на тот компьютер не
нужно.

Чтобы исполняемый файл (в разговоре его называют бинарником) остался на диске,
нужны другие команды. `go build` кладёт файл в текущий каталог. `go build -o`
кладёт его по пути, который вы назвали. `go install` кладёт его в каталог
`GOBIN`. Переменные `GOOS` и `GOARCH` выбирают, для какой
системы файл собирается.

Код писать не нужно. Примеры урока — программы курса: каждая создаёт во
временном каталоге один и тот же маленький проект, выполняет в нём команду
`go`, печатает списки файлов до и после команды и удаляет каталог. Читать
нужно командную строку и вывод, а не код самих программ.

## Проект `hello-build`

Все четыре примера собирают один и тот же подготовленный модуль с путём
`hello-build`. В нём два файла, и ниже приведено их точное содержимое.

Файл `go.mod` — две директивы из урока 1.4: `module` с путём модуля и `go` с
версией языка этого модуля. Строки файла по порядку:

1. `module hello-build`
2. пустая строка
3. `go 1.27`

Файл `main.go` — запускаемая программа, устроенная как в уроке 1.3; она
печатает одну строку. Строки файла по порядку:

1. `package main`
2. пустая строка
3. `import "fmt"`
4. пустая строка
5. `func main() {`
6. `fmt.Println("привет из собранного файла")` с отступом в начале строки
7. `}`

Чужих модулей проект не использует и написан на чистом Go, без cgo. Без чужих
модулей сборке этого проекта нечего загружать. Без cgo его можно собрать для
другой системы тем же тулчейном (раздел «Сборка для другой системы»).

## `go build`: файл в текущем каталоге

`go build` без аргументов собирает пакет текущего каталога. Если это пакет
`main`, команда записывает исполняемый файл в текущий каталог. В этом её
отличие от `go run .`: та тоже собирает файл, но во временном каталоге, сразу
запускает его и удаляет каталог, так что в проекте ничего не прибавляется.
`go build` файл оставляет, а программу не запускает. Имя файла она
берёт из последнего элемента пути импорта пакета. Пакет в корне модуля
`hello-build` имеет путь импорта `hello-build` (урок 1.4), поэтому файл
называется `hello-build`. Для пакета в корне модуля `example.com/notes` из урока
1.4 файл назывался бы `notes`. Имя каталога, в котором лежит проект, на имя
файла не влияет.

Имя зависит и от цели сборки. Когда команда пишет исполняемый файл для
Windows, она добавляет к имени `.exe`. Поэтому в Linux и macOS получится
`hello-build`, а в Windows, по документации команды `go`, обычный `go build`
даст `hello-build.exe`.

Успешная сборка проекта `hello-build` ничего не печатает. Тишина не значит, что
ничего не произошло: результат команды — появившийся файл, а не сообщение.
Если в коде ошибка, команда печатает сообщение компилятора и файла не создаёт,
как это делала `go run .` в уроке 1.2. Проект, которому нужны чужие модули,
при сборке может сообщать об их загрузке; такие проекты разбирает урок 11.6.

Готовый файл запускают отдельно, как любую программу. По документации это
делают так: в Linux и macOS `./hello-build` из каталога проекта, в
Windows `hello-build.exe`. Этот же файл можно скопировать на другой компьютер и
запустить там без Go, если выполнены условия урока 1.1, среди них —
совпадающая пара «система + архитектура» и поддерживаемая версия системы.

Программа ниже создаёт проект `hello-build` и печатает список файлов в его
каталоге. Затем она выполняет там `go build` и проверяет две вещи: завершилась
ли команда без ошибки и напечатала ли она хоть что-нибудь, в том числе в поток
ошибок. После этого программа снова печатает список файлов и запускает
появившийся файл напрямую, без `go run`.

### Example: `01-go-build`

Источник: `examples/01-go-build/`

```go
// Программа создаёт во временном каталоге проект hello-build, выполняет в его
// корне go build без флагов и запускает появившийся файл.
package main

import (
	"fmt"
	"os"
	"os/exec"
	"path/filepath"
	"strings"
)

// goMod — содержимое файла go.mod проекта.
const goMod = "module hello-build\n\ngo 1.27\n"

// mainGo — содержимое файла main.go проекта.
const mainGo = `package main

import "fmt"

func main() {
	fmt.Println("привет из собранного файла")
}
`

// writeProject создаёт временный каталог с файлами go.mod и main.go и
// возвращает его путь.
func writeProject() (string, error) {
	dir, err := os.MkdirTemp("", "project-")
	if err != nil {
		return "", err
	}
	if err := os.WriteFile(filepath.Join(dir, "go.mod"), []byte(goMod), 0o644); err != nil {
		os.RemoveAll(dir)
		return "", err
	}
	if err := os.WriteFile(filepath.Join(dir, "main.go"), []byte(mainGo), 0o644); err != nil {
		os.RemoveAll(dir)
		return "", err
	}
	return dir, nil
}

// listDir возвращает имена из каталога dir через запятую, а для пустого
// каталога — слово «(пусто)».
func listDir(dir string) (string, error) {
	entries, err := os.ReadDir(dir)
	if err != nil {
		return "", err
	}
	if len(entries) == 0 {
		return "(пусто)", nil
	}
	names := make([]string, 0, len(entries))
	for _, entry := range entries {
		names = append(names, entry.Name())
	}
	return strings.Join(names, ", "), nil
}

// goCommand выполняет команду go с аргументами args в каталоге dir и
// возвращает её стандартный вывод и поток ошибок вместе.
func goCommand(dir string, args ...string) ([]byte, error) {
	command := exec.Command("go", args...)
	command.Dir = dir
	// Одинаковые условия запуска на любой машине.
	command.Env = append(os.Environ(), "GOWORK=off", "GOTOOLCHAIN=local")
	return command.CombinedOutput()
}

// run выполняет пример и удаляет временный каталог перед возвратом.
func run() error {
	dir, err := writeProject()
	if err != nil {
		return err
	}
	defer os.RemoveAll(dir)

	before, err := listDir(dir)
	if err != nil {
		return err
	}
	fmt.Println("в каталоге проекта до команды:", before)

	output, err := goCommand(dir, "build")
	fmt.Println("go build завершилась без ошибки —", err == nil)
	fmt.Println("go build ничего не напечатала —", len(output) == 0)
	if err != nil {
		return fmt.Errorf("go build не выполнилась: %w: %s", err, output)
	}

	after, err := listDir(dir)
	if err != nil {
		return err
	}
	fmt.Println("в каталоге проекта после команды:", after)

	// Собранный файл запускается напрямую, без go run.
	printed, err := exec.Command(filepath.Join(dir, "hello-build")).Output()
	if err != nil {
		return fmt.Errorf("собранный файл не запустился: %w", err)
	}
	fmt.Print("собранный файл напечатал: ", string(printed))
	return nil
}

func main() {
	// Выход с ошибкой — только здесь, после того как run удалила каталог.
	if err := run(); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}

```

До команды в каталоге два файла, после команды — три: добавился `hello-build`.
Программа печатает имена по алфавиту, поэтому новый файл стоит между `go.mod` и
`main.go`. Сама `go build` не напечатала ни строки. Последняя строка вывода —
то, что напечатал собранный файл, когда программа примера его запустила.
Временный каталог назывался не `hello-build`, а файл всё равно получил имя по

Если повторяете команды у себя, выполните в каталоге проекта `go build`.
Убедитесь, что в каталоге появился файл `hello-build` (в Windows — `hello-build.exe`), и запустите его:
`./hello-build` в Linux и macOS, `hello-build.exe` в Windows.

## `go build -o`: имя и место файла

Файл не обязан лежать рядом с исходниками и называться по пути модуля. Флаг
`-o` задаёт путь, по которому `go build` запишет результат. Последний элемент
пути становится именем файла, а часть пути перед ним — каталогом.
`go build -o out/app` в корне модуля собирает тот же пакет текущего каталога и
записывает файл `app` в каталог `out`. Имя пакета `main` и путь модуля
`hello-build` на имя файла здесь не влияют: имя выбрали вы, когда писали
аргумент.

Это правило действует, когда каталога с именем последнего элемента пути нет.
В примере и в самопроверке ниже так и есть: в `out` нет каталога `app`, поэтому
`app` называет файл.

Программа ниже создаёт проект, добавляет в него пустой каталог `out` и печатает
содержимое проекта и каталога `out`. Затем она выполняет `go build -o out/app`
и снова печатает оба списка.

### Проверьте себя: `dist/card-app`

В корне того же модуля `hello-build` уже есть пустой каталог `dist`. Вы
выполняете `go build -o dist/card-app`. Прежде чем читать разбор, ответьте на
два вопроса. Какой файл и в каком каталоге появится? Запустит ли эта команда
программу?

**Разбор.** Появится файл `card-app` в каталоге `dist`. Каталог и имя выбрал
аргумент `-o`: последний элемент пути, `card-app`, стал именем файла, а `dist` —
каталогом. Путь модуля `hello-build` и имя пакета `main` на результат не
влияют, поэтому файла `hello-build` в корне проекта не появится. Программу
команда не запускает: `go build` только собирает файл. Строку программы
напечатает сам файл `dist/card-app`, когда его запустят отдельно.

Теперь в той же команде замените имя: `go build -o dist/hello-tool`. Назовите
файл и каталог, прежде чем читать разбор.

остались теми же, изменился только аргумент `-o` — и вместе с ним имя файла.

## Сборка для другой системы

Допустим, программа нужна на компьютере с Windows и процессором архитектуры
`amd64`, а собираете вы её в другой системе. Из урока 1.1 вы знаете, что
исполняемый файл собирается для одной пары «система + архитектура». Из урока
1.2 — что эту пару, цель сборки, задают переменные `GOOS` и `GOARCH`. По
умолчанию цель совпадает с системой тулчейна. Если задать `GOOS` или `GOARCH` в
окружении команды, цель меняется, а тулчейн остаётся тем же.

Сборку исполняемого файла для другой пары «система + архитектура», чем та, для
которой собран ваш тулчейн, называют **кросс-компиляцией**.

Чтобы выбрать пару, назовите систему и архитектуру компьютера, на котором файл
будет работать. Для Windows на `amd64` это `GOOS=windows` и `GOARCH=amd64`.
Задавайте обе переменные. Если задать только `GOOS`, архитектура останется
архитектурой тулчейна: тулчейн для `arm64` соберёт файл для `windows/arm64`.

Для программы на чистом Go, как `hello-build`, больше ничего не нужно: ни
компьютера с Windows, ни отдельного тулчейна. Условие «на чистом Go» здесь
важно: при кросс-компиляции cgo по умолчанию выключен, и программе, которой
нужен код на C, этого способа недостаточно.

Программа ниже создаёт свежий проект и выполняет в нём `go build` с
`GOOS=windows` и `GOARCH=amd64` в окружении команды. Затем она печатает список
файлов.

компьютер при этом остались прежними. Для этого подготовленного проекта на
чистом Go без чужих модулей хватило уже установленного подходящего тулчейна:
команда только собрала файл и записала его в каталог. Пример этот файл не
запускает: он собран для Windows, и запускать его нужно там.

Переименование не заменяет кросс-компиляцию. Допустим, вы собрали проект
обычной командой `go build` в Linux или macOS и дописали к имени `hello-build`
окончание `.exe`. Внутри файла остался машинный код для вашей системы: имя не
меняет того, для какой пары собран файл. Рассчитывать на его запуск в Windows
нельзя — пару файла выбирают при сборке (урок 1.1).

Если повторяете команды у себя, в терминале Linux и macOS цель задают перед
командой: `GOOS=windows GOARCH=amd64 go build`. В «командной строке» Windows, по
документации, переменные задают отдельными строками перед командой:
`set GOOS=windows`, затем `set GOARCH=amd64`, затем `go build`. Команда
`go env -w` для этого не подходит: она записывает настройку в файл настроек
пользователя, и настройка действует на все следующие команды `go`.

В Windows значение, заданное командой `set`, по документации Microsoft
действует в этом окне «командной строки» и для всех следующих команд. Поэтому
сборку для другой цели делайте в отдельном окне: откройте новое окно
«командной строки», перейдите в каталог проекта, выполните три строки выше, а
после сборки закройте это окно. Для раздела о `go install` откройте ещё одно
новое окно «командной строки» тем же способом. Не запускайте его командой из
окна, где собирали файл для Windows: такое окно получит те же переменные.
Перейдите в новом окне в каталог проекта.

## `go install`: файл в каталоге `GOBIN`

`go build` оставляет файл там, где вы работаете. Программу, которой вы
пользуетесь постоянно, удобнее держать в одном каталоге для своих
инструментов. Это делает `go install`. Без аргументов команда собирает пакет
`main` текущего каталога, как `go build`, и кладёт исполняемый файл в каталог,
названный переменной окружения `GOBIN`. Имя файла то же, что дал бы
`go build`, — `hello-build`. Каталог проекта при этом не меняется.

`GOBIN` задают абсолютным путём, то есть от корня файловой системы. Если
`GOBIN` не задан, по документации команды `go` файл попадает в каталог `go/bin`
в вашем домашнем каталоге, а если задана переменная `GOPATH`, — в каталог `bin`
внутри неё. В примере урока `GOBIN` задан явно, поэтому видно, куда лёг файл.

Проекту из примера ниже чужие модули не нужны, и установленного подходящего Go
для него хватает, поэтому `go install` только собирает файл и кладёт его в
`GOBIN`. Форма команды с путём и версией, которую урок 1.2 показывал для
установки `gopls`, скачивает чужую программу; здесь она не разбирается.

Программа ниже создаёт проект и отдельный пустой каталог для `GOBIN` и
печатает содержимое обоих. Затем она выполняет в проекте `go install`, указав в
окружении команды `GOBIN` на этот каталог, и снова печатает оба списка. Путь к
каталогу при каждом запуске свой, поэтому программа его не печатает, а называет
каталог словом `GOBIN`.

**Правильный ответ: A.**

`go run .` собирает файл во временном каталоге и удаляет его, а `go build`
записывает файл в текущий каталог под именем из пути модуля. Вариант B верно
описывает `go run .`, но в примере урока `go build` оставила `hello-build`
рядом с исходниками. Вариант C приписывает `go run .` постоянный файл, хотя она
удаляет временный каталог вместе с собранным файлом и каталог проекта не
меняет. Вариант D берёт имя из строки
`package`, но пакет каждой запускаемой программы называется `main`, а имя
файла дал путь модуля.

## Вопрос 4

Вы работаете в Linux или macOS. Программу `example.com/report` на чистом Go,
без cgo, нужно отдать коллеге: у него Windows на процессоре `amd64`. Компьютера
с Windows у вас нет. Как получить для коллеги исполняемый файл и как он будет
называться?

Варианты ответа:

- A. Выполнить в корне модуля `go build` с `GOOS=windows` и `GOARCH=amd64` в
  окружении команды; получится `report.exe`.
- B. Установить отдельный тулчейн Go для Windows или собрать на компьютере с
  Windows; своим тулчейном такой файл не получить.
- C. Выполнить обычный `go build` и переименовать `report` в `report.exe`;
  Windows узнает исполняемый файл по суффиксу.
- D. Выполнить в корне модуля `go build` с `GOHOSTOS=windows` в окружении
  команды; получится `report.exe`.

Прежде чем смотреть ответ, назовите переменные, которые описывают компьютер
коллеги, и объясните, почему имя файла не решает, для какой системы он собран.

**Правильный ответ: A.**

Цель сборки задают `GOOS` и `GOARCH`; программе на чистом Go хватает
установленного тулчейна, а суффикс `.exe` команда добавляет сама, когда пишет
файл для Windows. Вариант B считает кросс-компиляцию отдельно устанавливаемой
возможностью, но в примере урока тот же тулчейн собрал `hello-build.exe`.
Вариант C путает имя файла с его содержимым: после переименования внутри
остаётся машинный код вашей системы, а пару файла выбирают при сборке. Вариант
D путает цель с системой тулчейна: `GOHOSTOS` описывает систему, для которой
собран сам тулчейн, а цель задают `GOOS` и `GOARCH`. По документации команды
`go`, `GOHOSTOS` из окружения не читается, поэтому получился бы файл `report`
для вашей системы.
