Ты получаешь материалы одного урока курса по Go.

Твоя задача — **не пересказать исходный материал целиком**, а подготовить

1. понять основные концепции урока;

3. ответить на проверочные вопросы из раздела «Проверочные вопросы»;
4. решить типовые практические задачи по этой теме;
5. не перепутать похожие понятия и исключения.

### Правила подготовки ответа

- Сохраняй техническую точность.
- Не выкидывай правила, которые могут быть проверены в quiz.
- Особое внимание уделяй причинам: **почему ответ правильный**, а остальные
  варианты неправильны.
- Если в quiz есть конкретный сценарий, команду, код или вывод программы —
  обязательно объясни соответствующее правило.
- Не пересказывай очевидные вводные фразы и организационную информацию.
- Не добавляй информацию, которой нет в предоставленных материалах, если она
  не нужна для объяснения приведённого материала.
- Код из примеров используй как источник конкретных правил и поведения Go.
- Не нужно разбирать каждую строку примера, если это не помогает ответить
  на вопрос quiz.
- Сохраняй названия команд, функций, типов, операторов и других сущностей
  точно.
- Если есть важное исключение или типичная ошибка — вынеси её отдельно.

## Терминал, текущий каталог и команда

Команды набирают в **терминале** — программе, где вводят строку команды и
получают ответ текстом. В Linux и macOS для этого есть приложение терминала,
в Windows — командная строка или PowerShell.

В строке `go env GOOS GOARCH` первое слово, `go`, — имя запускаемой программы.
Остальные слова — **аргументы**, которые терминал передаёт программе: `env`
выбирает подкоманду, `GOOS` и `GOARCH` называют нужные настройки.

Программу `go` терминал находит через `PATH` — **переменную окружения**, то
есть именованное значение, которое запущенная программа получает от своего
окружения. В `PATH` записан список каталогов, и терминал запускает первую
программу с нужным именем из этих каталогов. Установка Go добавляет в `PATH`
свой каталог. Окно терминала, открытое до установки, этого не видит, поэтому
после установки открывают новое окно.

**Текущий каталог** — каталог, в котором выполняется команда. Команда `cd`, за
которой через пробел записан путь, делает текущим этот каталог. От текущего
каталога зависят, например, ответ `go env GOMOD` и работа `go run .`.

## Что ставится при установке

Установка кладёт на диск **дерево установки** — каталог с тулчейном. Путь к его
корню печатает `go env GOROOT`. Внутри различают два каталога.

1. **`bin`** — его добавляют в `PATH`. Оттуда вы запускаете по имени `go` и
   `gofmt`. Сборка, запуск, тесты и чтение настроек — подкоманды одной команды
   `go`. `gofmt` — отдельный инструмент форматирования, он в уроке 1.10.
2. **Каталог внутренних инструментов** — путь печатает `go env GOTOOLDIR`. Там
   лежат компилятор `compile`, компоновщик `link`, анализатор `vet` и другие.
   По имени их не запускают: к ним обращается команда `go`. Их список печатает
   `go tool` без аргументов.

Программа ниже спрашивает оба пути, ищет в каталогах имена программ и сверяет
их со списком `go tool`.

```go

### Example: `02-toolchain-on-disk`

Источник: `examples/02-toolchain-on-disk/`

```go
// Программа смотрит, что лежит в дереве установки Go: в каталоге bin, который
// добавляют в PATH, и в каталоге внутренних инструментов.
package main

import (
	"fmt"
	"os"
	"os/exec"
	"path/filepath"
	"runtime"
	"strings"
)

// goOut запускает команду go и возвращает её вывод без крайних пробелов.
func goOut(args ...string) string {
	out, err := exec.Command("go", args...).Output()
	if err != nil {
		fmt.Fprintln(os.Stderr, "go", args, "не выполнилась:", err)
		os.Exit(1)
	}
	return strings.TrimSpace(string(out))
}

// has отвечает, лежит ли в каталоге dir программа с именем name.
func has(dir, name string) bool {
	if runtime.GOOS == "windows" {
		name += ".exe"
	}
	_, err := os.Stat(filepath.Join(dir, name))
	return err == nil
}

func main() {
	bin := filepath.Join(goOut("env", "GOROOT"), "bin")
	tools := goOut("env", "GOTOOLDIR")
	listed := " " + strings.Join(strings.Fields(goOut("tool")), " ") + " "

	fmt.Println("в bin есть go и gofmt:", has(bin, "go") && has(bin, "gofmt"))
	fmt.Println("в bin нет compile и link:", !has(bin, "compile") && !has(bin, "link"))
	fmt.Println("GOTOOLDIR — другой каталог:", filepath.Clean(tools) != filepath.Clean(bin))
	fmt.Println("в GOTOOLDIR есть compile и link:", has(tools, "compile") && has(tools, "link"))
	fmt.Println("go tool называет compile, link и vet:",
		strings.Contains(listed, " compile ") && strings.Contains(listed, " link ") && strings.Contains(listed, " vet "))
	fmt.Println("gopls нет ни в bin, ни в GOTOOLDIR:", !has(bin, "gopls") && !has(tools, "gopls"))
}

```
```

Вы запускаете то, что лежит в `bin`; компилятор и компоновщик лежат отдельно;
`gopls` в дереве установки нет. Такой набор файлов — устройство стандартной
установки, документация Go его не обещает. Пакетные менеджеры и другие
способы установки могут класть файлы в другие места.

## Что показывает `go env`

Команда `go` работает по настройкам, а `go env` показывает их действующие
значения. Без аргументов она печатает все настройки в виде сценария оболочки,
в Windows — пакетного файла. С именами в аргументах печатает только значения,
по одному на строку, в порядке имён. Значение может прийти из переменной
окружения, файла настроек пользователя, файла в дереве установки или значения
по умолчанию, поэтому узнают его командой `go env ИМЯ`.

- `GOVERSION` — версия установленного дерева Go, начинается с `go1.`.
- `GOOS` и `GOARCH` — **цель сборки** из урока 1.1: система и архитектура, для
  которых команда `go` собирает программы. `GOHOSTOS` и `GOHOSTARCH` — система
  и архитектура, для которых собран сам установленный тулчейн; обычно они
  описывают ваш компьютер, и цель по умолчанию с ними совпадает. Если задать
  `GOOS` или `GOARCH` в окружении команды, `go env` покажет новую цель, а
  `GOHOSTOS` и `GOHOSTARCH` не изменятся: из окружения они не читаются.
  Допустимость пары `go env` не проверяет, неподдерживаемую пару отвергнет
  сборка.
- `GOMODCACHE` — каталог, где команда `go` хранит загруженные модули других
  авторов. Путь зависит от компьютера; подробности — в уроке 11.6.
- `GOMOD` — путь к `go.mod` текущего модуля, о нём следующий раздел.

Программа ниже спрашивает шесть значений, затем два в обратном порядке, затем
`GOOS` и `GOHOSTOS` с другой целевой системой в окружении.

```go

### Example: `01-go-env`

Источник: `examples/01-go-env/`

```go
// Программа спрашивает у команды go несколько настроек и печатает не сами
// значения (на каждом компьютере они свои), а проверки над ними.
package main

import (
	"fmt"
	"os"
	"os/exec"
	"path/filepath"
	"strings"
)

// goEnv запускает go env с именами и дополнительными переменными окружения.
func goEnv(extra []string, names ...string) []string {
	cmd := exec.Command("go", append([]string{"env"}, names...)...)
	cmd.Env = append(os.Environ(), extra...)
	out, err := cmd.Output()
	if err != nil {
		fmt.Fprintln(os.Stderr, "go env не выполнилась:", err)
		os.Exit(1)
	}
	return strings.Split(strings.TrimRight(string(out), "\r\n"), "\n")
}

func main() {
	v := goEnv(nil, "GOVERSION", "GOOS", "GOARCH", "GOHOSTOS", "GOHOSTARCH", "GOMODCACHE")
	fmt.Println("строк на шесть имён:", len(v))
	if len(v) != 6 {
		os.Exit(1)
	}
	goos, goarch, hostos, hostarch := v[1], v[2], v[3], v[4]
	fmt.Println("GOVERSION начинается с go1.:", strings.HasPrefix(v[0], "go1."))
	fmt.Println("GOMODCACHE — абсолютный путь:", filepath.IsAbs(v[5]))
	fmt.Println("цель сборки равна системе тулчейна:", goos == hostos && goarch == hostarch)

	back := goEnv(nil, "GOARCH", "GOOS")
	fmt.Println("имена в обратном порядке, значения тоже:", back[0] == goarch && back[1] == goos)

	// Цель выбирается заведомо отличной от системы тулчейна.
	target := "linux"
	if hostos == "linux" {
		target = "windows"
	}
	crossed := goEnv([]string{"GOOS=" + target}, "GOOS", "GOHOSTOS")
	fmt.Println("GOOS из окружения стала целью:", crossed[0] == target)
	fmt.Println("GOHOSTOS не изменилась:", crossed[1] == hostos)
}

## `GOMOD` и каталог, из которого запущена команда

Представьте проект магазина в каталоге `shop` с файлом `go.mod`. Такой каталог
со всем содержимым — **модуль**: единица, в которой команда `go` собирает
пакеты. Что записано в `go.mod`, разбирает урок 1.4. Модуль команда `go`
определяет сама, а `go env GOMOD` печатает путь к его `go.mod`.

Команда ищет `go.mod` в текущем каталоге, затем в родительском, затем выше и
берёт первый найденный. Из `shop` и из `shop/internal/store` ответ один:
`go.mod` в `shop`. Если в `shop/tools` лежит свой `go.mod`, это отдельный
модуль, в `shop` он не входит. Из `shop/tools` и `shop/tools/gen` ближайшим
окажется `go.mod` в `shop/tools`.

Если `go.mod` нет ни в текущем каталоге, ни выше, модуля нет. `go env GOMOD`
всё равно печатает значение, но не путь к `go.mod`, и какое — зависит от режима
и системы. По умолчанию команда `go` работает в **модульном режиме** — собирает
пакеты как части модулей, даже без `go.mod`. Тогда вне модуля `GOMOD` — имя
пустого устройства: `/dev/null` в Unix-подобных системах, `NUL` в Windows (по
документации команды `go`). Переменная окружения `GO111MODULE` управляет
режимом: `on` включает его явно, `off` выключает, и `GOMOD` пуст, а при `auto`
он пуст там, где `go.mod` не нашёлся. Поэтому вне модуля ждут не конкретное
значение, а признак: напечатанное значение — не путь к `go.mod`.

Программа ниже строит во временном каталоге проект `shop` с модулем
`shop/tools` и спрашивает `GOMOD` из разных мест в режимах `on` и `off`. Путей
она не печатает, а сравнивает ответ с созданными файлами.

```go

### Example: `04-gomod`

Источник: `examples/04-gomod/`

```go
// Программа строит во временном каталоге проект shop с вложенным модулем
// shop/tools и спрашивает go env GOMOD из разных каталогов. Вместо путей она
// печатает, на какой из созданных файлов go.mod указывает ответ.
package main

import (
	"fmt"
	"os"
	"os/exec"
	"path/filepath"
	"strings"
)

// gomod запускает go env GOMOD в каталоге dir; mode задаёт GO111MODULE.
func gomod(dir, mode string) string {
	cmd := exec.Command("go", "env", "GOMOD")
	cmd.Dir = dir
	cmd.Env = append(os.Environ(), "GO111MODULE="+mode)
	out, err := cmd.Output()
	if err != nil {
		fmt.Fprintln(os.Stderr, "go env GOMOD не выполнилась:", err)
		os.Exit(1)
	}
	return strings.TrimSpace(string(out))
}

// same отвечает, указывает ли напечатанный путь на файл file.
func same(printed, file string) bool {
	a, errA := os.Stat(printed)
	b, errB := os.Stat(file)
	return errA == nil && errB == nil && os.SameFile(a, b)
}

func main() {
	root, err := os.MkdirTemp("", "gomod-")
	if err != nil {
		fmt.Fprintln(os.Stderr, "не удалось создать каталог:", err)
		os.Exit(1)
	}
	defer os.RemoveAll(root)

	shop := filepath.Join(root, "shop")
	store := filepath.Join(shop, "internal", "store")
	tools := filepath.Join(shop, "tools")
	gen := filepath.Join(tools, "gen")
	os.MkdirAll(store, 0o755)
	os.MkdirAll(gen, 0o755)
	outer := filepath.Join(shop, "go.mod")
	nested := filepath.Join(tools, "go.mod")
	os.WriteFile(outer, []byte("module shop\n\ngo 1.27\n"), 0o644)
	os.WriteFile(nested, []byte("module shop/tools\n\ngo 1.27\n"), 0o644)

	fmt.Println("из shop — go.mod в shop:", same(gomod(shop, "on"), outer))
	fmt.Println("из shop/internal/store — go.mod в shop:", same(gomod(store, "on"), outer))
	fmt.Println("из shop/tools — go.mod в shop/tools:", same(gomod(tools, "on"), nested))
	fmt.Println("из shop/tools/gen — go.mod в shop/tools:", same(gomod(gen, "on"), nested))

	fmt.Println("вне модулей, режим on — имя пустого устройства:", gomod(root, "on") == os.DevNull)
	fmt.Println("вне модулей, режим off — пустая строка:", gomod(root, "off") == "")
	fmt.Println("из shop, режим off — пустая строка:", gomod(shop, "off") == "")
}

## Что проверяет `go version`

`go version` сообщает версию выбранного тулчейна и его пару
«система/архитектура». Сейчас команда печатает версию и пару одной строкой из
четырёх слов: `go`, `version`, версия, начинающаяся с `go1.`, и пара через
косую черту — например, `linux/arm64` или `windows/amd64`. Точный вид строки
документация не закрепляет, его задаёт текущая реализация команды `go`. Версия
и пара у каждого свои.

Успешный ответ значит: терминал нашёл `go` через `PATH`, команда запустилась и
сообщила версию выбранного тулчейна. Она ничего не компилирует, не запускает и
не тестирует. Документация Go не обещает, что после неё сборка пройдёт.

Почему «выбранного». В `go.mod` проекта может быть записано, что нужна версия
Go не ниже определённой. Если установленный тулчейн старше, внутри проекта всё
решает настройка `GOTOOLCHAIN`. При обычном `auto` команда `go` запускает нужный
тулчейн, при необходимости скачав его из сети, и `go version` сообщит его
версию. При `local` работает только установленный тулчейн: `go version`
печатает строку, а сборка отказывает.

Программа ниже разбирает строку `go version` в её нынешнем виде, который
документация не обещает, и сравнивает версию с `go env GOVERSION`. Затем она
создаёт проект, которому нужен Go 1.99, и выполняет в нём `go version` и
`go run .` с `GOTOOLCHAIN=local`.

```go

### Example: `03-go-version`

Источник: `examples/03-go-version/`

```go
// Программа запускает go version в каталоге примера, а затем в проекте,
// которому нужна версия Go 1.99, и печатает проверки. GOTOOLCHAIN=local
// оставляет в работе только установленный тулчейн.
package main

import (
	"fmt"
	"os"
	"os/exec"
	"path/filepath"
	"strings"
)

// run запускает команду go в каталоге dir и возвращает её общий вывод.
func run(dir string, args ...string) (string, error) {
	cmd := exec.Command("go", args...)
	cmd.Dir = dir
	cmd.Env = append(os.Environ(), "GOTOOLCHAIN=local")
	out, err := cmd.CombinedOutput()
	return strings.TrimSpace(string(out)), err
}

func main() {
	line, err := run("", "version")
	words := strings.Fields(line)
	fmt.Println("go version завершилась без ошибки:", err == nil)
	fmt.Println("одна строка из четырёх слов:", !strings.Contains(line, "\n") && len(words) == 4)
	if len(words) != 4 {
		os.Exit(1)
	}
	fmt.Println("первые два слова:", words[0], words[1])
	version, _ := run("", "env", "GOVERSION")
	fmt.Println("третье слово равно go env GOVERSION:", words[2] == version)
	fmt.Println("четвёртое слово — пара через косую черту:", strings.Count(words[3], "/") == 1)

	dir, err := os.MkdirTemp("", "go-version-")
	if err != nil {
		fmt.Fprintln(os.Stderr, "не удалось создать каталог:", err)
		os.Exit(1)
	}
	defer os.RemoveAll(dir)
	os.WriteFile(filepath.Join(dir, "go.mod"), []byte("module future\n\ngo 1.99\n"), 0o644)
	os.WriteFile(filepath.Join(dir, "main.go"), []byte("package main\n\nfunc main() {}\n"), 0o644)

	_, versionErr := run(dir, "version")
	out, runErr := run(dir, "run", ".")
	fmt.Println("в проекте для Go 1.99 go version без ошибки:", versionErr == nil)
	fmt.Println("там же go run . завершилась с ошибкой:", runErr != nil)
	fmt.Println("сообщение называет версию 1.99:", strings.Contains(out, "1.99"))
}

```
```

В одном каталоге `go version` прошла, а `go run .` отказала. `go version`
отвечает, какая команда `go` запускается и какой она версии. Собирается ли
проект, показывает только сборка.

## Редактор и `gopls`

Редактор подчёркивает необъявленное имя ещё до запуска, подсказывает имена и
переходит к объявлению функции. Эту работу для него выполняет `gopls` —
официальный **языковой сервер** Go: отдельная программа, которая разбирает код
проекта и отвечает редактору по протоколу языковых серверов (LSP). Запускает
его редактор; например, расширение Go для VS Code само устанавливает `gopls`,
а Go ставится отдельно. Вручную его ставят командой
`go install golang.org/x/tools/gopls@latest`, которой нужна сеть.

Зависимость направлена в одну сторону: чтобы узнать устройство проекта, `gopls`
вызывает команду `go`, например `go list`. Документация нигде не говорит, что
для `go build`, `go run` или `go test` нужен `gopls`. Без него редактор теряет
подсказки и подчёркивания, а сборка, запуск и тесты остаются командами
тулчейна.

Программа ниже оставляет в `PATH` только `bin` дерева установки, убеждается,
что `gopls` не находится, и в таком окружении собирает, запускает и тестирует
маленький пакет курса.

```go

### Example: `05-gopls`

Источник: `examples/05-gopls/`

```go
// Программа оставляет в PATH только каталог bin из дерева установки Go и в
// таком окружении собирает, запускает и тестирует соседний пакет subject.
package main

import (
	"fmt"
	"os"
	"os/exec"
	"path/filepath"
	"strings"
)

func main() {
	goroot, err := exec.Command("go", "env", "GOROOT").Output()
	if err != nil {
		fmt.Fprintln(os.Stderr, "go env GOROOT не выполнилась:", err)
		os.Exit(1)
	}
	os.Setenv("PATH", filepath.Join(strings.TrimSpace(string(goroot)), "bin"))
	_, lookErr := exec.LookPath("gopls")
	fmt.Println("gopls по имени не находится:", lookErr != nil)

	dir, err := os.MkdirTemp("", "gopls-")
	if err != nil {
		fmt.Fprintln(os.Stderr, "не удалось создать каталог:", err)
		os.Exit(1)
	}
	defer os.RemoveAll(dir)

	build := exec.Command("go", "build", "-o", filepath.Join(dir, "subject-program"), "./subject").Run()
	fmt.Println("go build завершилась без ошибки:", build == nil)

	out, runErr := exec.Command("go", "run", "./subject").Output()
	fmt.Println("go run завершилась без ошибки:", runErr == nil)
	fmt.Println("программа напечатала:", strings.TrimSpace(string(out)))

	test := exec.Command("go", "test", "-count=1", "-timeout=60s", "./subject").Run()
	fmt.Println("go test завершилась без ошибки:", test == nil)
}

```

«можно ли собирать и тестировать без языкового сервера» этого достаточно.

## Рабочий цикл: правка, `go run`, `go test`

Работа повторяет три шага: вы меняете исходный текст (как — урок 1.3),
запускаете программу командой `go run .` и тесты командой `go test`.

`go run .` компилирует пакет `main` из текущего каталога и сразу запускает
программу. Исполняемый файл собирается во временном рабочем каталоге, который
удаляется по завершении, поэтому в проекте файла не остаётся. Файл в текущем
каталоге оставляет `go build` — урок 1.5. Начиная с Go 1.24 `go run` ещё
сохраняет собранный файл в **кэше сборки** — каталоге, путь к которому
печатает `go env GOCACHE`; команда `go` переиспользует его содержимое в
следующих сборках и периодически чистит.

Текст после `go run .` печатают двое: ваша программа и команда `go`. Программа
пишет в **стандартный вывод** и в **поток ошибок** — два канала текста,
которые терминал показывает вместе. Команда `go` пишет свои сообщения в поток
ошибок. **Код завершения** — число, которым программа сообщает результат; `0` —
успех.

- **Ошибка компиляции.** Программа не запускалась: стандартный вывод пуст, в
  потоке ошибок — сообщение компилятора с файлом и номером строки.
- **Программа завершилась с кодом, например, `3`.** Напечатанное ею — её
  вывод. Строку `exit status 3` добавила команда `go`, а рядом в том же потоке
  ошибок могут стоять сообщения программы. Различают их по содержанию, а не по
  потоку: в текущем выводе число в строке `exit status 3` — код завершения
  программы. Сама `go run` завершается своим кодом: по документации он не
  совпадает с кодом программы, а текущая реализация возвращает `1`.

Программа ниже выполняет `go run .` в трёх маленьких проектах из `go.mod` и
`main.go` — исправном, с кодом 3 и с ошибкой компиляции — и разделяет потоки.

```go

### Example: `06-work-cycle`

Источник: `examples/06-work-cycle/`

```go
// Программа выполняет go run . в трёх маленьких проектах: исправном,
// завершающемся с кодом 3 и с ошибкой компиляции.
package main

import (
	"fmt"
	"os"
	"os/exec"
	"path/filepath"
	"strings"
)

// goRun создаёт проект из go.mod и main.go с телом функции main и выполняет в
// нём go run . Возвращает стандартный вывод, поток ошибок, код завершения
// go run и признак, что в проекте по-прежнему только эти два файла.
func goRun(body string) (string, string, int, bool) {
	dir, err := os.MkdirTemp("", "cycle-")
	if err != nil {
		panic(err)
	}
	defer os.RemoveAll(dir)
	os.WriteFile(filepath.Join(dir, "go.mod"), []byte("module cycle\n\ngo 1.27\n"), 0o644)
	src := "package main\n\nimport (\"fmt\"; \"os\")\n\nfunc main() {\n" + body + "\n}\n"
	os.WriteFile(filepath.Join(dir, "main.go"), []byte(src), 0o644)

	var stdout, stderr strings.Builder
	cmd := exec.Command("go", "run", ".")
	cmd.Dir, cmd.Stdout, cmd.Stderr = dir, &stdout, &stderr
	cmd.Run()
	files, _ := os.ReadDir(dir)
	return stdout.String(), stderr.String(), cmd.ProcessState.ExitCode(), len(files) == 2
}

func main() {
	out, _, code, same := goRun(`fmt.Fprintln(os.Stdout, "отчёт готов")`)
	fmt.Println("1. исправный проект — код go run:", code, "| в проекте только go.mod и main.go:", same)
	fmt.Print("   стандартный вывод: ", out)

	out, errs, code, _ := goRun(`fmt.Println("обработано записей: 2")
	fmt.Fprintln(os.Stderr, "файл настроек не найден")
	os.Exit(3)`)
	fmt.Print("2. программа с кодом 3 — стандартный вывод: ", out)
	fmt.Println("   в потоке ошибок строка программы:", strings.Contains(errs, "файл настроек не найден"),
		"| строка exit status 3:", strings.Contains(errs, "exit status 3"))
	fmt.Println("   код go run не 0 и не 3:", code != 0 && code != 3)

	out, errs, code, same = goRun(`fmt.Fprintln(os.Stdout, undefinedName)`)
	fmt.Println("3. ошибка компиляции — код go run не 0:", code != 0, "| стандартный вывод пуст:", out == "")
	fmt.Println("   в потоке ошибок место в main.go:", strings.Contains(errs, "main.go"),
		"| в проекте только go.mod и main.go:", same)
}

```
```

## Что печатает `go test`

**Тест** — функция, которая вызывает код проекта и сообщает об ошибке, если
результат не совпал с ожидаемым. `go test` выполняет тесты пакета и печатает
итог. Как писать тесты, разбирает урок 1.12.

По документации итог по пакету — строка со статусом `ok` или `FAIL`, путём
пакета и временем прогона. У прошедшего пакета печатается только эта строка, у
провалившегося — ещё и полный вывод его тестов. Сейчас итог выглядит как три
поля через табуляцию, например `ok`, путь пакета и `0.411s`. В показанном ниже
провале текущий вывод содержит строку `--- FAIL:` с именем теста, строку с
файлом, номером строки и сообщением, затем `FAIL` и итог с `FAIL` вместо `ok`.
Код завершения документация не описывает; текущая реализация при провале
возвращает `1`.

Статус говорит, прошли ли тесты. Часть итога со временем меняется от прогона к
прогону:

- **без пакетов в аргументах** (`go test` в каталоге пакета) кэш не
  используется, каждый прогон выполняет тесты и печатает время;
- **с пакетами в аргументах** (`go test .`) успешный результат запоминается.
  Если повторить команду, не меняя код, файлы и переменные окружения, которые
  читают тесты, вместо времени будет `(cached)`: тесты не выполнялись. Флаг
  `-count=1` заставляет выполнить их заново.

Программа ниже запускает `go test` на пакете курса в обеих формах, а затем на
копии с испорченным ожиданием. Время у прогонов разное, поэтому эталона вывода
нет: программа сама проверяет, где `(cached)` обязан быть, где его быть не
должно и что испорченная копия проваливается.

## Установка на свой компьютер и самопроверка

Чтение раздела ничего не устанавливает: установка готова, когда самопроверка
прошла в вашем терминале. Для чтения курса она не нужна; вернитесь сюда перед
практикой на своём компьютере и не позже урока 1.12. Установке нужна сеть,
среде курса — нет.

Файл скачивают со страницы [go.dev/dl](https://go.dev/dl/), под свою систему и
архитектуру процессора. Согласно странице загрузок, текущие выпуски требуют
macOS 13 Ventura или новее и Windows 10 или Windows Server 2016 или новее. Для
Linux минимальное ядро зависит от архитектуры: архивам 386, amd64, arm64 и
armv6l нужно ядро 3.2 или новее, а некоторым архитектурам — более новое,
например linux/ppc64 требует ядро 3.13. Требование для выбранного архива
сверяют на той же странице. Пакетные менеджеры официальная инструкция не
описывает: они могут ставить Go в другие места, самопроверка для них та же.

### Linux

1. Если `/usr/local/go` остался от прежней установки, уберите его:
   распаковывать архив поверх старого нельзя.
2. Распакуйте архив в `/usr/local`, чтобы появился `/usr/local/go`; обычно для
   этого нужны права администратора. Команда распаковки приведена в
   [официальной инструкции по установке](https://go.dev/doc/install).
3. Допишите в конец файла `$HOME/.profile` (или `/etc/profile`, чтобы
   изменение касалось всех пользователей) строку из официальной инструкции:
   `export PATH=$PATH:/usr/local/go/bin`. Она добавляет `/usr/local/go/bin` в
   конец списка `PATH`.
4. Изменение профиля вступает в силу при следующем входе в систему. Чтобы не
   ждать, выполните в терминале `source $HOME/.profile` — по той же
   инструкции такая команда применяет изменение сразу.

### macOS

1. Откройте скачанный `.pkg` и пройдите установщик. Он ставит Go в
   `/usr/local/go` и добавляет `/usr/local/go/bin` в `PATH` файлом
   `/etc/paths.d/go`.
2. Откройте новое окно терминала.

### Windows

1. Запустите скачанный `.msi`. По умолчанию он ставит Go в `Program Files` или
   `Program Files (x86)` (место можно изменить) и сам меняет переменные
   окружения.
2. Откройте новое окно терминала.

### Самопроверка

1. Создайте пустую папку, например `go-check`, вне своих проектов: ни в ней,
   ни выше не должно быть `go.mod`. В новом окне терминала перейдите в неё:
   `cd`, пробел и путь к этой папке. Внутри проекта `go version` может
   сообщить версию, выбранную проектом, а `GOMOD` — чужой модуль.
2. Выполните `go version`. Ожидается скачанная версия и пара
   «система/архитектура» вашего компьютера; текущая команда печатает их одной
   строкой, как в разделе «Что проверяет `go version`».
3. Выполните `go env GOOS GOARCH GOMOD`. Ожидаются три строки: система и
   архитектура, обычно те же, что сообщила `go version`, и значение `GOMOD`,
   которое не является путём к `go.mod`.

Если результат другой:

- **команда `go` не найдена** — откройте новое окно (в Linux выполните
  `source $HOME/.profile` или войдите в систему заново), затем проверьте, что
  `bin` вашей установки есть в `PATH`;
- **версия не та, что вы ставили** — в `PATH` раньше стоит другая установка Go;
- **`GOMOD` напечатал путь к `go.mod`** — текущий каталог лежит внутри модуля:
  этот `go.mod` находится в нём или выше. Выберите каталог вне проектов и
  повторите проверку; по той же причине `go version` там могла сообщить
  версию, выбранную проектом;
- **в Linux `go` найдена, но не запускается** — возможно, архив для другой
  архитектуры процессора;
- **старая инструкция велит задать `GOROOT` и `GOPATH`** — для установки их
  больше задавать не нужно.

Прошедшая самопроверка значит, что команда `go` находится и запускается.
Работает ли сборка, покажет первая сборка или запуск программы.

## Вопрос 1

В каталоге проекта `shop` лежит `go.mod`. В подкаталоге `shop/tools` лежит
свой `go.mod`, а в `shop/tools/gen` файла `go.mod` нет. Вы перешли в
`shop/tools/gen` и выполнили `go env GOMOD` в модульном режиме. Что напечатает
команда?

Варианты ответа:

- A. Путь к `go.mod` в `shop`: модуль определяется корнем всего проекта.
- B. Путь к `go.mod` в `shop/tools`: это первый `go.mod` на пути вверх от
  текущего каталога.
- C. Значение, которое не является путём к `go.mod`: в `shop/tools/gen` файла
  `go.mod` нет.
- D. Сообщение об ошибке: команду запустили не из каталога с `go.mod`.

Прежде чем смотреть ответ, назовите каталоги, в которых команда `go` ищет
`go.mod`, в порядке поиска.

**Правильный ответ: B.**

Вариант A не учитывает, что поиск останавливается на первом найденном
`go.mod`, а `shop/tools` — отдельный модуль, в `shop` он не входит. Вариант C
прекращает поиск в текущем каталоге, хотя он продолжается вверх; значение без
пути бывает, только когда `go.mod` нет нигде выше. Вариант D приписывает
`go env` требование модуля: вне модуля она тоже печатает значение.

## Вопрос 2

Go установлен, `gopls` — нет. В проекте без внешних зависимостей и без ошибок
в коде вы выполняете `go run .`, а затем `go test .`. Что произойдёт?

Варианты ответа:

- A. Обе команды отработают; без `gopls` редактор не будет подсказывать имена и
  подчёркивать ошибки.
- B. Обе команды откажут: без языкового сервера команда `go` не может разобрать
  исходный текст.
- C. `go run .` сначала установит `gopls`, а затем соберёт и запустит
  программу.
- D. `go run .` отработает, а `go test .` откажет: тестам нужен разбор кода
  языковым сервером.

Прежде чем смотреть ответ, объясните, какая из двух программ — `go` или
`gopls` — вызывает другую.

**Правильный ответ: A.**

Вариант B путает службу редактора с тулчейном: компилирует команда `go` со
своими инструментами, а `gopls` сам вызывает `go`. Вариант C приписывает
`go run` установку: `gopls` ставят отдельно, например командой `go install`.
Вариант D делит команды тулчейна на зависящие и не зависящие от `gopls`, хотя
в примере урока без `gopls` работали и `go run`, и `go test`.

## Вопрос 3

В каталоге проекта лежат `go.mod` и `main.go`. Вы выполнили `go run .`, и
терминал показал три строки: `обработано записей: 2` в стандартном выводе,
затем `файл настроек не найден` и `exit status 3` в потоке ошибок. Код
завершения `go run` ненулевой. Какое утверждение верно?

Варианты ответа:

- A. Программа запустилась; `exit status 3` добавила команда `go`, а в каталоге
  проекта по-прежнему только `go.mod` и `main.go`.
- B. Все три строки — сообщения компилятора: программа не собралась, поэтому
  исполняемого файла нет.
- C. Все три строки напечатала программа, а `go run` оставила в каталоге
  проекта исполняемый файл для повторного запуска.
- D. Программа запустилась; `файл настроек не найден` и `exit status 3`
  напечатала команда `go`, потому что обе строки пришли в поток ошибок.

Прежде чем смотреть ответ, объясните, по каким признакам вы отделили строки
программы от сообщения команды `go`.

**Правильный ответ: A.**

Вариант B не замечает строку в стандартном выводе: при ошибке компиляции
программа не запускается, и стандартный вывод пуст. Вариант C приписывает
программе строку о её коде завершения и ждёт файл в проекте, хотя `go run`
собирает файл во временном каталоге и удаляет его; файл в каталоге оставляет
`go build`. Вариант D различает строки по потоку, а программа и команда `go`
пишут в один поток ошибок; `exit status 3` — сообщение `go`, а строку о файле
настроек напечатала программа.

## Вопрос 4

Вы установили Go, открыли новое окно терминала в каталоге чужого проекта и
выполнили `go version`. Команда напечатала строку с версией и завершилась с
кодом 0. Что из этого следует?

Варианты ответа:

- A. Проект соберётся: команда сообщила версию, значит, компилятор и
  компоновщик работают.
- B. Команда `go` находится через `PATH` и запускается; соберётся ли проект,
  покажут только сборка или запуск.
- C. Версия подходит проекту: если бы проекту нужна была более новая, команда
  не напечатала бы версию.
- D. В этом каталоге есть модуль: вне модуля `go version` завершилась бы с
  ошибкой.

Прежде чем смотреть ответ, назовите, что `go version` не делает.

**Правильный ответ: B.**

Вариант A считает проверку версии сборкой, но `go version` ничего не
компилирует и не компонует. Вариант C не учитывает пример урока: с
`GOTOOLCHAIN=local` в проекте, которому нужна более новая версия, `go version`
прошла, а `go run .` отказала. Вариант D приписывает команде требование модуля,
а `go version` работает и вне проектов.

## Вопрос 5

На компьютере `go env GOOS GOARCH GOHOSTOS GOHOSTARCH` печатает строки `linux`,
`amd64`, `linux`, `amd64`. Вы задаёте в окружении этой команды `GOOS=windows`
и повторяете её. Что будет напечатано?

Варианты ответа:

- A. `windows`, `amd64`, `linux`, `amd64`: цель сборки сменилась, а система
  тулчейна осталась прежней.
- B. `windows`, `amd64`, `windows`, `amd64`: `GOHOSTOS` следует за `GOOS`.
- C. `linux`, `amd64`, `linux`, `amd64`: `go env` показывает систему компьютера,
  окружение на неё не влияет.
- D. Сообщение об ошибке: тулчейн для Linux отвергнет цель Windows.

Прежде чем смотреть ответ, объясните, что описывает пара `GOOS`/`GOARCH`, а
что — `GOHOSTOS`/`GOHOSTARCH`.

**Правильный ответ: A.**

Вариант B не учитывает, что `GOHOSTOS` и `GOHOSTARCH` описывают сам тулчейн и
из окружения не читаются. Вариант C путает цель сборки с системой тулчейна:
`GOOS` берётся и из окружения. Вариант D ждёт проверки от `go env`, а она пару
не проверяет; к тому же сборка для другой системы — обычная цель из урока 1.1.

## Вопрос 6

Вы дважды подряд выполнили `go test .` в каталоге пакета, ничего не меняя.
Первый итог — `ok`, путь пакета и `0.412s`, второй — `ok`, путь пакета и
`(cached)`. Что верно?

Варианты ответа:

- A. Во второй раз тесты не выполнялись, результат взят из кэша; выполнить их
  заново заставит `-count=1`.
- B. Во второй раз тесты выполнились мгновенно, потому что уже собраны, и время
  просто не напечатано.
- C. `(cached)` появится и после повторного `go test` без аргументов: форма
  команды на кэш не влияет.
- D. Второй прогон провалился: при успехе на месте `(cached)` всегда стоит время.

Прежде чем смотреть ответ, назовите, какая часть итога говорит об успехе, а
какая меняется от прогона к прогону.

**Правильный ответ: A.**

Вариант B считает `(cached)` быстрым прогоном, но с этой пометкой тесты не
выполнялись вовсе. Вариант C не учитывает форму команды: без пакетов в
аргументах кэш результатов не используется. Вариант D читает успех по части со
временем, хотя об успехе говорит статус `ok`.

## Вопрос 7

Вы установили Go и в окне терминала, открытом ещё до установки, выполнили
`go version`. Терминал сообщил, что команда `go` не найдена. Что сделать
сначала?

Варианты ответа:

- A. Открыть новое окно терминала и повторить `go version` в каталоге вне
  проектов: старое окно не видит изменённый `PATH`.
- B. Установить `gopls`: без языкового сервера команда `go` не запускается.
- C. Перейти в каталог проекта с `go.mod`: вне модуля `go version` не работает.
- D. Задать вручную `GOROOT` и `GOPATH`: без них терминал не найдёт установку.

**Правильный ответ: A.**

Вариант B путает службу редактора с командой `go`, которой `gopls` не нужен.
Вариант C приписывает `go version` требование модуля, а внутри чужого проекта
она к тому же может сообщить версию, выбранную проектом. Вариант D повторяет
старые советы: команду терминал ищет через `PATH`. Если новое окно не помогло,
проверьте, что каталог `bin` установки есть в `PATH`.
